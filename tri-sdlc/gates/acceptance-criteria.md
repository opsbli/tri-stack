# SDLC 阶段门禁验收标准总表（单一事实源）

> 本表是 tri-sdlc 阶段门禁的**唯一事实源**。子 SKILL 产出交付物后，tri-sdlc MUST 逐条对照本表判定，
> 并将判定结果写入该阶段的 `gate-report.md`。**NEVER 凭印象放行，NEVER 在报告外另立标准。**

## 一、判定口径

| 判定值 | 含义 | 是否阻断 |
|---|---|---|
| `PASS` | 交付物中能定位到满足该条的**具体证据**（文件+位置） | 否 |
| `FAIL` | 缺失、空泛、或证据不满足条目要求 | **必检项 FAIL 即阻断** |
| `WARN` | 建议项未满足，或必检项满足但质量偏弱 | 否（记入报告） |
| `N/A` | 该条对本项目不适用，**MUST 附不适用理由** | 否（无理由的 N/A 视为 FAIL） |

**门禁总判定规则**：

- 必检项（M）**全部** `PASS` 或**带理由的** `N/A` → 门禁 `PASS`
- 必检项存在 ≥1 条 `FAIL` → 门禁 `FAIL`，MUST 输出修订意见并回炉该阶段
- 建议项（R）`FAIL`/`WARN` **不阻断**，但 MUST 记入报告「建议改进项」

**通用必检项（P0–P8 每阶段均适用，编号 `Pn-M0`）**：

| 编号 | 验收标准 | 判定方式 |
|---|---|---|
| `Pn-M0` | 本阶段规定的交付物文件**全部存在**于指定目录，且**无 `<...>` / `TODO` / `待定` 占位残留**（显式登记为「后续阶段确定」并说明时间点的除外） | 文件存在性 + 全文占位符扫描 |

## 二、P0 立项与规划（tri-charter）

**交付物**：`P0-charter/charter.md`

### 必检项

| 编号 | 验收标准 | 判定方式 |
|---|---|---|
| `P0-M1` | 业务背景陈述完整，且**核心问题为可证伪的单句**——能回答「谁在什么场景下遇到什么损失」；「提升体验」「更加智能」类空泛表述判 FAIL | 定位核心问题句并检验可证伪性 |
| `P0-M2` | 项目范围含 **in-scope 与 out-of-scope 双清单**，各 ≥1 条，且两者无交叉矛盾 | 双清单存在性 + 交叉比对 |
| `P0-M3` | **三维可行性**（技术 / 资源 / 时间）均有明确结论（可行 / 有条件可行 / 不可行）**及依据**，缺任一维判 FAIL | 逐维检查结论+依据 |
| `P0-M4` | 里程碑 ≥2 个，每个含 **名称 + 交付内容 + 目标日期**（绝对或相对日期均可） | 逐条检查三要素 |
| `P0-M5` | 项目目标可度量——至少 1 条目标带**量化指标或可判定的完成定义** | 目标条目检查 |

### 建议项

| 编号 | 建议标准 |
|---|---|
| `P0-R1` | 干系人清单（角色 + 关注点） |
| `P0-R2` | 关键假设与约束登记 |
| `P0-R3` | 初步风险登记（风险 + 影响 + 应对方向） |

## 三、P1 需求分析（tri-require）

**交付物**：`P1-requirements/requirements.md`、`user-stories.md`、`acceptance-criteria.md`、`traceability-matrix.md`

### 必检项

| 编号 | 验收标准 | 判定方式 |
|---|---|---|
| `P1-M1` | 每条需求有**唯一 ID**（推荐 `REQ-nnn`），无重号、无跳跃解释缺失 | ID 唯一性扫描 |
| `P1-M2` | **功能性与非功能性需求分列**；非功能覆盖 **性能 / 安全 / 兼容** 三类各 ≥1 条，不适用需显式声明理由 | 分区检查 + 三类覆盖检查 |
| `P1-M3` | 用户故事符合「作为&lt;角色&gt;，我希望&lt;能力&gt;，以便&lt;价值&gt;」三段式，且每条可回链需求 ID | 逐条格式与回链检查 |
| `P1-M4` | **每条需求 ID ≥1 条验收标准**，且为**可观测可判定**表述（含触发条件 + 预期结果）；「运行正常」类判 FAIL | 逐条可判定性检验 |
| `P1-M5` | 每条需求标注优先级（**MoSCoW** 的 Must/Should/Could/Won't 或 **RICE** 分值） | 优先级字段完整性 |
| `P1-M6` | 可追溯矩阵覆盖**全部**需求 ID：无**孤儿需求**（无验收标准）、无**无源验收标准**（不对应任何需求 ID） | 双向连通性检查 |
| `P1-M7` | requirements.md 标注**基线版本号 + 冻结时间**，声明本轮需求已冻结 | 基线字段检查 |

### 建议项

| 编号 | 建议标准 |
|---|---|
| `P1-R1` | 需求来源标注（访谈 / 调研 / 竞品分析） |
| `P1-R2` | 需求变更流程说明 |
| `P1-R3` | 术语表（统一领域语言） |

## 四、P2 方案设计（tri-design）

**交付物**：`P2-design/design.md`、`api-contract.md`、`data-model.md`

### 必检项

| 编号 | 验收标准 | 判定方式 |
|---|---|---|
| `P2-M1` | 总体架构含**分层与模块划分**，每个模块职责可一句话陈述，模块间依赖方向明确 | 模块表/图 + 职责句检查 |
| `P2-M2` | **需求覆盖率 100%**：P1 全部 `Must` 级需求 ID 在设计中有对应落点（模块/接口/表），可经矩阵查证 | 需求 ID 逐条比对 |
| `P2-M3` | 数据模型含**实体 / 字段 / 类型 / 约束 / 主外键**，关键查询路径有索引说明 | 逐实体字段表检查 |
| `P2-M4` | 每个接口含 **方法 + 路径 + 入参 + 出参 + 错误码**，错误码 ≥2 类（至少覆盖参数错误与业务/系统错误） | 逐接口五要素检查 |
| `P2-M5` | ≥1 个**时序图或状态机**覆盖核心链路（关键业务流程或状态流转） | 图/表存在性 + 链路覆盖 |
| `P2-M6` | 技术选型每项含 **候选 ≥2 + 选定 + 选定理由**；单候选无对比判 FAIL | 逐项三要素检查 |

| `P2-M8` | 容量与性能目标为**可度量指标**（如 QPS / P99 响应时间 / 并发数 / 存储量），无量纲表述判 FAIL | 指标可度量性检验 |

|---|---|
| `P2-R1` | 可扩展性设计（水平扩展点、插件点） |

## 十二、可扩展性

1. **新增验收标准**：在对应阶段的必检/建议项表格**追加一行**，编号顺延（如 `P2-M9`），门禁审计逻辑零改动。
2. **新增阶段**：在本表追加一节 `Pn 阶段名（tri-xxx）` 并给出必检/建议项，同步在 `tri-sdlc/SKILL.md` §阶段清单与子SKILL路由 追加一行、`children/` 建对应子 SKILL 目录。
3. **调整阈值**：`P4-M3` 覆盖率、`P6-M3` 通过率等阈值可在项目 `manifest.md` 的「阈值覆写」区声明项目级取值，**优先级高于本表默认值**；覆写 MUST 记录理由。
4. **裁剪阶段**：通过 `tri-sdlc` §执行剖面 选择 `full` / `standard` / `lite`，未纳入剖面的阶段在 manifest 标记「未启用」，不触发其门禁。
