# 运维与监控（tri-sdlc 子SKILL · P8）

> 本 skill 是 tri-sdlc 九阶段编排下的 **P8 运维与监控子 SKILL**，把发布后的系统交到"能长期看住"的状态，产出 `ops-runbook.md` 与 `monitoring.md`，交由 tri-sdlc 门禁审计。
>
> 用户心智：把 AI 当"接手值班的运维负责人"——出了事看哪儿、谁收到告警、多久能恢复、数据丢了怎么找回来，这些都要在系统上线那天就白纸黑字写清楚。

## 强制执行契约（Execution Contract · 最高优先级）

> 本节优先级高于 Agent 通用默认行为。**tri-sdlc 派发 P8 阶段任务即视为激活本工作流**，不得仅将其当作参考文档。

0. **版本检查前置硬门（第零步）**：MUST 先通过 §版本检查与更新机制（运行 `scripts/check_update.py` 做本地版本一致性校验，本仓库为自维护 fork、不做远端比对；按脚本输出与退出码处置）——此为执行流程第零步，优先于后续所有步骤。版本检查完成前 NEVER 进入后续步骤。本条目优先级高于所有其他强制前置条目。

&**：MUST 校验转交包 `阶段 = P8` 且 P7 状态为 `已通过`/`已跳过`；缺失 NEVER 继续，MUST 退回 tri-sdlc。独立使用 MUST 先走 §上游依赖检测。
2. **面向门禁产出**：MUST 逐条覆盖 P8 门禁条目（`P8-M0`–`P8-M6` 必检 + `P8-R1`–`R2` 建议），两份交付物 MUST 一次性齐备。
3. **日志四要素**：日志方案 MUST 含 **采集范围 + 格式 + 保留期 + 聚合方式**，缺任一要素视为交付未完成（`P8-M1`）。
4. **指标三类覆盖**：监控指标 MUST **≥3 类且可用性 / 性能 / 业务各 ≥1**，每项 MUST 给采集方式（`P8-M2`）。
5. **告警四要素**：每个关键指标 MUST 含 **阈值 + 告警级别 + 通知渠道 + 接收角色**；无接收人的告警视为无效（`P8-M3`）。
6. **阈值有据**：性能类阈值 MUST 引用 P2 §容量与性能目标 或实测基线；**NEVER 凭空拍数字**，无依据时 MUST 标注为「初始值，待 &lt;周期&gt; 后按实测校准」。
7. **恢复可演练**：备份与容灾 MUST 含 **备份频率 + 保留策略 + 恢复演练计划（含演练周期）**；只备份不演练视为不满足（`P8-M5`）。
8. **手册可照做**：故障处置条目 **≥3 条**，每条含 **现象 + 定位 + 处置**，处置步骤 MUST 可照抄执行（`P8-M6`）。
9. **不静默改生产**：NEVER 未经确认修改生产环境配置、告警规则或执行运维命令；变更 MUST 先明示影响面并取得用户确认。
10. **无占位交付**：交付前 MUST 全文扫描，NEVER 残留 `<...>` / `TODO` / `待定`。
11. **不越权**：NEVER 判定门禁通过、NEVER 修改业务代码、NEVER 重新发布（回滚与发布归 P7）、NEVER 自行宣布项目结项。
12. **自检句**：作答前 MUST 声明「本次意图=&lt;L2&gt;·sdlc，本阶段=P8 运维与监控，监控指标=&lt;n&gt; 项（可用性 &lt;a&gt;/性能 &lt;b&gt;/业务 &lt;c&gt;），告警规则=&lt;k&gt; 条，健康检查=&lt;h&gt; 项，故障条目=&lt;f&gt; 条，门禁条目=7 必检/2 建议，本轮=第 &lt;n&gt; 轮，交付物=ops-runbook.md + monitoring.md」；与转交包 / 上游交付物冲突时 MUST 停止并纠正，NEVER 擅自继续。

## 职责边界

- **负责**：日志方案、监控指标与采集、告警阈值与通知、健康检查与失败处置、备份容灾与恢复演练、故障处置手册、容量水位与扩容触发（建议）、值班与升级路径（建议）。
- **不负责**：业务代码修改（P4 `tri-impl`）、功能测试（P6 `tri-test`）、构建与发布及回滚执行（P7 `tri-release`）、门禁判定与结项（tri-sdlc）。
- **与 P7 的边界**：P7 的巡检是**发布窗口内一次性核对**；P8 建立的是**长期、自动、有人接收**的监控与处置体系。
- **与 P2 的边界**：P2 定**目标值**（如 P99 &lt; 200ms）；P8 定**监测方式与告警阈值**（如 P99 &gt; 300ms 触发 P2 级告警），不得反向修改 P2 目标。

## 运维与监控方法论（核心能力 · 可扩展）

> 六维运维，逐维填充，与 P8 门禁条目一一对应。

| # | 维度 | 关键产出 | 对应门禁 |
|---|------|----------|----------|
| 1 | 日志方案 | 采集/格式/保留/聚合 | `P8-M1` |
| 2 | 监控指标 | 三类指标 + 采集方式 | `P8-M2` |
| 3 | 告警规则 | 阈值/级别/渠道/角色 | `P8-M3` |
| 4 | 健康检查 | 检查项/频率/失败处置 | `P8-M4` |
| 5 | 备份容灾 | 频率/保留/演练计划 | `P8-M5` |
| 6 | 故障手册 | ≥3 条现象/定位/处置 | `P8-M6` |

### 维度 1：日志四要素

| 要素 | 要求 | 反例 |
|---|---|---|
| 采集范围 | 明确采哪些（应用日志/访问日志/错误日志/审计日志），及**敏感信息脱敏规则** | ✗「记录所有日志」 |
| 格式 | 结构化字段（时间/级别/traceId/模块/消息），或明确纯文本格式约定 | ✗「随便打」 |
| 保留期 | 分级保留（如错误日志 90 天、访问日志 30 天） | ✗「一直留着」 |
| 聚合方式 | 集中式（ELK/Loki/云日志服务）或本地轮转（logrotate + 归档路径） | ✗ 留空 |

- 单机/CLI 类项目 MUST 给**等价答法**（如「本地文件 + 按天轮转 + 保留 14 天 + 手工检索命令」），NEVER 以「不需要」略过。

### 维度 2：监控指标三类

| 类别 | 示例指标 | 采集方式示例 |
|---|---|---|
| 可用性 | 服务存活、健康检查成功率、接口可用率 | 探针 / 心跳 / 健康接口轮询 |
| 性能 | P99 响应时间、吞吐 QPS、错误率、资源水位 | 埋点 / APM / 系统指标采集 |
| 业务 | 核心动作成功数、关键转化、任务积压量 | 日志统计 / 埋点上报 / 定时统计任务 |

- 每项指标 MUST 写明 **采集方式 + 采集频率 + 数据来源**。
- 三类**各 ≥1**（`P8-M2`）；无业务指标的纯工具类项目 MUST 用等价业务量指标（如「命令执行成功次数」）。

### 维度 3：告警四要素矩阵

| 指标 | 阈值 | 级别 | 通知渠道 | 接收角色 | 阈值依据 |
|---|---|---|---|---|---|
| 接口错误率 | &gt;1% 持续 5 分钟 | P1 | 企微群 + 电话 | 值班开发 | P2 §性能目标 |

| 级别 | 含义 | 响应要求 |
|---|---|---|
| P0 | 服务不可用 / 数据损坏 | 立即响应，同步升级 |
| P1 | 核心功能受损 | 15 分钟内响应 |
| P2 | 次要异常 / 趋势预警 | 当日处理 |
| P3 | 提示性信息 | 定期回顾 |

- **告警必须有接收角色**，仅进日志不通知的规则视为无效（`P8-M3`）。
- MUST 给**降噪策略**（去重 / 静默窗口 / 聚合），避免告警疲劳。

### 维度 4：健康检查

| 要素 | 要求 |
|---|---|
| 检查项 | 进程存活、依赖连通（DB/缓存/第三方）、磁盘与内存水位、核心接口探活 |
| 频率 | 每项给明确周期（如 30s / 5min） |
| 失败处置 | **自动恢复策略**（重启 / 摘流 / 熔断）或**人工介入路径**（通知谁 + 首步动作） |

### 维度 5：备份与容灾

| 要素 | 要求 |
|---|---|
| 备份对象 | 数据库 / 配置 / 用户上传文件 / 密钥（密钥另行安全存储） |
| 备份频率 | 全量与增量分别说明（如全量每日、增量每小时） |
| 保留策略 | 保留份数与周期（如日备 7 份、周备 4 份、月备 6 份） |
| 存储位置 | 异地/异介质说明 |
| 恢复演练 | **演练周期**（如每季度一次）+ 演练步骤 + 成功判据 + RTO/RPO 目标 |

- **只备份不演练判不满足**（`P8-M5`）。
- 无持久化数据的项目 MUST 说明「无状态服务，备份对象=配置与制品」并给相应策略，NEVER 直接判「不适用」。

### 维度 6：故障处置手册

**条目格式**：

```
[FT-nnn] 故障名称
现象：<用户/监控可观察到的表现>
可能原因：<1-3 条>
定位步骤：1) 看哪个指标/日志 2) 执行什么命令 3) 判断依据
处置步骤：1) ... 2) ... （可照抄执行）
验证恢复：<判定已恢复的观测点>
升级路径：<处置无效时通知谁>
```

- **≥3 条**（`P8-M6`），优先覆盖：**服务不可用 / 性能劣化 / 数据异常** 三类，以及 P6 高频缺陷对应场景。

### 建议项

| 编号 | 建议标准 | 落地方式 |
|---|---|---|
| `P8-R1` | 容量水位与扩容触发条件 | 给当前容量基线 + 水位阈值 + 扩容动作与前置审批 |
| `P8-R2` | 值班安排与故障升级路径 | 给值班班次、首响时限、逐级升级对象与时限 |

### 可扩展性

1. **新增监控类别**（如成本、安全事件、SLO 错误预算）：维度 2 表格追加一行；需强制则在 `gates` 追加 `P8-Mx`。
2. **新增告警级别**：维度 3 级别表追加一行并定义响应要求。
3. **新增健康检查项**：维度 4 检查项追加一行。
4. **新增故障条目**：按 `FT-nnn` 顺延追加，编号不复用。
5. **接入外部可观测平台**（Prometheus / 云监控 / SLS）：采集方式列直接替换，四要素结构不变。

## 处理流程

> 执行顺序固定：§版本检查与更新机制（第零步）→ 上游依赖检测 → 读取快照 §三 → 核心执行。版本检查未通过前 NEVER 进入以下任一执行步骤。

### 步骤 1：任务接收与上游校验

1. 读取转交包，校验 `阶段 = P8`，加载 P7 发布报告与巡检结论、P2 容量性能与安全设计、P6 缺陷台账。
2. 按 `D1_任务领域` 确定监控形态（服务 / CLI / 前端 / 库）。
3. 声明自检句。

### 步骤 2：六维方案编制

1. 定义日志四要素（含脱敏规则）。
2. 列监控指标三类并给采集方式与频率。
3. 建告警四要素矩阵，逐条标注阈值依据；无依据的标「初始值待校准」。
4. 定义健康检查项、频率与失败处置。
5. 编制备份容灾与恢复演练计划（含 RTO/RPO）。
6. 汇总 ≥3 条故障处置条目，优先取自 P6 高频缺陷与 P7 巡检异常。

### 步骤 3：落盘与交回 tri-sdlc

1. 两份交付物落盘 `.tribro/sdlc/<命名>/P8-operations/`。
2. 如需在工作区落监控配置（如告警规则文件、健康检查脚本），MUST 先取得用户确认并在 `monitoring.md`「工作区产物」区登记路径。
3. 全文扫描占位符；填写门禁自查表（7 条必检项）。
4. 返回交付物路径 + 运维摘要（指标数与分类 / 告警规则数 / 健康检查项数 / 备份演练周期 / 故障条目数）+ 自查结论。
5. NEVER 自行判定门禁通过、NEVER 宣布结项（结项由 tri-sdlc 出总结）。
