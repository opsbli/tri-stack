# 蒸馏工作流方法论（distill-workflow）

> 被 tri-god 在识别对象类型=工作流（workflow）后加载。
> **目标**：把一套散落在实例、经验、SOP 中的流程，抽象成可复用、可执行的 **workflow skill**——具备明确触发条件、步骤序列、决策分支、契约与异常处理。

## 引用合规（MUST）

- 蒸馏基于真实工作流实例；引用他人流程文档须保留出处，NEVER 整段照搬内部机密流程未经授权。

## 核心信条

捕捉「流程 HOW it runs（如何运转）」而非「某一次 WHAT happened（发生了什么）」——从多个实例中抽象出**稳定的流程骨架与状态机**，而非记录单次执行。

## 五阶段流水线

### 阶段 1 · 观察 / 采集现有工作流实例

MUST 采集**多个真实实例**（≥2 个，单实例无法抽象）：谁在什么触发下、按什顺序、做了哪些步骤、在哪些点做决策、遇到异常如何处理。产出「实例采集清单」。

### 阶段 2 · 抽象出阶段与状态机

从实例中归纳共性，形式化为状态机：

| 抽象项 | 内容 |
|--------|------|
| 阶段（States） | 流程可划分为哪些稳定阶段 |
| 状态转移（Transitions） | 阶段间在什么条件下流转 |
| 触发条件（Trigger） | 整个流程由什么事件/信号启动 |
| 终条件（Terminal） | 流程在什么条件下结束（成功/失败） |

### 阶段 3 · 识别审批门与回炉点

MUST 显式标出流程中的**控制点**：

- **审批门（Gates）**：哪些阶段需人工/系统确认后方可推进。
- **回炉点（Rework loops）**：门未过时回退到哪个阶段、携带什么反馈。
- **禁跳门规则**：哪些阶段严禁跳过抢跑。

### 阶段 4 · 形式化为步骤清单 + 契约

将状态机落为可执行规格：

| 规格项 | 内容 |
|--------|------|
| 步骤序列 | 每个阶段的原子步骤（有序、可核对） |
| 决策分支 | 分支条件与各分支去向（if/else、多路） |
| 输入契约 | 每步的输入前置条件 |
| 输出契约 | 每步的产物与验收标准 |
| 异常处理 | 各步失败时的兜底/重试/上报策略 |

### 阶段 5 · 生成可执行 workflow skill

将上述规格封装为 workflow skill：

- **SKILL.md**：触发条件 + 状态机图（mermaid）+ 步骤序列 + 审批门/回炉点 + 输入输出契约 + 异常处理，用 MUST/NEVER 约束推进规则（禁跳门、回炉机制、最小化）。
- **配套**：实例来源清单、流程图、示例走查（跑一遍典型实例验证骨架成立）。

## 阶段化对接 tri-god 审批门

| tri-god 门 | 本方法论阶段 |
|---|---|
| 门① requirements.md | 目标流程、实例来源、复用范围、用途 |
| 门② design.md | 「加载 distill-workflow + 五阶段规划 + 状态机/审批门抽象计划」 |
| 门③ tasks.md | 拆解为实例采集 → 状态机抽象 → 门/回炉识别 → 形式化 → skill 构造任务（含复选框） |
| 执行 → implements.md | 各阶段执行记录 + 走查验证结果 |

## 质量红线（全过方可交付）

- [ ] 基于 ≥2 个真实实例抽象，非单次记录。
- [ ] 状态机完整：阶段 / 转移 / 触发条件 / 终止条件齐全。
- [ ] 审批门与回炉点显式标出，含禁跳门规则。
- [ ] 步骤序列 + 决策分支 + 输入输出契约 + 异常处理四项齐全。
- [ ] 产出 workflow skill 可独立调用，含状态机图与示例走查。
- [ ] 实例来源可追溯，尊重授权与出处。
