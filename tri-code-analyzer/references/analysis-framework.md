# 剖析框架（analysis-framework）

> 本文件是 tri-code-analyzer 的「角色/模式层」知识：每次剖析开始时按 §需要加载对应小节。所有规范受 SKILL.md §强制执行契约 约束（证据锚定铁律 > 结论置信标注 > 本文件其余内容）。

## §结论置信标注（契约第 10 条 · 每条结论产出前对照）

**三要素行内格式**：`结论……（置信度：高；依据：事实 known；来源：<URL 或 file:line>）`

| 要素 | 取值 | 规则 |
|---|---|---|
| 置信度 | 高 / 中 / 低 | 事实+证据锚充分=高；单一来源或部分采样=中；反向工程/未验证=低 |
| 依据类型 | `事实 known` / `计算 computed` / `推断 inferred` / `常识 common` / `框架 iframe` / `猜测 guess` | 六选一或组合（如 `推断 inferred + 常识 common`）；与本地证据锚不冲突 |
| 来源 | URL（官网/文档/规范/数据页）或 `file:line` 代码锚 | 存在可访问来源 MUST 附 URL；纯代码结论用本地锚；均无标注「无外部来源」 |

**六类依据判定**：

| 类型 | 适用场景 | 示例 |
|---|---|---|
| 事实 known | 代码直接可见的事实（路由表、依赖版本、目录结构） | 「项目使用 MyBatis（pom.xml:88）」（事实 known；来源：pom.xml:88） |
| 计算 computed | 由数据/公式/统计推导 | 「单测覆盖率约 34%（38/112 用例）」（计算 computed） |
| 推断 inferred | 由命名/结构/导入关系逻辑推断 | 「该模块疑似采用 CQRS（读模型与写模型分离）」（推断 inferred；来源：OrderQueryService.java:22） |
| 常识 common | 领域共识/通用最佳实践 | 「连接池未配置上限存在耗尽风险」（常识 common） |
| 框架 iframe | 框架/规范/官方文档定义的行为 | 「Pinia 为 Vue3 官方推荐状态库」（框架 iframe；来源：https://pinia.vuejs.org/） |
| 猜测 guess | 证据不足的主观判断 | 「该 TODO 可能未实现限流」（猜测 guess，低置信，需人工验证） |

**执行规则**：

1. 报告部分一/二/三中的**每个判断句**（「采用 X 架构」「存在 Y 风险」「遵循/偏离 Z 惯例」）MUST 带三要素标注；描述性铺陈（目录树罗列、代码引用本身）不强制。
2. 证据锚（`file:line`）满足「事实 known」的来源要求，二者互补不互斥：代码锚给可验证性，依据类型给可信度分类。
3. `guess` 类结论 MUST 标注低置信 + 「需人工验证」，且每份报告 `guess` 类结论占比 SHOULD ≤ 10%（超出说明采样不足，应回到阶段 1 补采样）。
4. 联网抓取的框架行为结论（框架 iframe）MUST 附官网 URL；官网不可达时降级为 `常识 common` 并标注「未联网核验」。

## §深度三档定义

| 档位 | 触发 | 范围 | 交付裁剪 |
|---|---|---|---|
| 快速导览 | 用户要「快速了解/概览」或代码库超大且未指定 | 依赖清单 + 入口 + 路由注册 | 仅部分一（精简）+ 部分四（架构图 1 张） |
| 标准剖析 | 默认 | 全维度，核心链路 2 条 | 五部分全量 |
| 深度穿透 | 用户要「深度/逐文件/吃透」 | 全维度 + 核心链路 ≥3 条 + 关键模块逐文件注解 | 五部分全量 + 附录：关键模块逐文件注解 |

## §管道：七阶段执行细则

### 阶段 0 教训预载

- 读取 `.tribro/code-analyzer/lessons.md`（历史执行沉淀的经验教训，契约第 9 条）；目录或文件不存在 → 静默跳过，NEVER 报错、NEVER 中断。
- 与本次剖析相关的教训 MUST 影响后续阶段行为（路径处理/栈卡偏差/采样策略调整），并在自检句「已读教训=<N 条/无文件>」体现。

### 阶段 1 定位

- 确定根路径；枚举顶层目录与配置文件（`package.json` / `pom.xml` / `build.gradle` / `requirements.txt` / `pyproject.toml` / `go.mod` / `Cargo.toml` / `*.csproj` / `CMakeLists.txt` / `oh-package.json5` / `pubspec.yaml` 等）。
- 产出：语言构成、构建体系、 monorepo 判定（workspaces/lerna/nx/pnpm-workspace）。
- 大仓库采样策略（入口优先）：`依赖清单 → 构建配置 → 启动入口 → 路由/导航注册 → 核心业务目录 → 外围工具`。NEVER 试图全库逐文件通读；按链路反查所需文件。

### 阶段 2 识别

- 按 `tech-stacks/INDEX.md` 探测信号匹配技术栈（框架+版本、状态库、ORM、MQ、测试框架）。
- 可选确定性预检：运行 `python scripts/stack_detect.py <repo>` 输出命中栈与缺信号清单，提升探测稳定性与可复现性；脚本不可用时退回读表判定。
- 命中 → 读对应栈卡，用「分析要点」预设该栈的目录惯例/路由/状态/异步预期。
- 未命中 → 执行 `acquire-unknown-stack.md` 协议；联网不可用时降级为「基于依赖清单与代码特征的反向工程」，并在报告头部声明知识层缺失。

### 阶段 3 拓扑（→ 报告部分一）

- 架构模式判定证据链：分层目录（layered）、领域目录（DDD/package-by-feature）、事件总线引用（EDA）、CQRS 读写分离痕迹。
- 模块依赖方向：以 import/require 分析上游→下游；标出循环依赖与高耦合区（一个文件被 >N 处导入的中心节点，N 按仓库规模取 10~30）。
- 服务间通信：同步（HTTP/RPC/GraphQL）与异步（MQ/Event Bus）的实际使用位置（证据锚）。
- 功能清单全景：按业务域枚举功能点 + 代码入口 + 状态判定（稳定/待完善）。「待完善」判据：TODO/FIXME 注释、空实现、被跳过的测试。

### 阶段 4 穿透（→ 报告部分二）

- 主链路选取：从路由注册表/入口 handler 中选**用户价值最高、调用链最深**的 2~3 条（深度穿透档 ≥3 条）。
- 逐层展开：每跳记录 `文件路径:行号 + 类/函数名`，直到持久层/外部 I/O 边界。
- 六维度「如有」判定（每维度结论 = 判定 + 证据锚或「未涉及」声明）：
  1. 路由设计：层级、中间件/拦截器（Auth/Log/RateLimit）、动态路由、权限校验点。
  2. 实体设计：Entity/DO、DTO、PO 的分层与转换机制（手写/MapStruct/AutoMapper/class-transformer）。
  3. 状态管理：前端全局状态（Redux/Pinia/Zustand/Provider）或后端状态机（XState/Spring StateMachine）+ 持久化策略。
  4. 异步与并发：async/await、Reactor/RxJava、Future/Channel、线程池配置、锁（ReentrantLock/Mutex/分布式锁）、原子操作。
  5. 配置管理：多环境加载（.env/application.yml/Apollo/Nacos）、热加载、敏感密钥注入与脱敏。
  6. 工具库与中间件：通用工具类、缓存/日志/MQ 的统一封装与切面。

### 阶段 5 横切（→ 报告部分三）

- 设计哲学归纳（DDD/响应式/事件驱动/FP/OOP 极简）——必须给出 ≥2 处代码证据。
- 设计模式落地：标注「模式名 + 具体代码位置」（如：策略模式消除 if-else 于 `Xxx.java:88`）。
- 风格四查：命名约定（各层各语言）、判空策略、异常体系（全局 handler/错误码）、Lint 配置存在性。
- 架构技术债：违背单一职责、高耦合低内聚、并发隐患、缺超时/重试控制的点，逐条附证据锚。

### 阶段 6 对照（技术栈校准）

- 逐项核对栈卡「分析要点」：项目是否遵循该栈惯例（目录/路由/状态官方推荐方案）。
- 偏离处标注：`偏离 + 影响 + 证据锚`（如：未用 Pinia 而用全局单例store，测试隔离差）。
- 栈卡与实践冲突时按 SKILL.md §知识装配顺序 的覆盖优先级处理并回写。

### 阶段 7 交付（→ 报告部分四 + 五 + 落盘 + 教训沉淀）

- Mermaid 四图生成并逐图过安全清单。
- 上手指南 + 重构优先队列。
- 按 SKILL.md §落盘规则 归档。
- **教训沉淀**：执行结束后 MUST 追加本次经验教训至 `.tribro/code-analyzer/lessons.md`（格式见 SKILL.md §进化契约：场景/问题/规避，MUST 可操作）；写入失败提示用户但不阻断交付。

> 报告四核心必备章节映射（用户视角的命名）：**部分一 = 项目概览**；**部分二 = 代码结构**；**部分三 = 潜在问题（架构技术债）**；**部分五 = 改进建议（重构优先队列）**。四者 MUST 齐备，缺任一即视为报告未完成。

## §部分一：架构师视角（必备小节）

1. 系统上下文与 C4：系统边界、外部依赖（DB/MQ/第三方 API/中间件）清单表（名称/类型/交互方式/证据锚）。
2. 架构模式与拓扑：模式判定 + 依据 + Mermaid 架构图引用。
3. 服务设计：划分方式、通信机制表（调用方→被调方/协议/场景/证据锚）。
4. 全局依赖关系：关键三方库表（库名/版本/用途/风险标注：停更/重大版本落后/已知漏洞面）。
5. 功能清单全景：业务域/功能点/代码入口/状态 四列表格。
6. 非功能质量与技术债：扩展性、高可用与韧性设计（容错/熔断/限流/重试/降级的实现位置或「未发现」判定）、架构技术债清单。

## §部分二：程序员视角（必备小节）

1. 目录蓝图：核心目录树 + 每目录职责注解 + 组织风格判定（by-layer vs by-feature）。
2. 路由设计：路由层级结构、拦截器链、动态路由与权限机制（如有）。
3. 主链路穿透：2~3 条链路的逐跳调用表（层级/文件:行号/方法/职责），配套时序图。
4. 实体与数据结构：核心实体关系 + 转换机制（如有）+ ER 图引用。
5. 状态管理：定义位置/流转路径/持久化（如有）。
6. 异步与并发：使用场景与任务队列、线程池/协程/锁的配置位置（如有）。
7. 配置管理：加载机制、热加载、密钥安全（如有）。
8. 工具库与基础设施：工具类清单 + 中间件封装位置（如有）。

## §部分三：设计与风格审计（必备小节）

设计哲学与证据、设计模式落地表（模式/位置/评价）、命名约定表（对象/风格/示例）、防御性编程与判空策略、异常处理体系（全局拦截/错误码体系/日志标准）、Lint 与静态检查配置存在性。

## §部分四：可视化图谱引擎（强制四图）

| 图 | 类型 | 内容 |
|---|---|---|
| 架构图 | `graph TD` | 分层与服务/模块拓扑（节点名中文标注） |
| 时序图 | `sequenceDiagram` | 核心链路从 API 入口穿透到持久层 |
| ER 图 | `erDiagram` | 核心实体与表关系 |
| 状态/流程图 | `stateDiagram-v2` 或 `flowchart` | 异步任务流转/状态机/关键控制流 |

## §Mermaid 安全清单（每图产出前逐项过）

1. 节点/边标签不含英文双引号、反斜杠；含特殊字符的标签用中文改写。
2. `sequenceDiagram` 的 participant 别名不含空格与连字符（用下划线）。
3. `erDiagram` 关系标签用 `: 描述` 短语，描述内不用逗号。
4. 节点 id 用 ASCII，显示名用 `id[中文]` 形式。
5. 子图（subgraph）标题不含括号。
6. 无未闭合的代码块标记；每图独立成块，前后空行。

## §部分五：上手与行动指南（必备小节）

1. 断点调试路线：首个断点的 `文件:行号` + 选择理由（最长链路交汇点/最高频入口）+ 建议的调试路径顺序。
2. 新功能开发 Checklist：按本项目实际分层给出次序（如 ① 定义 Entity/DTO → ② 增加 Service → ③ 注册 Router/Controller → ④ 配置环境变量 → ⑤ 注册测试），每步给出**本项目中的参照文件**（模仿现有范例而非抽象建议）。
3. 重构建议优先队列：P0（正确性/并发隐患）/ P1（可维护性）/ P2（风格统一），每条 = 问题 + 证据锚 + 建议 + 影响面。
