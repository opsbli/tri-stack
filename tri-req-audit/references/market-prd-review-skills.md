# 市面 PRD / 需求文档审核 skill 注册表（委派契约单一事实源）

> **本文件是 tri-req-audit「二跳委派」的唯一事实源。** 优先级、调用契约、可用性探测方式、
> 降级路径均以此为准；SKILL.md 内的候选表为速查，冲突时以本文件为准。
>
> **形态归属**：本文件登记的被执行方属「**中介路由 + 具体执行**」二跳形态中的**具体执行**方，
> **不注册**为 tri-intent 的下游路由项。该二跳形态已在 `tri-forge/references/family-spec.md` §五 登记。

---

## 一、登记口径（收录判据）

| 判据 | 要求 |
|---|---|
| **职能对得上** | 必须是「**审核 / 审查 / 评审**需求文档或 PRD」，而非**撰写** PRD、生成原型、做需求采集 |
| **输入对得上** | 能消费「一份需求文档 / PRD 文本或文件」，不强制要求原型链接、代码库或在线协作环境 |
| **输出可聚合** | 产出可被本 skill 聚合（问题清单 / 分级结论 / 就绪度判定），而非仅给一段散文建议 |
| **可探测** | 有稳定的安装落点（平台用户级 / 项目级 skills 目录），可被门③ 的可用性探测命中 |

> **不收**：纯撰写型（`prd-writer` / `prd-assistant` / `prd-expert` / `prd-authoring`）、
> 原型生成型（`lofi-prototype` / `hifi-prototype` / `web-hifi-prototype`）、
> 需求采集型（`pm-idea-to-feature` / `requirements-to-prd`）、综合产品包（`product-manager-skills`——
> 含「评审 PRD」但主体是六领域知识包，职能不单一，仅作**备选提示**不作为委派目标）。

---

## 二、优先级序（门③ MUST 按此顺序探测与委派）

| 优先级 | slug | 版本（实测） | 一句话能力 | 何时选用 |
|---|---|---|---|---|
| **1 · 首选** | `prd-review` | 1.0.0 | 审查人工或 AI 生成的软件产品需求文档，判断产品 / UX / UI / 前端 / 后端 / 测试**能否据此开工**，识别并去重流程、状态、权限、字段、交互、异常、数据与验收问题，输出 **P0/P1/P2 分级 + 岗位就绪度 + 产品决策清单** | **默认路径**——其输出形态（分级 + 就绪度）与本 skill 的聚合层天然对齐 |
| **2 · 备选** | `requirement-testability-review` | 2.3.2 | 需求**可测性**审查：两级门禁（一级 8 项快筛出达标卡，二级 12 维度深审出雷达图），支持多格式文件 / 在线文档 / 原型链接 / 截图 OCR / 粘贴文本 | 当审核重点是**验收标准可测性**，或用户明确要求可视化产物（达标卡 + 雷达图）时 |
| **3 · 场景特化** | `bg-requirement-review` | 1.0.0 | **B 端 / G 端**需求文档审阅，以「技术管理者 + 资深产品专家」双视角做系统性初审，识别方案合理性、逻辑矛盾、设计优化空间与遗漏风险 | 当项目为 B/G 端，或用户明确要求**管理者视角初审**时 |

> **多候选同时可用时的选择规则**：按「用户显式指定 → 场景匹配（B/G 端取 3、可测性诉求取 2）→ 优先级序（取 1）」三级判定。
> **NEVER 为了「多跑几个」而并发委派多家**——重复结论会在聚合层制造噪声；如确需交叉验证，MUST 在报告中显式标注为「交叉验证模式」并说明取舍。

## 三、调用契约（每个候选 MUST 按此契约委派）

| 契约项 | 要求 |
|---|---|
| **输入** | `requirements.md` 的**内容或路径**（全文，NEVER 截断后喂入） |
| **附加上下文** | 审核视角（若用户指定）、项目类型（B/G 端与否）、已知的「待补充项」摘要 |
| **调用方式** | 以该 skill 的**自然语言触发语**发起（按其 `description` 的触发词），NOT 直接调用其内部脚本 |
| **输出解析** | 提取「问题条目 + 分级 + 就绪度 + 决策清单」；无法结构化时**保留原文**并记 `parse=raw` |
| **回执登记** | MUST 把「探测结果 / 实际调用结果原文 / 解析状态」写入 `delegation-receipts.json` |
| **失败处置** | 记为「调用失败」，**继续尝试下一优先级候选**；NEVER 编造其结论 |

---

## 四、可用性探测（门③ 第 1 步）

逐一按优先级序检查候选是否已安装，记录三态：

| 探测落点 | 说明 |
|---|---|
| `~/.workbuddy/skills/<slug>/SKILL.md` | 平台用户级安装（本机主路径） |
| `~/.codebuddy/skills/<slug>/SKILL.md` | 另一客户端用户级安装 |
| `<项目根>/.workbuddy/skills/<slug>/SKILL.md` | 项目级安装 |

| 状态 | 含义 | 后续 |
|---|---|---|
| **已安装** | 落点存在且 `SKILL.md` 可读 | 进入委派 |
| **未安装** | 全部落点均不存在 | 尝试下一优先级候选；全部未安装 → 兜底审核 |
| **调用失败** | 已安装但调用 / 解析失败 | 记回执，尝试下一候选；全部失败 → 兜底审核 |

> **探测只读**：NEVER 因探测而安装、修改或删除候选 skill；安装是用户的显式决定。
> 提示语（可选给出，不阻断）：`python ops/install-skills.py --target <目标目录>`。

---

## 五、降级路径（兜底审核）

当优先级序内**全部候选**为「未安装」或「调用失败」时：

1. 报告中标注 `delegation=unavailable`，并附**实际尝试记录**（依次探测了哪些 slug、各自三态）
2. 改用 `references/audit-dimensions.md` 的 **D1–D8 自带规则**完成审核
3. 在报告「结论可信度」区注明：**未获得市面 skill 的岗位就绪度与决策清单视角**，通用产品视角的覆盖弱于委派审核
4. 把「建议安装哪一家 + 安装命令」写入报告的「后续建议」区

> **兜底 ≠ 降级标准**：D1–D8 是为家族下游契约定制的判据，在「可消费性」一项上**强于**市面通用 skill；
> 兜底审核的问题分级标准与委派审核**完全一致**（同一份 §分级判据），NEVER 因降级而放宽。

## 六、新增候选的登记方式（零改动扩展）

在本文件 §二 注册表追加一行，填写：slug / 版本 / 一句话能力 / 何时选用；并在 §三 契约表确认其输入输出可归入既有契约
（输入 = 需求文档全文、输出 = 可聚合的问题清单）。**探测与委派逻辑零改动**——门③ 按本表遍历。

若新候选的输入形态无法归入既有契约（如需原型链接作为必需输入），MUST 在 §三 单列「契约变体」小节说明，NEVER 静默套用默认契约。
