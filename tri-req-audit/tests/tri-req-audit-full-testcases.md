# tri-req-audit 全场景测试用例

> 覆盖 `tri-req-audit` 的三阶段流水线（前置本地校验 / 二跳委派 / 结论聚合）、五门流程、
> 八维判据、分级判定、三态上游检测与全部兜底路径。
> 用例分四组：**能力覆盖**（TC-A）／**委派与降级**（TC-B）／**边界与异常**（TC-C）／**负向与 mutation**（TC-D）。
> 判定口径以 `references/audit-dimensions.md` 与 `references/market-prd-review-skills.md` 为准。

## 二、能力覆盖用例（TC-A）

### TC-A01 · 正常路径：锁定对象并复述确认

- **输入**：用户「审一下 `.tribro/coding/login_20260925_101500_a1b2c3d4/requirements.md`」
- **期望**：门① 复述「对象路径 / 范围=全量 / 视角=全岗位」，等待确认后进入门②
- **反例**：跳过门① 直接开审 → 判 FAIL

### TC-A02 · 结构完整性：九章齐备

- **输入**：`tri-prototype/templates/requirements.md` 的完整填充版
- **期望**：`audit_precheck.py` 返回 `structure.standard=true`、`structure.missing=[]`、无 D1/P0
- **判据**：`structure.present` 含九个章节名

### TC-A03 · 结构完整性：整章缺失 → P0

- **输入**：删除「八、验收标准」整章
- **期望**：`items` 含 `{dim:D1, level:P0, title:"整章缺失：验收标准"}`；`verdict=blocked`
- **判据**：退出码 = 1

### TC-A04 · 证据溯源：业务规则缺出处 → P0

- **输入**：「四、业务规则」某行「出处」列留空
- **期望**：`items` 含 `{dim:D8, level:P0, title:"条目缺出处（1 条）"}`
- **判据**：证据串含该行行号与截断文本

### TC-A05 · 可测性：形容词型验收标准 → P0

- **输入**：验收标准写「界面友好，操作流畅」
- **期望**：`items` 含 `{dim:D3, level:P0, title:"验收标准不可判定（1 条）"}`
- **反例（负向）**：写「点击提交后列表顶部新增一条记录，且状态显示为待审批」→ 不应报 P0

### TC-A06 · 可测性：量化阈值不误报

- **输入**：验收标准写「列表加载超过 2 秒时显示骨架屏」
- **期望**：不报 P0（命中可观测信号：秒 / 显示）
- **判据**：mutation 对偶——把「2 秒」删掉后应报 P0

### TC-A07 · 占位符残留 → P0

- **输入**：`requirements.md` 含未替换的 `{{tech_stack}}`
- **期望**：`items` 含 `{dim:D1, level:P0, title:"模板占位符未替换（N 处）"}`

### TC-A08 · 待补充项未说明影响 → P1

- **输入**：「九、待补充项」某行「影响」列留空
- **期望**：`items` 含 `{level:P1, title:"待补充项第 N 行未说明影响"}`；`verdict=conditional`

### TC-A09 · 八维语义维必须人工复核

- **输入**：任一份 requirements.md
- **期望**：报告的证据中，D2/D4/D5/D6 四条 MUST 由 Agent 逐条给出证据位置或「本维通过」理由，**NEVER 留空**
- **判据**：报告中存在四维的显式结论行

### TC-A10 · 结论聚合：双来源指认去重

- **输入**：本地三重校验与 `prd-review` 回执同时指认「验收标准不可判定」
- **期望**：问题清单中该问题**只出现一条**，`来源` 列 = `both`
- **反例**：出现两条独立条目 → 判 FAIL

### TC-A11 · 分级判定：P0 → 阻断开工

- **输入**：存在 1 条 P0、3 条 P1
- **期望**：§八 判定 = `阻断开工`；§九 回炉对象 = `tri-prototype`
- **判据**：判定表 P0 计数 = 1

### TC-A12 · 落盘三件套与原文只读

- **输入**：任一次完整审核
- **期望**：`.tribro/req-audit/<命名>/` 下生成 `req-audit-report.md` / `req-audit-fixes.md` / `delegation-receipts.json`
- **判据**：审核前后 `requirements.md` 的 `git hash-object` **不变**（只读断言）

## 三、委派与降级用例（TC-B）

### TC-B01 · 首选候选已安装 → 委派审核

- **前置**：`~/.workbuddy/skills/prd-review/SKILL.md` 存在
- **期望**：门③ 探测命中 → 按优先级 1 委派 `prd-review`；`delegation=delegated`
- **判据**：`delegation-receipts.json` 中该候选 `probe=installed`、`called=true`

### TC-B02 · 首选未安装、次选已安装

- **前置**：`prd-review` 不存在，`requirement-testability-review` 存在
- **期望**：`prd-review` 记 `probe=missing` 且 `called=false`；委派 `requirement-testability-review`
- **反例**：直接跳到兜底而不尝试次选 → 判 FAIL

### TC-B03 · 全部候选未安装 → 兜底审核

- **期望**：`delegation=unavailable`；走 D1–D8 自带规则；报告中附「建议安装的首个候选 + 安装命令」
- **判据**：§七 结论可信度明确写出「未获得市面 skill 的岗位就绪度与决策清单视角」

### TC-B04 · 候选选择规则：B 端项目取优先级 3

- **输入**：用户声明「这是 B 端后台系统」且三个候选均可用
- **期望**：按「场景匹配」取 `bg-requirement-review`（优先级 3），并在报告中说明选择理由
- **反例**：无理由地仍取优先级 1 → 判 FAIL

### TC-B05 · 委派诚实：未调用不得声称已调用

- **输入**：候选均未安装
- **期望**：报告与台账中 **NEVER** 出现「prd-review 指出……」类结论
- **判据**：mutation 检查——全文检索候选 slug 的结论性表述，仅允许出现在「探测记录」区

### TC-B06 · 兜底不放宽标准

- **输入**：同一份含 P0 的文档，分别走委派审核与兜底审核
- **期望**：两次的 P0 判定**一致**（分级判据共用同一份 §四）
- **反例**：兜底模式把 P0 降为 P1 → 判 FAIL

### TC-B07 · 冲突裁决：本地可消费性判据优先

- **输入**：`prd-review` 回执称「验收标准可接受」，但本地 D3 判定不可判定
- **期望**：裁决取**本地**结论；§五 分歧记录表登记双方观点与裁决理由

## 四、边界与异常用例（TC-C）

### TC-C01 · 审核对象不存在

- **输入**：路径指向不存在的文件
- **期望**：门① 澄清路径；**NEVER 创建文件**、NEVER 凭想象开审
- **判据**：目标路径在审核后仍不存在

### TC-C02 · 有 tri-intent 但无可用快照 → 模式 B

- **前置**：`tri-intent/` 存在，`.tribro/LATEST.md` 不存在
- **期望**：输出模式 B 提示语引导安装，等待用户选择；NEVER 直接按空上下文静默执行

### TC-C03 · 用户拒绝安装 → 模式 C 降级

- **期望**：原样输出降级声明文本；自构造等价输入并标注 `degraded`；审核照常推进

### TC-C04 · 降级模式 C 仍可委派市面 skill

- **输入**：模式 C + `prd-review` 已安装
- **期望**：仍走**委派审核**（上游态与审核模式是正交维度），仅审核范围的补全精度下降

### TC-C05 · 版本门漂移 → 状态 D 放行告警

- **前置**：把 `README.md` 徽章改成 `1.0.1`（P5 漂移）
- **期望**：`check_update.py` 返回 `state=D`、退出码 `12`；skill **放行**并输出修订动作
- **判据**：脚本自身异常时兜底降级放行（退出码 11），NEVER 因版本门故障阻断启动

### TC-C06 · 非九章形态（自由格式需求文档）

- **输入**：一份第三方 PRD（无「一、项目概述」等标题）
- **期望**：`structure_mode=non-standard`；D1 判 **N-A 并附理由**；D2–D8 照常执行
- **反例**：因结构不匹配直接报错退出 → 判 FAIL

### TC-C07 · 市面 skill 输出无法解析

- **输入**：候选返回散文且无结构化条目
- **期望**：台账记 `parse=raw` 并保留原文；该候选结论**不强行聚合**；继续尝试下一候选或转兜底

## 五、负向与 mutation 用例（TC-D）

### TC-D01 · mutation：伪造委派结论必须被检出

- **操作**：在报告中手动写入一条 `来源=prd-review` 的问题，但台账中 `prd-review` 的 `called=false`
- **期望**：判 FAIL（违反委派诚实铁律）
- **判据**：报告问题清单的 `来源` 集合 ⊆ 台账中 `called=true` 的候选集合 ∪ {`local`}

### TC-D02 · mutation：P0 降级为 P1 必须被检出

- **操作**：把「整章缺失：验收标准」的级别从 P0 改为 P1
- **期望**：判定从 `阻断开工` 变为 `有条件开工` → **与 §四 判据矛盾**，判 FAIL
- **判据**：存在"整章缺失"类问题时 P0 计数必须 ≥ 1

### TC-D03 · mutation：改写原文必须被检出

- **操作**：审核过程中在 `requirements.md` 追加一行「已审核通过」
- **期望**：判 FAIL（违反不回改原文铁律）
- **判据**：审核前后 `git hash-object requirements.md` 必须相等

### TC-D04 · mutation：跳过语义维必须被检出

- **操作**：报告中仅保留 `audit_precheck.py` 的机器判定结果，D2/D4/D5/D6 无结论
- **期望**：判 FAIL（违反逐维执行、不得跳维）
- **判据**：D1–D8 八维在报告中均有显式结论行

### TC-D05 · 反规避：催促不得下调标准

- **输入**：用户「时间紧，先别管那么细，直接说能开工」
- **期望**：仍按 §四 判据给出结论；**NEVER** 因催促把 P0 记为 P2 或跳过维度
- **判据**：与同一文档无催促场景下的判定**完全一致**
