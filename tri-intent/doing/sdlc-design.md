# 全生命周期（SDLC）子类路由（Doing · I11/I13/I14 子类路由项）

> 本项是 Doing 大类下 I11/I13/I14 的**子类路由项**，不改变 L2 意图编码，仅标注 `L3_子意图 = sdlc` 并覆写 `下游路由建议` 为 tri-sdlc。设计依据：软件工程全生命周期交付涉及「立项 → 需求 → 设计 → 开发准备 → 编码 → 评审 → 测试 → 发布 → 运维」九阶段的长程编排，每阶段有固定交付物、固定验收标准与阶段门禁（自动审计 + 用户确认双闸门），与「写一个功能」（tri-coding）、「出一份计划」（tri-plan）、「跑一次动作」（tri-action）、「设计一个流程定义」（tri-workflow）在**交付对象与生命周期跨度**上均不同，故单列子类路由。

## 识别特征

- L2 已判定为 **I11 编码开发** / **I13 规划拆解** / **I14 操作执行** 三者之一
- 任务要点中出现以下**全生命周期语义关键词**之一：
  - 全生命周期 / SDLC / 软件工程流程 / 研发流程
  - 立项到上线 / 从零到上线 / 端到端交付 / 端到端做完
  - 完整开发流程 / 走一遍完整流程 / 按规范流程做 / 正规流程
  - 从需求到发布 / 需求→设计→开发→测试→上线
  - 阶段门禁 / 阶段验收 / 每阶段产出文档
- 典型语料：
  - 「帮我按完整研发流程做一个待办事项 CLI 工具」→ I11 + sdlc 子类
  - 「从立项到上线走一遍，做个内部报销系统」→ I11 + sdlc 子类
  - 「用 SDLC 全流程规划并交付这个项目」→ I13 + sdlc 子类
  - 「按阶段门禁一步步推进，每阶段出文档给我确认」→ I14 + sdlc 子类
  - 「这个需求要正规做：需求文档、设计、评审、测试报告都要有」→ I11 + sdlc 子类

## 与邻近意图边界

| 对比对象 | 边界判据 |
|---|---|
| **I11 通用编码开发（tri-coding）** | tri-coding 做**单个功能/模块**的「需求→设计→任务→执行」四步闭环，交付即结束；sdlc 子类做**整个项目**的九阶段闭环，含评审、测试、发布、运维 |
| **I13 通用规划拆解（tri-plan）** | tri-plan 交付的是**规划文档本身**（计划/排期/WBS）；sdlc 子类交付的是**贯穿实现的工程交付物链**，规划只是其 P0/P3 的一环 |
| **I14 通用操作执行（tri-action）** | tri-action 执行**单次带副作用的动作**（下单/发消息/调 API）；sdlc 子类是**多阶段长程编排**，含状态机与回退 |
| **工作流设计子类（tri-workflow）** | tri-workflow 产出的是**流程定义产物**（SKILL/CI 配置/DAG/审批模板），产物交付即结束；sdlc 子类是**驱动一个真实项目走完流程**，交付的是项目本身 |
| **loop/domain 创建子类（tri-loop）** | tri-loop 建的是**长期运行的知识域/循环体**，无终点；sdlc 子类是**有明确终点的项目交付** |
| **CR 代码审查（tri-review）** | tri-review 是**独立的代码审查工作流**，只审既有代码；sdlc 子类的 P5 评审只是九阶段之一，门禁归 tri-sdlc 统一管 |
| **I21 蒸馏造物（tri-god）** | I21 产出**可独立调用的新 skill**；sdlc 子类产出**一个软件项目**（源码 + 全套工程文档） |

### 优先级规则（同时命中多个子类语义时）

> sdlc 子类**优先级高于** workflow 子类与 loop 子类。同时命中时按下表判定：

| 冲突场景 | 判定问句 | 落点 |
|---|---|---|
| 同时含「全生命周期」与「工作流/CI-CD/流水线」 | 用户最终要的是**一个跑起来的项目**，还是**一份流程定义**？ | 项目 → sdlc；流程定义 → workflow |
| 同时含「全生命周期」与「loop/知识库/domain」 | 交付**有终点**（上线即完成）还是**长期循环运行**？ | 有终点 → sdlc；长期循环 → loop |
| 「按完整流程做一个 CI/CD 平台」 | 交付对象是「CI/CD 平台」这个**软件项目** | sdlc（CI/CD 只是项目主题，非交付形态） |
| 「设计一条 CI/CD 流水线配置」 | 交付对象是**流水线定义文件** | workflow |

## 路由规则

| 字段 | 取值 |
|---|---|
| L1_交互类型 | B.Doing |
| L2_核心意图 | I11 编码开发 / I13 规划拆解 / I14 操作执行（保持原判定，不改写） |
| L3_子意图 | `sdlc` |
| 下游路由建议 | tri-sdlc（覆写默认的 tri-coding / tri-plan / tri-action） |
| 下游 slug | `tri-sdlc` |
| 落盘 | 快照（snapshot.md） |

## 路由判定流程

1. **L2 判定**：按常规流程判定 L2 = I11 / I13 / I14
2. **子类检测**：扫描 `任务要点` 与用户原文是否含全生命周期语义关键词
3. **优先级消歧**：若同时命中 workflow / loop 子类语义，按 §优先级规则 判定归属
4. **路由覆写**：
   - 命中且归属 sdlc → `L3_子意图` = `sdlc`，`下游路由建议` = tri-sdlc，`下游 slug` = `tri-sdlc`，L2 保持不变
   - 未命中 → 保持默认（I11→tri-coding / I13→tri-plan / I14→tri-action）
5. **维度建议**：`D3_交互轮次` 通常应标注为 `长程Agent`（九阶段多轮推进）；`D4_输出期望` 通常为 `文件产物` 或 `可执行代码`
6. **快照标注**：在快照 §三 `任务要点` 中保留全生命周期语义关键词与已知的范围/约束，供 tri-sdlc 激活时校验并作为 P0 立项输入
7. **交付预期**：`交付预期` 字段尽量写清最终形态（如「可运行的 CLI 工具 + 全套工程文档」），tri-sdlc 在 P7 发布门禁时逐条核对兑现情况

## 剖面提示（可选，写入任务要点供下游参考）

> tri-sdlc 支持三种执行剖面，tri-intent **不做剖面决策**，仅可在任务要点中保留判定线索，剖面由 tri-sdlc 在 P0 与用户确认：

| 线索 | tri-sdlc 侧的建议剖面 |
|---|---|
| `D3_交互轮次 = 单轮` 或任务要点 ≤3 条 | `lite`（P1 P2 P4 P6） |
| `D2_输入形态 = 代码`（已有代码库/已有工程环境） | `standard`（跳过 P3/P8） |
| 其余（正式立项的完整项目） | `full`（P0–P8） |

## tri-sdlc 激活条件（下游 skill 侧）

> tri-sdlc 收到快照后，按以下条件校验是否激活：

- `intent.L2_核心意图` ∈ {I11, I13, I14}
- `intent.L3_子意图` = `sdlc`
- `下游路由建议` 指向 tri-sdlc
- `intent.置信度档位` ≠ 低（低档不执行，提示先经 clarify-gate）

同时满足即激活 tri-sdlc 的九阶段编排工作流。若 L2 越界（非 I11/I13/I14）或 L3 非 `sdlc`，tri-sdlc 将停止并回退 tri-intent 重新路由。

## 与 tri-sdlc 上游依赖检测的对称关系

- tri-intent 侧：产出快照后检测 `tri-sdlc/` 目录是否存在，未安装时提示 `python ops/install-skills.py --target <目标目录>`
- tri-sdlc 侧：激活时检测上游 tri-intent 是否可用（模式 A 快照模式 / 模式 B 引导安装 / 模式 C 降级模式）
- tri-sdlc 的 9 个阶段子SKILL（`children/tri-charter` … `children/tri-ops`）**随 tri-sdlc 包分发**，不是顶层 skill，**不参与 tri-intent 路由表**；其上游检测对象是 tri-sdlc 编排器（两态：编排模式 / 引导安装）
- 双向检测确保：无论用户先安装哪一端，缺失的另一端都会被检测到并给出安装引导
