# I11 编码开发（Doing）

## 识别特征

- 动词为 **写/实现/开发/加个功能/搭个 + 代码产物**
- 面向**新增能力**，非修复现有故障
- 典型语料：「写个登录组件」「实现文件上传接口」「加个防抖 hook」

## 与邻近意图边界

- vs **I12 调试修复**：I11 造新功能，I12 修已有故障
- vs **I08 翻译转换**：语言互转归 I08，写新逻辑归 I11
- vs **I13 规划拆解**：I11 出代码，I13 出方案/任务清单（不写实现）

## 前端设计方向子类（frontend-design · 子类路由）

**触发语义**：任务要点为「界面设计方向 / 风格锚点选定 / 配色字体结构方案 / 动效设计与评审 / 多变体探索」等**设计语义**，而非代码实现。

**路由规则**：`L3_子意图` 标注为 `frontend-design`，`下游路由建议` **直接覆写为 tri-frontend-design**（一跳），L2 保持 I11 不变。

**MECE 依据**：「一个 L2 意图（I11）对应一个一跳下游」，仅由 `L3_子意图` 区分——产出设计方向与令牌规格（CSS 令牌/动效基线/多变体方案）→ tri-frontend-design；产出可运行代码实现 → tri-coding 默认。

**对称双向检测**：tri-intent 的下游依赖检测在此场景仅需检测源码树 `tri-frontend-design/`，缺失即提示安装；tri-frontend-design 独立使用时反向检测 tri-intent 可用性（三态：快照模式/引导安装/降级模式）。

**边界细则**：「实现这个页面」/「写个登录组件」产出可运行代码 → 仍走 tri-coding 默认；「给这个界面定个风格 / 出几个配色方向 / 加动效并评审」只出设计方向不出代码 → tri-frontend-design。设计先行后需落代码时，由 tri-frontend-design 交付令牌规格，tri-coding 依令牌实现，两者按交付对象衔接不竞争。

## 动效实现子类（motion · 子类路由）

**触发语义**：任务要点含「生成动画/动效代码、Lottie 集成、转场/微交互/加载态实现、动画代码审查修复」等**动效实现语义**。

**路由规则**：`L3_子意图` 标注为 `motion`，`下游路由建议` **直接覆写为 tri-lottie**（一跳），L2 保持 I11 不变。

**MECE 依据**：I11 下三子类以交付对象区分——设计方向与令牌规格 → tri-frontend-design；动画代码/Lottie 集成/动效审查 → tri-lottie；一般编码 → tri-coding 默认。tri-frontend-design 的「动效设计与评审」止于设计基线；tri-lottie 接手规格落地的可运行代码与资产集成，两者按交付对象衔接不竞争。

**对称双向检测**：tri-intent 的下游依赖检测在此场景需同时检测 `.tribro/skills/tri-lottie/` 与源码树 `tri-lottie/`，缺失即提示安装；tri-lottie 独立使用时反向检测 tri-intent 可用性（三态：快照模式/引导安装/降级模式）。

## 全生命周期子类（sdlc · 子类路由）

**触发语义**：任务要点含全生命周期语义（全生命周期 / SDLC / 研发流程 / 立项到上线 / 端到端交付 / 完整开发流程 / 从需求到发布 / 阶段门禁）。

**路由规则**：`L3_子意图` 标注为 `sdlc`，`下游路由建议` **覆写为 tri-sdlc**（一跳），L2 保持 I11 不变。详见 `sdlc-design.md`。

**MECE 依据**：写一个功能/模块 → I11 默认 tri-coding；按完整研发流程交付一个项目 → sdlc 子类覆写 tri-sdlc。该子类同样适用于表层动词为规划（I13）或推进执行（I14）的说法，**优先级高于 workflow / loop 子类**。
