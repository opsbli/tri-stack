# 代码审查（Doing · 特殊路由项）

> 本项是 Doing 大类下的**特殊路由项**，不占用 I01–I16 编号位，独立路由至 tri-review。设计依据：代码审查的输入形态（diff/PR）与产出形态（审查报告）与 I11 编码、I12 调试均不同，且 tri-review 采用两阶段分离关注点方法论，属于验证类而非执行类，故单列。

## 识别特征

- 出现 **审查 / review / CR / code review / 看看代码 / 过一遍代码 / code review 一下**
- 面向**既有代码变更的验证**，目标是产出审查报告而非改代码
- 典型语料：「帮我 review 一下这个 PR」「审查这个分支的改动」「做个 CR」

## 与邻近意图边界

- vs **I11 编码开发**：代码审查只看不改，I11 产出新代码
- vs **I12 调试修复**：代码审查是预防性验证，I12 是故障已发生后的修复
- vs **I10 分析处理**：代码审查聚焦代码变更的规格合规与质量，I10 是通用数据分析

## 路由规则

| 字段 | 取值 |

| L1_交互类型 | B.Doing |
| L2_核心意图 | 代码审查（特殊路由项，非 I 编号） |

| 落盘 | 快照（snapshot.md） |

## 模式判定（交付 tri-review 后由其自行判定）

tri-review 支持两种激活模式，由 tri-intent 快照的 `任务要点` 与 `dimensions.D2_输入形态` 共同决定：

- **独立调用模式**：用户直接要求 review 某分支/PR/diff，快照 `D2_输入形态` 含 diff/PR/分支信息
- **工作流集成模式**：由 tri-coding/tri-fix 在门③执行前确认时调用（此场景下 tri-intent 快照可能不直接路由，而由上游 skill 内部委托）

> 两种模式的输入契约差异详见 `tri-review/SKILL.md` §输入契约。
