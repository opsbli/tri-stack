# Doing 委托执行（二级路由 I06–I16 + I21 + CR）

用户心智：**「帮我把这件事做出来」**。产出是成果物，非知识。

## 二级判定

| 意图 | 一句话信号 | skill |
| --- | --- | --- |
| I06 内容生成 | 从零写文本成稿 | `I06-content-gen` |
| I07 内容改写 | 有原文，润色/扩缩/改风格 | `I07-rewrite` |
| I08 翻译转换 | 跨语言/跨格式等价转换 | `I08-translate` |
| I09 总结提炼 | 长输入压缩成要点 | `I09-summarize` |
| I10 分析处理 | 材料中挖洞察/评估/诊断 | `I10-analyze` |
| I11 编码开发 | 写新功能/组件/脚本 | `I11-coding`（全生命周期子类→`sdlc-design`） |
| I12 调试修复 | 修报错/异常/故障 | `I12-debug` |
| I13 规划拆解 | 出计划/方案/任务清单 | `I13-planning`（工作流设计子类→`workflow-design`；全生命周期子类→`sdlc-design`） |
| I14 操作执行 | 用工具真实执行动作 | `I14-execute`（工作流编排子类→`workflow-design`；循环/Loop 子类→`loop-design`；全生命周期子类→`sdlc-design`） |
| I15 多媒体生成 | 产图/图表/音视频/PPT | `I15-multimedia`（音乐创作子类→ tri-mm 委派 tri-music） |
| I16 头脑风暴 | 发散多个候选点子 | `I16-brainstorm` |
| I21 蒸馏造物 | 把人/工作流/技能提炼成可复用 skill | `I21-distill` |
| CR 代码审查 | 审查既有代码质量/规格合规 | `code-review`（特殊路由，无数字编码） |

## 消歧要点

- **有无原文**：无→I06，有→I07（同语言）/I08（跨语言格式）
- **代码类**：新增→I11，修故障→I12，审既有→CR，只出方案→I13，真跑起来→I14
- **单功能 vs 整项目**：写一个功能/模块→I11 默认 tri-coding；**按完整研发流程交付一个项目**（立项→需求→设计→编码→评审→测试→发布→运维）→ `L3_子意图`=sdlc，覆写 **tri-sdlc**，详见 `sdlc-design.md`。该子类同样适用于表层动词为规划（I13）或推进执行（I14）的说法，**优先级高于 workflow / loop 子类**
- **压缩 vs 洞察**：只提要点→I09，要评判结论→I10
- **产物是程序还是 skill**：业务代码/程序→I11，可独立调用的新 skill→I21
- **文章撰写子类**：I06 内容生成若任务要点含「写文章/去 AI 化文章/技术文章/博客/个人风格长文」语义，`L3_子意图`=article，`下游路由建议` 覆写 **tri-article**（一跳，详见 `../SKILL.md` §一路由映射表）
- **skill 锻造（内部工具）**：若用户要「按家族规范生成 / 补全 / 审计一个 skill」，由 **tri-forge** 内部专用工具承接（不经意图路由，用户直接调用）；tri-forge 产出的 skill 若具备下游身份，由 tri-forge 同步回填本路由表。其余蒸馏（人/工作流/方法论/事物）维持 **tri-god**，二者以「产出是否为合规 skill 包」区分
- 需求模糊/缺关键信息 → 先激活 `../clarify-gate`

## Doing 交付模板（委托执行专属 · 识别结果结构化呈现）

> 执行类核心审计点：**素材齐不齐、成果长什么样、验收标准、动作是否有副作用**。这是最需要用户二次确认的一类（会真实产出/执行）。

```yaml
# ===== Doing 意图确认卡 | 回复「确认」开工，或「修改：…」=====
你要我做: <复述交付任务，如「你要我用 React 写一个可搜索的表格组件」>

intent:
  L2_核心意图: <I06 生成|I07 改写|I08 翻译|I09 总结|I10 分析|I11 编码|I12 调试|I13 规划|I14 执行|I15 多媒体|I16 头脑风暴>

输入素材:
  已提供: <用户给的原文/代码/文件/数据，无则填 无>
  D2_形态: <文本|代码|图片|文档|表格|音视频|链接|无>
  缺失素材: <执行还需但用户没给的，无则填 无>

成果规格:
  产物类型: <文稿|代码|数据表|方案|图片|操作结果>
  D4_格式: <语言/框架/字数/结构，如「TypeScript + 函数组件」>
  数量: <如：3 个候选方案 / 1 篇>
  验收标准: <怎样算做对了，如「可编译、含单测」>

执行约束:
  技术/风格约束: <必须遵守的规范，无则填 无>
  副作用提示: <仅 I14：是否有下单/删除/发送等不可逆动作，其余填 无>

待确认项: <素材缺失或规格不清处，全清晰填 无>
交付预期: <一句话说明最终交付物>
# ===== 填入快照 snapshot.md §三，作为下游 skill 的交接输入。可选向用户轻量复述一次，原则上无需再次确认 =====
```

- 命中 `待确认项` → 先走 `../clarify-gate`
