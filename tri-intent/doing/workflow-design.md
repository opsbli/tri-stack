# 工作流设计子类路由（Doing · I13/I14 子类路由项）

> 本项是 Doing 大类下 I13/I14 的**子类路由项**，不改变 L2 意图编码，仅覆写 `下游路由建议` 为 tri-workflow。设计依据：工作流设计的产出形态（可执行工作流产物：SKILL.md/CI配置/审批模板/DAG配置）与通用规划（tri-plan）、通用执行（tri-action）不同，tri-workflow 采用 7 阶段混合智能流水线（环境感知→模板匹配→对话补全→编译优化→校验验证→多目标输出→迭代反馈），属于专业域执行而非通用规划/执行，故单列子类路由。

## 识别特征

- L2 已判定为 **I13 规划拆解** 或 **I14 操作执行**
- 任务要点中出现以下**工作流设计语义关键词**之一：
  - 工作流 / 流水线 / pipeline
  - 审批流 / 审批流程
  - 自动化流程 / 自动化编排
  - CI/CD / 持续集成 / 持续部署
  - 编排 / orchestration
  - 多步骤任务编排
  - 协作流水线
  - 数据处理流 / DAG
  - 故障响应流程
  - 发布流水线
  - 多 Agent 协作编排
- 典型语料：
  - 「帮我设计一个 CI/CD 流水线」→ I13 + 工作流设计子类
  - 「设计一个代码提交到部署的自动化流程」→ I13 + 工作流设计子类
  - 「帮我编排一个多 Agent 协作的工作流」→ I14 + 工作流编排子类
  - 「设计一个审批流，从申请到归档」→ I13 + 工作流设计子类

## 与邻近意图边界

- vs **I13 通用规划拆解（tri-plan）**：通用规划产出结构化步骤/计划，工作流设计子类产出可执行的工作流产物（含节点编排、依赖关系、SLA、触发条件）
- vs **I14 通用操作执行（tri-action）**：通用执行侧重运行/操作既有系统，工作流编排子类侧重设计并产出可复用的工作流定义
- vs **代码审查特殊路由（tri-review）**：代码审查有独立 L2 编码（非 I 编号），工作流设计保持 I13/I14 编码不变，仅覆写下游路由

## 路由规则

| 字段 | 取值 |
|---|---|
| L1_交互类型 | B.Doing |
| L2_核心意图 | I13 规划拆解（工作流设计子类）或 I14 操作执行（工作流编排子类） |
| 下游路由建议 | tri-workflow（覆写默认的 tri-plan/tri-action） |
| 落盘 | 快照（snapshot.md） |

## 路由判定流程

1. **L2 判定**：按常规流程判定 L2 ∈ {I13, I14}
2. **子类检测**：扫描 `任务要点` 是否含工作流设计语义关键词
3. **路由覆写**：
   - 命中关键词 → `下游路由建议` = tri-workflow，L2 保持不变
   - 未命中关键词 → `下游路由建议` = tri-plan（I13）或 tri-action（I14），保持默认
4. **快照标注**：在快照 §三 `任务要点` 中保留工作流设计语义关键词，供 tri-workflow 激活时校验

## tri-workflow 激活条件（下游 skill 侧）

> tri-workflow 收到快照后，按以下条件校验是否激活：

- `intent.L2_核心意图` ∈ {I13, I14}
- `下游路由建议` 指向 tri-workflow
- `任务要点` 含工作流设计语义

三者同时满足即激活 tri-workflow 的 7 阶段流水线。若 L2 越界（非 I13/I14），tri-workflow 将停止并回退 tri-intent 重新路由。

## 与 tri-workflow 上游依赖检测的对称关系

- tri-intent 侧：产出快照后检测 `tri-workflow/` 目录是否存在，未安装时提示 `skillhub install tri-workflow --dir <目标目录>`
- tri-workflow 侧：激活时检测上游 tri-intent 是否可用（模式 A 快照模式 / 模式 B 独立降级模式）
- 双向检测确保：无论用户先安装哪一端，缺失的另一端都会被检测到并给出安装引导
