# 宿主兼容与提问呈现（Host Compatibility · 提问呈现纪律）

> **定位**：家族横切约束——规定「需要用户决策的时机」在**不同宿主**下如何呈现。
> 本文件是**细则唯一真源**；各 skill 的 `## 宿主兼容与提问呈现` 节为**自包含瘦节**
> （独立安装场景下不依赖本文件可达，两处理论 MUST 一致，修订时同步）。
>
> **与版本检查门的区别**：版本检查是**可执行判定**（细则归 `references/version-check-spec.md`，
> 逻辑归 `scripts/check_update.py`，prompt 层不内联）；本条是**呈现纪律**，由 prompt 层直接执行，
> **无可执行载体**——不存在需要脚本判定的确定性分支，故不设 `host-compat-stub` 外的脚本层。

---

## 一、成因：呈现形式由宿主决定，不由 skill 决定

tri 家族的「需要用户决策」时机**全部**以宿主中立的自然语言书写，例如：

| 来源 | 原文形态 |
|---|---|
| tri-intent 门① | 「是否现在安装 `<slug>`？（是 / 否）」 |
| tri-intent 门② | 「是否立即执行该 skill 处理本次请求？（是 / 否）」 |
| tri-coding 门③ | 「主动询问用户两件事：① 是否调用其它 skill 协同 ② 是否有需要补充的需求」 |
| clarify-gate | 「需澄清项 + 建议默认 + 回复方式：逐条补充 / 回『按默认』/ 『继续』」 |
| 各 skill 审批门 | 「向用户结构化复述供审计；**通过后**方可进入下一门」 |

这类句式在**无交互式提问工具的宿主**（WorkBuddy / Trae / Cursor 等）中就是普通 Markdown 文本，
用户直接打字回复；在**提供交互式提问工具的宿主**（如 Proma 的 `AskUserQuestion`）中，
运行时系统指令会引导模型把「是否…？（是 / 否）」这类二选一句式**自动升级**为交互式问答横幅。

> **同一段 `SKILL.md`，两个宿主，两种呈现** —— 这不是 skill 的缺陷，而是宿主能力差异的投影。
> 因此家族内 `AskUserQuestion` / `request_user_input` / `clarify` 等工具名**零引用**（本分支 35 个 skill 实测 0 命中），
> 保持 skill 与宿主解耦。

## 二、家族约定（MUST）

在**提供交互式提问工具的宿主**中，凡触发「🔴 STOP 用户确认检查点」或 `clarify-gate` 的时机，
MUST 以**普通 Markdown 文本**呈现为聊天问题，**NEVER 调用交互式提问工具**
（`AskUserQuestion` / `ask_user_question` / `request_user_input` / `clarify` 及等价物）。

**判据只有一条**：该时机是否在 SKILL.md 中以 🔴 STOP / 「征询」/「（是 / 否）」/「主动询问用户」
形态登记为**用户确认检查点**。命中即受本条约束；未命中（如纯信息复述、无决策要求的进度同步）不受约束。

## 三、为何禁止选项化：契约失真对照表

家族门控的**用户回复契约**是为自由文本回复设计的。选项卡（interactive picker）会使其失真：

| 契约 | 出处 | 选项卡下的失真 |
|---|---|---|
| 「逐条补充」 | clarify-gate §澄清反问模板 | 多轮细化回复的空间被压扁，一次点选即终止对话 |
| 「回『按默认』全采纳建议值」 | clarify-gate §门控使用规则 2 | 仅在模型**恰好**把默认值建成 option 时可用；否则这个出口静默丢失 |
| 「『继续』表示无需澄清」 | clarify-gate §澄清反问模板 | 同左；退出澄清的显式出口不可靠 |
| 「是否调用其它 skill 协同 / 是否有补充」 | tri-coding 门③ | 开放式追问，选项化会**诱导**用户选「无补充」以求快速过关，削弱门③价值 |
| 「是否现在安装 / 是否立即执行」 | tri-intent 门①/门② | 两条不可逆动作（装、跑）各自留出口是有意设计；连续两个横幅会把「一次确认」感知成「两道摩擦」，用户倾向于无脑点「是」，与门的设计意图相反 |
| 审批门「通过后进入下一门」 | tri-coding 门①/门② 等 | 审批需用户**读文档再表态**，选项卡跳过了阅读环节 |

> **核心判断**：选项卡擅长收集**偏好**，家族门控收集的是**决策授权**——后者需要阅读、需要自由文本理由、
> 需要「按默认」这类非选项出口。用前者承载后者，形式越顺，授权越廉价。

## 四、边界与例外

1. **只管呈现，不管判定**：本条 MUST NOT 改动任何门控的**判定条件、触发时机、通过/驳回处置动作**。
   门该停的地方必须停，不因呈现形式变更而合并、跳过或自动放行。
2. **空转安全**：在**无**交互式提问工具的宿主中本条自然空转，行为与引入本条前完全一致——
   这是刻意设计，避免为兼容 Proma 而改变 WorkBuddy 侧既有行为。
3. **用户显式授权优先**：用户明确说「用选项问我」「弹窗问我」「直接给我按钮选」时，优先用户指令，
   该次交互可用交互式提问工具，**不视为违反本条**。
4. **M05 中止确认不受约束**：即时叫停/放行属「不落盘」类即时回应，走自然对话，本就无门控横幅。
5. **外部 skill 不辖**：本条只约束本家族 `tri-*` 成员（含 `tri-sdlc/children/*`）。
   第三方/上游 skill（如 `.workbuddy/_upstream/` 下的 `tri-mm` 家族，其自带
   「batch N questions in ONE AskUserQuestion call」约定）不在管辖范围——**NEVER 替其改契约**。
6. **NEVER 反向耦合**：本条落地后，NEVER 因此在新 skill 或新门控中引用具体宿主工具名
   （保持家族与宿主解耦；引用工具名即破坏跨宿主可移植性）。

## 五、自检钩子

作答前自检句**不新增**本条字段（避免自检句膨胀）；本条的自检归入既有门控自检：
凡声明「当前阶段=<门①/门②/门③/澄清门>」时，同时 MUST 满足本条的呈现要求。
