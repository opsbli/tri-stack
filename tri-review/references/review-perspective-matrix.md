# 代码审查视角矩阵

> 锚定对照基准：对照基准档 §4.1（engineering 方法域）。本文件为覆盖度补齐视角，不搬运角色正文。
> 最后验证日期：2026-09-21 ｜ 状态：新增（P2 增强项 E5）
> grep 检索模式：`视角` / `漏检` / `级别倾向` / `边界` / `幂等` / `契约` / `可观测`

## 定位与边界

- 本文件是 **Phase 2 代码质量审查的视角覆盖层**：`review-checklists.md` 给「维度 × 逐项判定」，本文件给「换视角扫一遍，防止维度内漏检」。
- 严重度档位沿用既有口径：**BLOCKER / MAJOR / MINOR**，偏好类记 `[PHASE2-NOTE]`。
- 定级纪律沿用 §3 rubric：**先证成可达性（`file:line` 触发路径）→ 先跑完反证据 → 再定级**。本文件不改变该纪律。
- **不适用**：架构级增量审计（走 Phase 0）；规格合规判定（走 Phase 1）。

---

## 使用方式

审查一段 diff 时，逐视角过一遍「该问的问题」，把命中的问题挂回对应 Phase 2 维度并定级。**NEVER 把「过完六视角」当成审查结论**——视角是保证覆盖，结论仍需证据。

| # | 视角 | 核心问句 | 对应 Phase 2 维度 |
|:--:|---|---|---|
| P1 | 正确性与边界 | 输入边界、异常路径、错误语义是否都覆盖？ | 健壮性 / 行为正确性 |
| P2 | 安全与信任 | 外部输入在哪被信任？权限在哪被校验？ | 安全性 |
| P3 | 并发与状态 | 有无共享可变状态？重复执行会怎样？ | 健壮性 |
| P4 | 性能与资源 | 有无 N+1、无界集合、未释放资源、无界重试？ | 性能 |
| P5 | 接口契约与兼容 | 对外契约是否被破坏？旧调用方还能活吗？ | 代码结构 / 可维护性 |
| P6 | 可观测与运维 | 出问题能定位吗？能回滚吗？会静默失败吗？ | 测试 / 健壮性 |

## P1 正确性与边界

**必问**

1. 边界值：空、零、一、极大、超长、负数、未初始化——哪几个在本变更的真实取值域内？
2. 异常路径：失败时的返回值/异常类型/错误码是否与调用方预期一致？
3. 部分成功：多步操作中间失败，已完成的步骤是否留下脏状态？

**常见漏检**：只测主流程 happy path；把「不可能发生」当论据（须给出不变量来源）；错误被 catch 后吞掉。

**级别倾向**：数据丢失/损坏且无防护 → BLOCKER；错误处理缺失导致问题被吞 → MAJOR。

---

## P2 安全与信任

**必问**

1. 外部输入在哪一点从「不可信」变成「可信」？该点是否有校验/净化？
2. 权限校验发生在**入口**还是**深层**？深层是否可被绕过（直连内部方法/任务/回调）？
3. 凭据、密钥、个人信息是否进入日志、错误信息、缓存、URL？

**常见漏检**：只审新增代码不看调用链外部；把框架自动防护当作已校验（须指出具体机制）；把内部服务间调用默认视为可信。

**级别倾向**：漏洞且生产路径可达 → BLOCKER；仅内部路径可达、影响有限 → MAJOR。

---

## P3 并发与状态

**必问**

1. 有无共享可变状态（单例字段、静态变量、缓存、文件、DB 行）被并发写？
2. **重复执行是否安全**（幂等）？重试、消息重投、用户双击会怎样？
3. 有无时序依赖（先写后读、异步回调顺序）？

**常见漏检**：把「我们并发量小」当论据（须给出量级与观察窗口）；幂等只考虑单次重试不考虑并发重投。

**级别倾向**：可导致数据错乱且无防护 → BLOCKER；仅在极端时序下出现 → MAJOR 并注明触发条件。

---

## P4 性能与资源

**必问**

1. 循环内是否有 I/O（DB/HTTP/文件）→ N+1？
2. 集合/缓存/队列是否有上界？无界增长由什么触发？
3. 连接、句柄、流、锁是否在所有路径（含异常路径）释放？
4. 重试是否有次数上限与退避？无限重试或零退避即为缺陷。

**常见漏检**：只看算法复杂度不看 I/O 次数；只测小数据集；超时配置为 0/无穷。

**级别倾向**：可导致服务不可用/资源耗尽 → BLOCKER；局部劣化且有既有缓解 → MAJOR。

---

## P5 接口契约与兼容

**必问**

1. 对外（HTTP API / 事件 / 库导出 / 数据库 schema / 配置文件）的签名或语义是否变化？
2. 旧调用方还能正常工作吗？是否存在未被追踪的调用方（脚本、外部系统）？
3. 默认值变化、枚举新增、字段可选性变化——是否属破坏性变更？

**常见漏检**：只改实现自测通过就认为兼容；忽略默认值/字段顺序/序列化格式的隐式契约；schema 变更未给数据回迁或双写窗口。

**级别倾向**：破坏既有契约且影响面跨模块 → BLOCKER；影响面可控且有迁移路径 → MAJOR。

---

## P6 可观测与运维

**必问**

1. 失败时是否有足够上下文的日志（可定位到请求/用户/资源，不含敏感信息）？
2. 是否**静默失败**（catch 后无日志无指标无告警）？
3. 变更是否可回滚？回滚是否需要数据回迁？
4. 新增的外部依赖 / 配置 / 开关，缺失时的降级行为是什么？

**常见漏检**：日志只记「失败」不记关键标识；新增指标无对应告警；开关默认关闭但无启用计划。

**级别倾向**：静默失败导致问题不可发现 → MAJOR；不可回滚且无兜底 → MAJOR（升级因子：生产路径）。
