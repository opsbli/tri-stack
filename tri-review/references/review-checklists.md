# 审查 Checklist 参考（Phase 1 + Phase 2 + 关闭纪律）

> 本文件从 SKILL.md 外移，是 Phase 1 / Phase 2 审查清单与关闭纪律的**单一事实源**。SKILL.md 仅留维度概览表 + 指针，逐项审查时查本文件。
> grep 检索模式：`Phase 1` / `Phase 2` / 维度名（如 `功能完整性` / `代码结构`）/ 标记名（如 `[PHASE1-FAIL]`）/ `严重度校准` / `反证据` / `覆盖度账本`。

---

## Phase 1: 规格合规审查（Spec Compliance）

> **目标**：验证「做了对的事」——代码变更是否完整、准确地实现了规格说明中定义的需求。
> **门禁规则**：存在 BLOCKER 级问题 → 标记 `[PHASE1-FAIL]`，直接退回，不进入 Phase 2。

### 1.1 功能完整性 (Functionality Completeness)

- [ ] **所有规格中定义的必选功能点均已实现** — 判定标准：逐条比对规格功能点清单，每一项在 diff 中有对应实现
- [ ] **所有规格中定义的输入类型均已处理** — 判定标准：规格中列出的输入类型在代码中有对应处理分支
- [ ] **所有规格中定义的输出格式均已遵循** — 判定标准：输出结构/格式与规格定义一致
- [ ] **所有规格中定义的边界条件均已覆盖** — 判定标准：规格中的边界条件在代码中有显式处理

### 1.2 行为正确性 (Behavioral Correctness)

- [ ] **正常路径（Happy Path）行为与规格一致** — 判定标准：核心业务流程的代码行为与规格描述一致
- [ ] **异常路径（Error Path）行为与规格一致** — 判定标准：错误处理流程与规格定义一致
- [ ] **空值/边界值处理与规格一致** — 判定标准：空值与边界值的行为与规格定义一致
- [ ] **并发/竞态条件已正确实现** — 判定标准：规格中涉及的并发场景在代码中有正确的同步/锁机制

### 1.3 需求对齐 (Requirement Alignment)

- [ ] **没有规格外的额外功能（Gold-plating）** — 判定标准：diff 中不存在规格未要求的功能实现
- [ ] **没有遗漏规格中的隐式需求** — 判定标准：日志/监控/埋点/权限等隐式需求已实现
- [ ] **API 契约与接口规格完全一致** — 判定标准：函数签名/参数/返回值/错误码与规格定义一致
- [ ] **错误码/错误消息与规格定义一致** — 判定标准：错误码与消息文本与规格定义逐一比对

### 1.4 上下文一致性 (Context Consistency)

- [ ] **变更范围与规格描述一致** — 判定标准：diff 涉及的文件与规格描述的范围一致
- [ ] **没有遗漏关联文件修改** — 判定标准：规格中提到的关联文件均已修改
- [ ] **配置变更与规格中的环境需求一致** — 判定标准：配置项变更与规格环境需求一致
- [ ] **数据库 Schema 变更与规格中的数据模型一致** — 判定标准：DDL/迁移脚本与规格数据模型一致

### Phase 1 输出标记

| 标记 | 含义 | 是否阻塞 |
|---|---|---|
| `[PHASE1-OK]` | 该审查项通过 | 否 |
| `[PHASE1-ISSUE] BLOCKER` | 阻塞级问题——必须修复才能进入 Phase 2 | 是（阻塞 Phase 2） |
| `[PHASE1-ISSUE] MAJOR` | 严重问题——应修复，可附条件进入 Phase 2 | 否（记录但传递给 Phase 2） |
| `[PHASE1-ISSUE] MINOR` | 次要问题——建议修复 | 否 |
| `[PHASE1-NOTE:QUALITY]` | 代码质量观察——不阻塞 Phase 1，传递给 Phase 2 | 否 |

### Phase 1 门禁判定

| 条件 | 判定 | 后续动作 |
|---|---|---|
| 存在任一 BLOCKER 级问题 | `[PHASE1-FAIL]` | 直接退回，不进入 Phase 2 |
| 无 BLOCKER，存在 MAJOR 级问题 | `[PHASE1-PASS-WITH-CONDITIONS]` | 进入 Phase 2，MAJOR 问题记录并传递 |
| 无 BLOCKER，无 MAJOR，存在 MINOR 级问题 | `[PHASE1-PASS]` | 进入 Phase 2，MINOR 问题记录 |
| 全部通过 | `[PHASE1-PASS]` | 进入 Phase 2 |

## Phase 2: 代码质量审查（Code Quality）

> **目标**：验证「做得对吗」——代码实现是否符合质量标准、最佳实践和团队规范。默认 Phase 1 已通过（或有明确标记的例外项）。

### 2.1 代码结构 (Code Structure)

- [ ] **单一职责原则** — 判定标准：每个函数/类/模块只有一个变更理由
- [ ] **合理的抽象层级** — 判定标准：没有泄漏的抽象或过度的间接层
- [ ] **恰当的模块划分** — 判定标准：文件大小合理，职责清晰
- [ ] **无循环依赖** — 判定标准：没有引入新的循环依赖

### 2.2 可读性与可维护性 (Readability & Maintainability)

- [ ] **命名准确表达意图** — 判定标准：变量、函数、类、文件名能揭示其作用或所持内容
- [ ] **函数/方法长度合理** — 判定标准：建议≤50行；超出须有正当理由
- [ ] **嵌套深度可控** — 判定标准：建议≤3层；超出须有正当理由
- [ ] **魔法数字已用命名常量替代** — 判定标准：硬编码数字/字符串已提取为命名常量
- [ ] **复杂逻辑有恰当的内联说明** — 判定标准：非显而易见的逻辑有注释说明意图

### 2.3 健壮性 (Robustness)

- [ ] **错误处理完整且恰当** — 判定标准：不吞异常、不过度捕获、错误信息有意义
- [ ] **资源管理正确** — 判定标准：连接、文件句柄、锁的获取与释放成对出现
- [ ] **空安全检查到位** — 判定标准：可能为 null/undefined 的值有显式检查
- [ ] **外部输入验证充分** — 判定标准：所有外部输入在使用前经过验证
- [ ] **超时和重试策略合理** — 判定标准：外部调用有超时设置，可重试操作有重试策略

### 2.4 性能 (Performance)

- [ ] **无不必要的循环嵌套** — 判定标准：O(n²) 及以上复杂度须有正当理由
- [ ] **数据库查询使用合适的索引** — 判定标准：查询条件字段有对应索引
- [ ] **无 N+1 查询问题** — 判定标准：循环内无数据库查询，或已用批量查询替代
- [ ] **大对象/大数据量的内存使用合理** — 判定标准：无不必要的全量加载，流式处理或分页已考虑
- [ ] **关键路径无同步阻塞风险** — 判定标准：I/O 密集操作使用异步模式

### 2.5 安全性 (Security)

- [ ] **没有硬编码的密钥/凭证** — 判定标准：密钥/凭证从环境变量或密钥管理服务读取
- [ ] **SQL 注入防护** — 判定标准：使用参数化查询，无字符串拼接 SQL
- [ ] **XSS 防护** — 判定标准：用户输入输出时有适当的编码/转义
- [ ] **敏感数据日志脱敏** — 判定标准：日志中不出现密码/Token/身份证等敏感信息
- [ ] **权限检查在业务逻辑前执行** — 判定标准：鉴权在业务逻辑入口处完成

### 2.6 测试 (Testing)

- [ ] **核心逻辑有单元测试覆盖** — 判定标准：核心业务逻辑有对应的单元测试
- [ ] **边界条件有专门测试用例** — 判定标准：边界值/空值/异常输入有专门测试
- [ ] **Mock/Stub 使用恰当** — 判定标准：不过度 Mock，Mock 的是依赖而非被测对象
- [ ] **测试用例可读且独立** — 判定标准：测试用例间无依赖，可独立运行

### Phase 2 输出标记

| 标记 | 含义 | 是否阻塞 |
|---|---|---|
| `[PHASE2-OK]` | 该审查项通过 | 否 |
| `[PHASE2-ISSUE] STRUCTURE` | 代码结构问题 | 视严重程度 |
| `[PHASE2-ISSUE] READABILITY` | 可读性问题 | 视严重程度 |
| `[PHASE2-ISSUE] ROBUSTNESS` | 健壮性问题 | 视严重程度 |
| `[PHASE2-ISSUE] PERFORMANCE` | 性能问题 | 视严重程度 |
| `[PHASE2-ISSUE] SECURITY` | 安全问题 | 视严重程度 |
| `[PHASE2-ISSUE] TESTING` | 测试覆盖问题 | 视严重程度 |
| `[PHASE2-BLOCKER:FUNCTIONAL]` | Phase 2 中发现的功能性缺陷 | 是（回退 Phase 1 重新评估） |

### 严重程度分级

| 级别 | 定义 | 处理方式 |
|---|---|---|
| BLOCKER | 阻塞合并——存在安全漏洞/数据丢失风险/核心功能不可用 | 必须修复 |
| MAJOR | 严重问题——影响可维护性/性能/安全，但不阻塞核心功能 | 应修复 |
| MINOR | 次要问题——代码风格/命名/注释等改进建议 | 建议修复 |

> 分级的**判定顺序**与**校准口径**见 §3（严重度校准 rubric）。定级 MUST 先证成可达性并跑完反证据（§4），再定级——**定级是结论，不是开场立场**。

## §3 严重度校准 rubric（Severity Calibration）

> 来源：提炼自 某开源项目 `analysis/severity_calibration.md`（Apache-2.0），去产品化改写为代码审查定级口径。
> 解决的问题：同一份 diff，不同审查者给出的 BLOCKER/MAJOR/MINOR 常有系统性偏差——「想象中的最坏情况」被定成 BLOCKER，而真实可达的缺陷被低估。

### 3.1 定级前的两个前置

1. **先证成可达性**：证明该问题在真实执行路径上会触发（给出 `file:line` 的触发路径），而非「理论上可能」。
2. **先跑完反证据**：见 §4。未做反证据的定级一律视为**未定级**，不得写入报告结论列。

### 3.2 校准总问句

> 如果这家团队的声誉押在这份审查报告上，这个问题会被严肃的第三方审计/代码评审接受为 BLOCKER/MAJOR 吗？

若诚实答案是「只有接受一长串假设才行」，则它不是 BLOCKER——**定你证明了的那个缺陷，而不是你想象中能推演到的最坏情况**。

### 3.3 各级判据

| 级别 | 判据（须有证据，非推测） | 升级/降级因子 |
|---|---|---|
| **BLOCKER** | ① 数据丢失/损坏风险且无防护；② 安全漏洞且路径可达（注入/越权/硬编码凭证泄漏在生产路径）；③ 核心功能不可用；④ 破坏既有契约且影响面跨模块 | 升级：无防护、公网/生产路径可达、影响面跨模块或跨租户、可自传播（一处错误引发连锁） |
| **MAJOR** | ① 影响可维护性/性能/安全但不阻塞核心功能；② 错误处理缺失导致问题被吞；③ 明确违反仓库成文规范且影响面较大；④ 测试覆盖缺口使回归无法发现 | 升级：修复成本随放大（越晚修代价越高）；降级：有既有缓解措施（重试/告警/兜底）且已验证有效 |
| **MINOR** | 命名/风格/注释/局部冗余；仓库规范未强制的偏好类建议 | 降级：纯个人偏好且仓库无共识 → 记为 `[PHASE*-NOTE]` 而非 ISSUE |

### 3.4 校准自检（定级后逐条过）

- [ ] 该级别对应的判据条目能具体指出是哪一条，而非「感觉严重」
- [ ] 结论中不含「如果……那么……」的假设链；若有，降级到假设链最短的那个结论
- [ ] 已记录一条**反向证据**（为什么它可能没那么严重），并在定级说明中回应
- [ ] 定级与同批次同类问题一致（同类问题不同级别须有显式差异说明）

## §4 反证据关闭门（Counterevidence Closure Gate）

> 来源：提炼自 某开源项目 `analysis/counterevidence.md`（Apache-2.0），去产品化改写为审查结论关闭纪律。
> 解决的问题：审查中最容易失真的不是「报错了什么」，而是「凭什么说这里没问题」——假阳性与假阴性都出在这一半。

### 4.1 三态关闭（每个被打开的审查候选 MUST 落入且仅落入其一）

| 状态 | 定义 | 落盘要求 |
|---|---|---|
| `confirmed` | 有可复现证据（失败用例/执行轨迹/日志），或白盒下完整的「入口 → 控制点 → 汇点 → 影响」链路 | 写入报告问题清单，附证据 `file:line` |
| `ruled_out` | **能点名具体防护机制**（在哪、做什么、为何在受影响路径上生效） | 写入覆盖度账本（§5）`ruled_out` 列，附防护位置 |
| `open_proof_gap` | 既不能证实，也不能点名防护排除——**这是合法且预期的结局** | 写入覆盖度账本 `gaps` 列，说明卡在哪一步 |

**关闭句强制**：判定 `ruled_out` 前 MUST 能完整补全这句话，否则不得关闭——
> 「这里是安全的，因为 `<防护机制>` 位于 `<file:line 或观测行为>`，它在 `<汇点/受影响操作>` 之前 `<做了什么>`，且在所有可达路径上都生效。」

### 4.2 不算反证据的四类（显式排除）

1. **没时间/没跑**——未执行不等于安全
2. **工具没报**——工具静默 ≠ 无问题（工具覆盖不到的路径要显式记 gap）
3. **以前一直这样**——历史存续不等于正确
4. **看起来没问题**——没有 `file:line` 的直觉不构成证据

### 4.3 关闭门触发点

- Phase 0/1/2 每个维度收尾时执行：本维度的「未发现问题」结论 MUST 逐项给出关闭状态
- 门②（结论确认）前执行总检：报告中所有「无问题」结论无关闭状态 → 标记 `[INVALID:UNCLOSED]` 退回补充

## §5 覆盖度账本（Coverage Ledger）

> 来源：提炼自 某开源项目 `report/coverage.py` 的「扫描的负空间」设计（Apache-2.0），去产品化改写为审查账本。
> 解决的问题：一份「零问题」的审查报告无法回答「你到底查了什么」——而这在复核语境下才是决定报告是否可信的问题。

### 5.1 双源分离（禁止合并记账）

| 源 | 含义 | 谁产生 |
|---|---|---|
| `self_reported` | 审查者自述的检查项与结论（rich but 主观） | 审查过程中逐维记录 |
| `machine_observed` | 运行时客观记录的事实：实际执行的命令与退出码、实际读取的文件清单、实际跑过的测试与结果、是否跑完（vs 被上下文/预算截断） | 执行过程留痕，非事后回忆 |

**铁律**：两者 MUST 分列且各带 `source` 标记。**把「幻觉的已检查且无问题」混进客观记录，比没有覆盖度记录更不诚实。** 矛盾项（自报已查但实测无记录）MUST 进 `gaps`，不得静默调和。

### 5.2 账本最小结构（写进报告 §覆盖度账本 章节）

```
| 检查项 | 源（self_reported / machine_observed） | 结论（confirmed / ruled_out / open_proof_gap） | 证据（file:line / 命令+退出码） |
```

末尾三行固定：

- **gaps**：未能确认也未能排除的项 + 卡点（上下文截断/工具不可用/信息缺失）
- **未覆盖声明**：明确列出本次**没查**的维度与原因（范围外/资源限制）
- **完成度**：`complete: true|false`——被预算或上下文截断时 MUST 为 `false`，无论账本多整齐

### 5.3 与现有流程的衔接

- Phase 0（三维 18 项）、Phase 1（16 项）、Phase 2（28 项 + 12 坏味）逐项落账，禁止合并行
- 门②前执行账本总检：`gaps` 非空须逐条说明是待办还是已解决（已解决的更新原条目，不新增重复行）

### 5.4 跳过判据（skipped 理由的封闭清单）

> 解决的问题：`skipped` 若无成文判据，跳过判据因人而异、不可复现，覆盖率收尾就失去对照基准。**仅以下六类可作为 skipped 理由，判据外跳过 = 覆盖缩水**（执行纪律 §七 第 2 条引用本节）：

| # | 判据 | 说明 | 附加义务 |
|---|---|---|---|
| 1 | 生成物 / vendored | 构建产物、第三方 vendor 目录、锁文件（package-lock 等）——变更本身无人工审查价值 | 标注「由何种工具/流程替代校验」（如 lockfile 由依赖审计工具管） |
| 2 | 纯重命名 / 纯移动 | 内容 diff 为空或仅路径变化 | 账本标注新路径，供捆绑单元（纪律 §四）关联审查 |
| 3 | 二进制 / 资源文件 | 无文本 diff 可审 | 记录文件类型 |
| 4 | 超大型生成 diff | minified、bundle、语料/数据集等人工审查无意义的生成 diff | 标注替代校验手段（构建通过 / 快照对比 / 专用工具） |
| 5 | 与变更语义无关 | diff 存在但不在本次变更目的链路上 | 给出一句链路判断依据（为什么判定无关） |
| 6 | 预算截断 | 非自愿跳过（上下文/时间/预算不足） | **此时账本 `complete` MUST 为 `false`** |

- 判据 1–5 为「有价值判断后的主动跳过」，判据 6 为截断态——两者都 MUST 逐文件落账、禁止合并行。
- 「没时间」「看起来不重要」「实现文件已审，接口文件不必再审」**均不在清单内**（最后这条正是纪律 §四第 1 条禁止的跳过理由）。

## 标记格式规范

> 所有审查结论使用统一标记格式，确保可追溯。

