# Phase 0: 架构师增量审计方法论

> 本文件是 Phase 0「架构师增量审计」的**单一事实源**。SKILL.md 仅留概览表 + 指针，详细方法论查本文件。
> grep 检索模式：`Phase 0` / 维度名（如 `代码设计改动` / `架构设计实现` / `功能设计实现`）/ `文档驱动` / `修复建议` / `[AUDIT-`。

---

## 核心理念

> **架构师视角的「设计意图 → 实现偏差」审计。**

传统代码审查（Phase 1/2）聚焦「代码是否符合规格」与「代码质量是否达标」，但缺少一个前置视角：**站在系统架构设计师的高度，先学习项目的设计意图（文档），再审视增量改动是否偏离设计、是否引入架构退化、是否破坏功能完整性**。Phase 0 补齐这一前置视角。

Phase 0 与 Phase 1/2 的关系：
- **Phase 0 是可选前置阶段**：触发增量审计模式时执行；标准代码审查模式跳过。
- **Phase 0 审计结论可馈入 Phase 1**：Phase 0 识别的「设计意图偏差」可作为 Phase 1 规格合规审查的补充规格来源。
- **Phase 0 不阻塞 Phase 1/2**：Phase 0 产出独立的审计报告（`audit-report.md`），与 `review-report.md` 并存或合并。

## 一、文档驱动学习链（4 级降级）

> Phase 0 的核心差异化能力：**先学设计意图，再审实现偏差**。按 4 级优先级降级获取项目设计文档，确保审计基于设计意图而非仅看代码。

| 级别 | 来源 | 采集方式 | 适用场景 |
|---|---|---|---|
| **L1 · 用户提供文档** | 用户在请求中显式提供的文档路径/内容 | 直接读取用户指定路径 | 用户有明确的设计文档/PRD/架构说明 |
| **L2 · 项目分析/介绍文档** | 项目内 `docs/`、`.docs/`、`specs/`、`.scratch/` 下的 `*.md` 分析/介绍文档 | Glob 匹配 + 关键词筛选（架构/设计/分析/介绍/design/architecture/overview） | 项目有自维护的设计文档 |
| **L3 · README.md** | 项目根目录 `README.md`（含子模块 README） | 读取根 README + 一级子目录 README | 项目仅有 README 级说明 |
| **L4 · 全量代码兜底** | 扫描实际代码设计与实现（目录结构/入口文件/配置文件/核心模块） | 目录树扫描 + 入口文件识别 + 配置文件解析（package.json/pom.xml/go.mod 等） | 无任何文档，从代码反推设计 |

### 降级规则

1. **逐级尝试**：从 L1 开始，本级无可用文档则降级到下一级，L4 为兜底（必有）。
2. **混合取用**：可同时使用多个级别（如 L2 项目文档 + L3 README 互补）。
3. **学习产出**：每级文档学习后，MUST 产出「设计意图摘要」（≤200 字），记录理解到的：架构模式 / 核心模块 / 设计约束 / 关键决策。
4. **门①呈现**：学习完成后，MUST 在门①向用户呈现「文档来源级别 + 设计意图摘要」，供用户确认理解是否准确。

## 二、三维审计框架

> 以系统架构设计师视角，从三个维度审计增量改动。每维产出：审计结论 + 修复建议 + 优先级。

| 维度 | 核心问题 | 数据来源 | 产出 | 检查项数 |
|---|---|---|---|---|
| 1. 代码设计改动 | 改了什么代码？改动设计是否合理？是否引入设计退化？ | Git diff + 设计意图摘要 | 改动设计评估 + 退化风险 + 修复建议 | 6 |
| 2. 架构设计实现 | 整体架构是否合理？模块边界/依赖方向/扩展性？ | 目录结构 + 入口文件 + 依赖配置 + diff 影响面 | 架构合理性评估 + 架构风险 + 修复建议 | 6 |
| 3. 功能设计实现 | 功能是否完整？功能模块关系是否清晰？用户旅程是否通畅？ | 设计意图摘要 + diff 功能变更 + 测试覆盖 | 功能完整性评估 + 功能风险 + 修复建议 | 6 |

### 维度 1: 代码设计改动（Code Design Changes）

- [ ] **改动符合设计意图** — 改动是否与学习到的设计意图一致？有无偏离设计方向的改动？
- [ ] **改动未引入设计退化** — 改动是否破坏既有设计模式/抽象层级/模块边界？
- [ ] **改动规模与复杂度合理** — 改动行数/文件数是否在合理范围？有无过度改动（Gold-plating）或改动不足？
- [ ] **改动遵循既有编码范式** — 改动是否遵循项目既有的编码风格/设计范式（如 MVC/DDD/分层）？
- [ ] **改动的影响面可控** — 改动波及的模块/接口是否在预期内？有无意外耦合扩散？
- [ ] **改动的可逆性** — 改动是否可回滚？是否有破坏性不可逆变更（如数据迁移/Schema 变更）？

### 维度 2: 架构设计实现（Architecture Design）

- [ ] **架构模式合理性** — 整体架构模式（单体/微服务/Serverless/事件驱动等）是否适合当前项目阶段与规模？
- [ ] **模块边界清晰性** — 模块划分是否遵循高内聚低耦合？边界是否清晰？有无职责重叠？
- [ ] **依赖方向正确性** — 依赖方向是否合理（如分层架构中上层依赖下层，不反向）？有无循环依赖？
- [ ] **扩展性设计** — 架构是否预留了合理的扩展点？改动是否利用了既有扩展点而非硬编码？
- [ ] **技术栈选型合理性** — 技术栈选型是否匹配项目需求？版本是否合理？有无过时/有安全风险的依赖？
- [ ] **架构一致性** — 新改动与既有架构风格是否一致？有无引入异构风格（如在分层架构中突插入事件驱动）？

### 维度 3: 功能设计实现（Function Design）

- [ ] **功能完整性** — 设计意图中的功能是否均已实现？有无遗漏的关键功能点？
- [ ] **功能模块关系清晰** — 功能模块间的调用关系/数据流是否清晰？有无隐式依赖？
- [ ] **用户旅程通畅性** — 从用户视角，核心功能流程是否完整可用？有无断点/死路？
- [ ] **异常路径覆盖** — 功能的异常路径（错误/超时/降级）是否有设计？还是仅实现了 Happy Path？
- [ ] **功能可测试性** — 功能是否可被测试？测试覆盖是否充分？有无难以测试的硬编码逻辑？
- [ ] **功能与文档一致性** — 实现的功能与设计文档描述是否一致？有无文档未记录的隐性功能？

## 三、修复建议模板

> 每个审计发现 MUST 附带修复建议，修复建议遵循「方向 + 方案 + 优先级」三段式。

```
[AUDIT-ISSUE] <BLOCKER|MAJOR|MINOR> <维度> <检查项>
  — 证据：<file:line / 设计意图条目>
  — 描述：<问题详情——偏离了什么设计意图/引入了什么风险>
  — 修复方向：<一句话指明修复方向，如"将硬编码依赖改为通过接口注入">
  — 修复方案：<2-3 句具体修复步骤建议>
  — 优先级：<BLOCKER 必须立即修复 / MAJOR 应在本轮修复 / MINOR 可后续迭代>
```

### 修复建议质量标准

- **修复方向 MUST 可执行**：不能是"优化一下""改进设计"等空话，MUST 给出具体技术方向。
- **修复方案 MUST 贴合上下文**：基于项目实际技术栈与架构，NEVER 给通用模板答案。
- **优先级 MUST 与影响匹配**：BLOCKER = 架构退化/数据丢失/核心功能不可用；MAJOR = 设计偏差/扩展性受损/可维护性下降；MINOR = 风格不一致/小改进建议。
- **NEVER 越界改代码**：修复建议是「建议」，修复动作由 tri-coding/tri-fix 执行。

## 四、Phase 0 输出标记

| 标记 | 含义 | 是否阻塞后续 |
|---|---|---|
| `[AUDIT-OK]` | 该检查项通过，无偏差 | 否 |
| `[AUDIT-ISSUE] BLOCKER` | 架构退化/核心设计偏离/数据风险——必须修复 | 阻塞合并（但不阻塞 Phase 1/2 执行） |
| `[AUDIT-ISSUE] MAJOR` | 设计偏差/扩展性受损——应修复 | 不阻塞，记录传递 |
| `[AUDIT-ISSUE] MINOR` | 小改进建议——可后续迭代 | 不阻塞 |
| `[AUDIT-NOTE]` | 架构观察——非问题，记录供参考 | 否 |

### Phase 0 与 Phase 1/2 标记隔离

> Phase 0 标记使用 `[AUDIT-*]` 前缀，与 Phase 1 `[PHASE1-*]` / Phase 2 `[PHASE2-*]` 标记**严格隔离**，不交叉使用。这确保三阶段审计结论可独立追溯，不互相污染。

## 五、Phase 0 门禁判定

| 条件 | 判定 | 后续动作 |
|---|---|---|
| 存在任一 BLOCKER 级问题 | `[AUDIT-FAIL]` | 审计报告标记，建议修复后重新审计；不阻塞 Phase 1/2 但建议先修 |
| 无 BLOCKER，存在 MAJOR 级问题 | `[AUDIT-PASS-WITH-CONDITIONS]` | 进入 Phase 1/2（若用户选择），MAJOR 记录传递 |
| 无 BLOCKER，无 MAJOR，存在 MINOR | `[AUDIT-PASS]` | 进入 Phase 1/2（若用户选择），MINOR 记录 |
| 全部通过 | `[AUDIT-PASS]` | 进入 Phase 1/2（若用户选择） |

> **Phase 0 与 Phase 1/2 的门禁独立**：Phase 0 FAIL 不强制阻塞 Phase 1/2（因为 Phase 0 是架构师视角的前置审计，Phase 1/2 是规格+质量审查，关注点不同）。但门②最终结论 MUST 汇总 Phase 0 结论，若 Phase 0 存在 BLOCKER，最终结论不得为 `APPROVED`。

## 六、Phase 0 可扩展性

| 扩展点 | 零改动扩展方式 |
|---|---|
| 新增审计维度 | 在本文件追加一维（如「安全架构审计」），audit-report.md 模板自动支持 |
| 新增检查项 | 在对应维度追加检查项 |
| 新增文档来源级别 | 在文档驱动学习链追加一级（如 L2.5 · API 文档） |
| 技术栈特定审计项 | 在对应维度追加技术栈子节（如 React/Vue/NestJS 特定架构项） |
| 修复建议模板定制 | 在修复建议模板段追加技术栈专属修复模式 |
