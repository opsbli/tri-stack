# tri-review

代码审查下游执行 skill，支持三模式：① 工作流集成模式——由 tri-coding/tri-fix 在门③执行前确认时调用；② 独立调用模式——读取 tri-intent 快照 §三；③ 增量审计模式——以系统架构设计师视角，文档驱动学习设计意图，对增量改动进行三维审计（代码设计改动/架构设计实现/功能设计实现），产出审计结果+修复建议+优先级。自主管理「Phase 0 架构师增量审计（可选）→ Phase 1 规格合规 → Phase 2 代码质量 → 审查/审计报告」完整链路，融合两阶段分离关注点方法论、文档驱动学习链、三维架构师审计与 Fowler 代码坏味基线（12 种），含双审批门 + 门禁机制 + 反规避检测。

## 特性

- **三模式适配**：工作流集成模式（上游链路文档为规格来源）+ 独立调用模式（快照驱动）+ 增量审计模式（文档驱动+架构师视角），灵活适配不同场景
- **Phase 0 架构师增量审计**：文档驱动学习链（4 级降级：用户文档→项目文档→README→全量代码兜底）+ 三维审计（代码设计改动/架构设计实现/功能设计实现）+ 修复建议（方向+方案+优先级）
- **两阶段分离关注点**：Phase 1 规格合规（做了对的事吗）→ Phase 2 代码质量（做得对吗），Phase 1 未通过不得进入 Phase 2
- **双审批门**：门①审查/审计范围确认 → 门②审查/审计结论确认，两道关卡严格串行
- **Fowler 代码坏味基线**：内置 12 种代码坏味（神秘命名/重复代码/依恋情结等），按「是什么 → 如何修」对照 diff 匹配
- **反规避机制**：4 种检测规则（阶段分离 / 清单完整性 / 交叉标记 / 门禁执行），防止审查阶段被合并或跳过；Phase 0/1/2 标记严格隔离
- **三态依赖检测**：独立安装时支持快照模式 / 引导安装 / 降级模式（增量审计模式不依赖快照，可在降级模式下执行）

## 安装

将 `tri-review/` 目录放入你的 skills 目录即可：

```bash
cp -r tri-review/ /path/to/your/skills/
```

> 本 skill 依赖 tri-intent 进行意图识别与输入校验。若未安装 tri-intent，激活时提示安装。增量审计模式（用户直接要求审计项目改动）不依赖快照，可在降级模式下正常执行。

## 使用

### 1. 代码审查工作流（工作流集成 / 独立调用模式）

激活后先判定模式，再按以下链路推进：

```
模式判定 → 读取输入 → 锁定固定点+识别规格/标准来源 → 门①审查范围确认 → Phase 1 规格合规 → Phase 2 代码质量 → 门②审查结论确认 → review-report.md
```

> **核心铁律**：先确认方向正确（Phase 1 规格合规），再确认步伐稳健（Phase 2 代码质量）。

### 2. 增量审计工作流（增量审计模式）

用户直接要求「增量审计」「架构师视角审计改动」时激活：

```
提取项目路径/增量模式/用户文档 → 文档驱动学习（4级降级链）+ 增量改动识别 → 门①审计范围确认 → Phase 0 三维审计 → 门②审计结论确认 → audit-report.md
```

> **Phase 0 差异化**：文档驱动学习设计意图（先学设计再审实现偏差），三维审计（代码设计改动/架构设计实现/功能设计实现），产出修复建议（方向+方案+优先级）。
> 用户可在 Phase 0 后选择是否继续 Phase 1/2 标准代码审查。

### 3. 两阶段门禁机制

- **Phase 0 门禁**：存在 BLOCKER → `[AUDIT-FAIL]`，建议先修（不强制阻塞 Phase 1/2，但门②最终结论不得为 APPROVED）
- **Phase 1 门禁**：存在 BLOCKER → `[PHASE1-FAIL]`，直接退回，不进入 Phase 2
- **Phase 2 回退**：发现功能性缺陷 → `[PHASE2-BLOCKER:FUNCTIONAL]`，回退 Phase 1 重新评估
- **反规避检测**：阶段分离 / 清单完整性 / 交叉标记（Phase 0/1/2 互不交叉）/ 门禁执行

### 4. 特殊路由

tri-intent 的 `doing/code-review.md` 定义了代码审查特殊路由项（不占 I 编号位），允许用户直接触发代码审查而不经过标准 I 编号意图路由。增量审计模式由用户直接要求触发，经降级模式或快照模式激活。

### 5. 交付产物

- 审查报告落盘于 `.tribro/reviews/<命名>/review-report.md`（工作流集成/独立调用模式）
- 审计报告落盘于 `.tribro/reviews/<命名>/audit-report.md`（增量审计模式）
- 审查/审计报告是代码合并的必要条件，非充分条件

## 设计原则

- **先意图后方向再步伐**：Phase 0 学设计意图（架构师视角），Phase 1 确认做对了事（规格合规），Phase 2 确认做得对（代码质量）
- **只审查/审计不改代码**：发现问题记录于报告并附修复建议（方向+方案+优先级），修复动作由 tri-coding/tri-fix 执行
- **文档驱动审计**：Phase 0 先学设计文档再审实现偏差，4 级降级确保无文档时也能从代码反推设计
- **反规避闭环**：4 种检测规则防止审查阶段被合并或跳过，Phase 0/1/2 标记严格隔离
- **三模式适配**：工作流集成/独立调用/增量审计三模式灵活适配不同审查/审计场景
