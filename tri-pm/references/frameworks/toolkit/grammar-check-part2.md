# 语法与行文检查（grammar-check · 技能态 · 续篇）

> 续 `grammar-check.md`｜源词数：1459｜本篇承接示例散文与清单（3 类 17 子类已在主篇逐类保留）

## Error Categories 示例（来自源文件）

**Grammar**
- Spelling：误 "buisness" → 正 "business"。
- Punctuation：缺撇号 "Lets get started" → "Let's"；多独立分句 run-on 长句拆为分句或加连词/分号。
- Subject-Verb：误 "The team are working" → 正 "The team is working"。
- Tense：混用过去现在（"We launched… and are seeing… Users report…"）→ 按时间框架统一时态。
- Pronoun："The manager told the designer that she should revise the mockups." → 改 "The manager told the designer to revise the mockups."
- Modifier："After reviewing the proposal, the decision seemed obvious." → 改 "After reviewing the proposal, we saw the decision was obvious."

**Logic**
- Unsupported："Our product is the best… because customers love it." → 补证据（评分、份额）。
- Contradictions：既说"重隐私"又说"与 50+ 第三方共享" → 澄清或协调。
- Incomplete："feature launched in Q3, so adoption increased." → 补因果（" adoption 次月增 25%，因 onboarding 改善"）。
- Vague："saves time and money." → 具体化（"onboarding 2h→15min，运营成本降 30%"）。

**Flow**
- Weak Transitions：段间跳接 → 加 "In addition / However / As a result"。
- Choppy："We launched. We got feedback. We iterated." → 合并为 "After launching, we received feedback and iterated quickly…"
- Passive：误 "The decision was made by the team…" → 正 "The team decided…"
- Unclear Pronoun："…their API. It was complicated…" → 改 "…API, which proved too complicated…"
- Redundancy："simple and easy to use; straightforward and uncomplicated." → 删冗余。
- Tone：正式与随意混用 → 统一语气。

## 审阅清单（Checklist for Review）

- [ ] 拼写（拼写检查+人工）
- [ ] 标点（缺逗号/撇号/句号）
- [ ] 主谓一致
- [ ] 时态一致
- [ ] 含糊代词
- [ ] 可合并/拆分以改善行文
- [ ] 被动语态是否过度
- [ ] 无支撑主张（"有证据吗？"）
- [ ] 矛盾
- [ ] 段落过渡是否顺
- [ ] 语气与目的一致
- [ ] 冗余词
- [ ] 过长句能否简化
- [ ] 主张是否支撑目标

## 有效反馈示例（Examples of Effective Feedback）

- 差："This sentence is unclear." 好："'the vendor's API, but it was too complex' 中 'it' 含糊，改为 'the vendor's API was too complex'。"
- 差："Fix the grammar here." 好："主谓不一致：'data' 在美式英语作复数，用 'The data show' 而非 'shows'。"
- 差："This doesn't flow well." 好："段间过渡破碎，加 'Beyond cost savings, our solution also improves employee satisfaction.' 连接成本讨论与下一点。"

## 何时建议不改（When to Suggest No Change）

不改正：有意风格（短促有力句）、正确非正式语（口语化语境的缩略）、修辞手段（头韵/排比重读）、个人声音与风格（除非损害清晰或目标）。聚焦清晰与正确，而非完美或风格统一。

## 重要准则补充（Important Guidelines 详）

- 具体："Vague pronoun reference; 'it' 可能指 API 或供应商提案。改为：'The vendor's API proved too complex.'"
- 考虑受众：修复须匹配目标受众与语境。
- 非母语者尤须讲清"为何"建议改。
- 不过度纠正风格偏好——"错"与"不同"有别。
- 专业文档另查语气一致与受众恰当。
