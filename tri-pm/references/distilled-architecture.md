## 一、四层结构

源项目为 **Claude Code 插件市场**，自上而下分四层，边界清晰、职责单一、无循环依赖（报告 §3.2）：

| 层 | 名称 | 载体 | 职责 |
|:--:|------|------|------|
| L0 | 市场层 | `.claude-plugin/marketplace.json` | 声明 9 个插件清单与全局描述；唯一市场入口 |
| L1 | 插件层 | `pm-{name}/.claude-plugin/plugin.json` | 每插件独立可安装；声明 name/version/author/keywords/homepage/license |
| L2 | 技能层 | `pm-{name}/skills/{skill}/SKILL.md` | 单职责领域知识（框架、画布、分析方法） |
| L3 | 工作流层 | `pm-{name}/commands/{command}.md` | 用户触发，链式编排一个或多个 L2 技能 |

> 关键性质：**L3 调用 L2，L2 之间互不调用**。L3 是唯一的编排层。

## 三、依赖关系

| 依赖类型 | 现状 | 工程评估 |
|----------|------|---------|
| 运行时依赖 | 无（内容 100% Markdown；校验/测试仅用 Python 标准库） | 极优，可移植性最强 |
| 插件内（intra-plugin） | skill↔command 同插件硬引用允许 | 可控，随包分发 |
| 跨插件（cross-plugin） | **刻意禁止硬引用** | 解耦彻底，但跨域工作流无法硬链式复用 |
| 外部知识 | `### Further Reading` 链接外部文章 | 存在知识衰减/可达性风险 |

**依赖方向恒为单向**：`L0 → L1 → {L2, L3}`，`L3 → L2`。无反向、无横向 L1↔L1 引用。

## 四、主要执行流程（数据流）

```
用户输入 / 话题
   └─> 命令（command，L3）触发
         └─> 链式调用 1..N 个技能（skill，L2）
                └─> 产出结构化产物（PRD / 画布 / 路线图 / 审计包等，多为 .md）
                       └─> 命令尾部以「自然语言」建议下一步（工作流流动）
```

**流程要点**：

1. 技能可被**话题匹配自动加载**，无需显式调用。
2. 命令是**编排者**，本身不含框架细节，只负责串联与检查点（checkpoint）。
3. 每步之间设**检查点**，用户可重定向、跳过或深入。
4. 工作流之间靠**自然语言建议**衔接（而非硬引用），这是解耦设计的直接体现。

## 五、设计决策（可复用原则）

| 决策 | 内容 | 为何重要 |
|------|------|---------|
| **Skills = 名词/概念** | 框架与分析知识，话题匹配时自动加载 | 知识可被多处复用，不绑定单一流程 |
| **Commands = 动词/工作流** | 用户触发，链式调用技能 | 流程与知识分离，各自演进 |
| **无跨插件硬引用** | 命令只能自然语言建议下一步 | 插件独立安装，硬引用会导致断链 |
| **渐进式披露** | frontmatter 精简（常驻加载），细节放正文（触发时加载） | 控制上下文开销 |
| **单一事实源** | `CLAUDE.md` 为 agent 指导真源；`CHANGELOG.md` 为发布真源 | 文档不漂移 |
| **版本强一致** | marketplace ↔ 9 个 plugin.json ↔ CHANGELOG 同版本 | 由测试强制，无独立版本 |
| **校验即门禁** | `validate_plugins.py` + `tests/` 在每次 PR/push 运行 | 结构一致性由机器保证 |

> 上述决策的可迁移性评估见 `interfaces-and-contracts.md` §四。
