# 家族合规核对清单（24 条）

> **本文件是门④「合规自检」的判据单一事实源。** 编号即判定序号，逐条执行，不得跳条。
> 构成：**12 条家族硬约束（1–12）+ 8 条增强约束（13–20）+ 1 条安装约束（21）+ 1 条版本检查去重（22）+ 2 条证据驱动约束（23–24）**。
> 判定由 `scripts/compliance_check.py` 承担可机器判定部分；标注 `[需人工]` 的条目 MUST 由 Agent 逐条给出证据位置，NEVER 臆断。
>
> **判定口径**：`PASS` / `FAIL` / `N-A`（**MUST 附不适用理由，无理由的 N-A 视为 FAIL**）。
> **必检项** FAIL → 门④ 判 FAIL → 回炉门②；**建议项**（下表标注）FAIL 不阻断，计入「建议改进项」——
> 与家族既有的「必检项 + 建议项」惯例一致。
> 任一门④ FAIL 连续 3 轮 → 停止自动回炉，报告卡点请求人工介入。

## 五、证据驱动约束（23–24）

> 两条均为**本仓库三轮 pilot 的实测产物**（pilot1 / pilot2b），判据口径经「26 个家族对象 + 23 个第三方对象」
> 上线前只读实测校准（见 §〇 校准记录）。**两条均为必检**——第 24 条于 2026-09-27（v1.2.0）由建议项升为必检。

| # | 约束 | 判定方法 | 适用 |
|---|---|---|---|
| 23 | **规范性判据单一事实源** | 包内自引用指针（`references/` / `scripts/` / `templates/` / `assets/` 路径）MUST 可解析——**先相对 skill 目录，再相对仓库根兜底**（跨 skill 引用如 `tri-forge/references/family-spec.md` 属合法形态）；不可解析即 FAIL | 全部 |
| 24 | **评估产物含案级结构化结论** | **适用性（L1）**：包内须存在**结构化产物定义**——① SQL `CREATE TABLE` 块；② markdown 字段表（**真表头**：表头行含 `字段`/`field`/`检查项`/`条目`/`键名`，且**后随分隔行** `\|---\|`）；③ 内联字段枚举（同一行既有产物名又有 `{a, b, c, …}` ≥3 项）。**且**该文件（剥离 frontmatter 后）须提到评估/台账类产物；**排除** `CHANGELOG.md`、`tests/**`、`## 输入契约` 类输入侧表格、以及**上级标题不含产物语境**（`账本|台账|ledger|schema|产物|交付|落账|回执`）的普通叙述表（DDL 例外，不依赖标题）。**判定（L2）**：案级键与结论字段 MUST 落在**同一 schema 区块**内——案级键 `case_id`/`用例 ID`/`test_id`/`testId`/`spec_id`/`unit_id`/`lesson_id`/`proposal_id`/`issue_id`/`item_id`/`案级`/`检查项`/`条目`；结论字段 `verdict`/`status`/`decision`/`result`/`ab_result`/`结论`/`裁决`/`判定`/`盖章`/`confirmed`/`ruled_out`。缺一即 FAIL。**N-A 三态**：① 无上述结构化定义 → `N-A`；② 账本**仅按聚合维度**（轮/批次/时间）落账且包内声明了**守卫/单调性**用途 → `N-A`（附理由：守卫型账本按轮聚合是刻意设计，案级维度在报告侧） | 定义了评估产物 schema 者 |

> 第 24 条的因果链（pilot2b 实测）：评估产物**保住「案级」这个结构单位**时诊断 recall 40% → 100%；
> 压到整轮散文则只剩 40%，且成本只差 1/17（案级台账 ~3.8 KB vs 原始 trace 65 KB）。

## 六、判定记录格式

```
## 门④ 合规自检 · 第 <轮次> 轮

| # | 约束 | 判定 | 证据位置 / FAIL 原因 |
|---|---|---|---|
| 1 | 目录结构完整 | PASS | SKILL.md / README.md / CHANGELOG.md / tests/ 均在 |

...

**汇总**：必检项 24/24 PASS（N-A x 项，均附理由）→ **门④ PASS**
```

- **每条 MUST 给出证据位置**（文件名 + 章节/行范围）或 FAIL 原因
- `N-A` MUST 附不适用理由
- 汇总 MUST 给出 `x/y PASS` 与门④ 总判定

## 七、变更验收（另见 · **不属**门④ 24 条范围）

> ⚠️ **本节不编号。** 上面的 24 条是对**单个 skill 包**的**静态**检查；
> 本节指向的是对**一次变更**的**动态**检查（门④.5），判据真源独立、编号独立。

**适用**：本次任务为**变更既有 skill**（改正文 / `references/` / `scripts/` 中的规范性判据），
或 B 模式补全审计**且发生写入**。从零生成新 skill、A 模式、纯字形调整 → `N-A`（MUST 附理由）。

**判据单一事实源**：`references/change-acceptance-gate.md`
—— 本文件**不重述**其判据（这是「规范单一事实源」纪律的自我约束；第 23 条已于 2026-09-27 设立，
本条即其**首个自证实例**：指针可达、判据不重述）。

**可执行实现**：

```bash
python scripts/acceptance_diff.py --before <前版台账.json> --after <后版台账.json> [--ops <ops.json>] [--repo-root <skill-dir>]
```

退出码：`0` 全过 / `1` 存在 `FAIL` 或 `INCOMPLETE`（阻断）/ `2` 输入错误。

**与门④ 的判定关系**：门④ 通过是门④.5 的**前置**（包都不合规，谈行为变更是空谈）；
门④.5 `FAIL`/`INCOMPLETE` 回炉门②，门④ 需重跑。
