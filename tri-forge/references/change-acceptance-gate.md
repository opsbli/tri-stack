# 变更验收门（门④.5）· 判据单一事实源

> **本文件是门④.5「变更验收」的判据唯一真源。** 其它位置（`compliance-checklist.md` / `SKILL.md`）
> ONLY 允许**瘦指针引用**，NEVER 重述本文件的判据 —— 这是硬约束第 23 条（规范单一事实源）的自我约束。
>
> 定位：门④ 24 条是对**单个 skill 包**的**静态**检查；本门是对**一次变更**的**动态**检查。
> 二者互补，不重叠，顺序为 门④ → 门④.5 → 门⑤。

---

## 一、要解决的问题

**变更既有 skill 时，当前没有任何"行为级"验收判据。** 变更是否真的改变了行为、
改变在哪条规则上、有没有副作用，只能靠人工判断或"评分涨了"这类聚合信号。

实测依据（三轮 pilot，2026-09-26）：

| 实测项 | 数字 |
|---|---|
| 「聚合分 + 散文摘要」的诊断 recall | **2/5 = 40%**，46% 弃权 |
| 「案级结构化台账」的诊断 recall | **5/5 = 100%**，0 误报 |
| 台账的输入成本 | **≈3.8 KB/轮**（对比全量原始 trace 65 KB） |
| 归档规模 ×5 后实际读取量变化 | **不变**（26 文件 / 65,039 B） |

→ 行为级验收**技术可行且成本极低**；本门把判据固定下来。

## 三、输入契约（案级台账 schema）

门读入**变更前后两轮的案级台账**。台账 MUST 按 case 分条，**NEVER 只给整轮聚合值 + 散文摘要**。

```json
{
  "run_id": "2026-09-26T14:02:00Z",
  "skill": "tri-evolve",
  "version": "1.1.8",
  "cases": [
    {
      "case_id": "F6",
      "verdict_token": "revert",
      "verdict": "revert（绝对总分 78.8 不 > 旧分 87.3）",
      "clauses": ["§评分规则", "§Phase 2 · Step 5 决策"],
      "evidence": ["§评分规则「改进后总分必须严格高于改进前才保留」"],
      "changed_by": ["op-004"]
    }
  ]
}
```

| 字段 | 必需 | 用途 |
|---|---|---|
| `case_id` | ✅ | 两侧对齐的键 |
| `verdict` | ✅ | 自由文本结论（人读） |
| `clauses` | ✅ | **解释「因为哪条改了」**；NEVER 用作翻转判据（见下） |
| `verdict_token` | ✅ | **翻转判据主键**（单值结论 token）；缺失 ⇒ 该条转 `need_manual` 并阻断 |
| `evidence` | ⬜ | 原文引句，供 grep **软回验** |
| `changed_by` | ⬜ | 该 case 的结论变化由哪些 op 引起（供 B1/B2 校验） |

**三条硬性口径（均由实测确定，脚本已实现）**：

1. **翻转判据 MUST 是结论本身（`verdict_token`），NEVER 是 `clauses` 的字符串比对。**
   实测：同一节在两版常被引成不同粒度（如 `Phase 2 · Step 1 诊断` vs `§自主优化循环 Phase 2 · Step 1 诊断`），
   字符串比对会把**未变的 case 系统性误报为变更**。
2. **`clauses` 为空 ⇒ 该条作废**（防虚假填写）。
   而 `evidence` 回验未命中 ⇒ 仅标 `unverified` 待复核，**NEVER 因此作废整条**
   （引句书写粒度因人而异，硬作废会抹掉真实翻转 —— 已实测）。
3. **`verdict_token` MUST 编码「总判 + 全部失败条目号」，NEVER 只编码总判。**
   实测（2026-09-27）：新增**建议项**条目**不改变** PASS/FAIL 总判，只改变条目集；若 token 只编码总判，
   这类变更会被判为「未翻转任何 case」而 **B1 FAIL** —— 而这恰是 pilot2b 指出的关键单位：
   可机械比对的最小粒度是**案级条款集**，不是分数、也不是总判。`MANUAL` 项**不入** token（它是待人工项，不是结论）。

**`clauses` 空值的口径修正（2026-09-27）**：**允许空列表**（一个全 PASS 的干净 case 本来就没有非 PASS 条款），
MUST **存在该键**；防虚假填写改判「**token 声称 FAIL 而条款集为空**」（自相矛盾）才作废。
早期口径把空列表当「字段缺失」⇒ 干净 case 被判作废，实测使一条**真实翻转被漏记**且错报为「两侧不齐」。

## 四、三条硬门

| # | 硬门 | 判定方式 | 不过时 |
|---|---|---|---|
| **B1** | 每条声称"行为变更"的 op **MUST** 至少翻转 **1 条** case 的结论 | 机械（需 `ops` 清单 + `changed_by`） | `FAIL`：该 op MUST 改标 `cosmetic`，或回炉门② |
| **B2** | 标记为 `cosmetic` 的 op **MUST NOT** 翻转任何 case | 机械 | `FAIL`：回炉门② |
| **B3** | 结论（`verdict_token`）无差异的 case **MUST NOT** 出现在变更清单里 | 机械（脚本结构性保证） | 不应发生；发生即脚本判定失效，报卡点 |

**判定态与阻断规则**：

| 态 | 含义 | 阻断 |
|---|---|---|
| `PASS` | 机械判定完成且无违反 | 否 |
| `FAIL` | 机械判定发现违反 | ✅ 阻断 |
| `INCOMPLETE` | 存在 `need_manual`（如 `verdict_token` 缺失），判定不完整 | ✅ **阻断**（判定不完整 ≠ 通过） |
| `N-A` | 无 `ops` 清单，本门只判 B3 | 否（但 MUST 在报告中声明） |

> **B3 提供 0 误报的机械保证**：只要两侧结论无差异，该 case 绝不入变更清单。
> 实测：某组 4 条 case 两版裁决逐字一致 ⇒ 变更清单里 0 条误报。

> **`out_of_scope`（第三种 op claim）**：变更**不在电池覆盖范围内**（如改测试脚本而非判据）时，该 op MUST 标
> `out_of_scope` **并附 `note` 说明为何超范围**；它**不参与** B1/B2。这条防的是**拿超范围声明掩盖未翻转** ——
> 未附 note 时脚本 MUST 告警；**未知 claim 值 MUST 被告警**，NEVER 静默忽略。

## 五、输出格式

门④.5 的产出 MUST 按此格式，可直接充当 changeset 里「哪些行为变了、因为哪条改了」一节：

```
## 门④.5 变更验收 · <skill> <前版> → <后版>

| case_id | 前版条款集 | 后版条款集 | 翻转? | 方向 | 条款差 |
|---|---|---|---|---|---|
| F6 | §评分规则 / §Phase 2 Step 5 | §评分规则 / §自主优化循环 Phase 2 Step 5 | ✅ | 前→后 | 棘轮口径：绝对分 delta → paired 多数决 |
| U2 | §异常与边界条件 / §约束规则 | §异常与边界条件 / §约束规则 | ❌ | — | 无（不入清单） |

**硬门判定**：B1 PASS / B2 PASS / B3 PASS

**变更清单**：F3, F5, F6, F7, F8
**未变清单（B3 保证不入变更清单）**：F1, F2, F4, U1, U2, U3, U4, U5
**need_manual**：无
**作废（clauses 为空）**：无
**evidence 待复核（软信号，不影响计入）**：无
```

> 上例为**实跑输出**（用 pilot2 的真实 ledger 数据回放）：机械判定得出 5 条翻转，
> 与人工 ground truth 完全一致，且 8 条未变 case 零误报入清单。

## 六、两阶段演进

| 阶段 | 台账来源 | 依赖 | 状态 |
|---|---|---|---|
| **阶段 1（已上线）** | 由人 / 评审者从现有评测输出整理台账 | **不依赖任何 skill 的 schema 改动** | 实测可达 100% recall |
| **阶段 2（未上线）** | 由执行 skill 自动产出（含 `verdict_token`） | 需改被测 skill 的 schema —— **须独立 proposal** | 待议 |

## 七、兜底处理（NEVER 静默失败）

| 场景 | 处置 |
|---|---|
| 前版台账缺失（无基线） | **N-A** 并在报告中显式声明「无基线，本次未做行为级验收」；NEVER 以"看起来没问题"代替 |
| `verdict_token` 缺失 | 该条转 `need_manual`，B1/B2 判 `INCOMPLETE` 并**阻断**；NEVER 凭 `verdict` 文本或 `clauses` 字符串模糊匹配代替 |
| `clauses` 为空 | **合法**（全 PASS 的干净 case 本无条款）；该条正常参与判定。仅当 **token 声称 FAIL 而条款集为空**（自相矛盾）才作废；作废数 MUST 报出 |
| 两侧 `clauses` 字符串不同但结论相同 | **判为未变**（字符串漂移不是行为差异）；该 case **MUST NOT** 进变更清单 |
| `evidence` grep 回验未命中 | 标 `unverified` 待复核，MUST 报出；**NEVER 因此作废整条** |
| 两侧 case 不齐（某侧缺 case） | 报出「两侧不齐」清单；**不得**据此推断翻转 |
| 电池不存在 | 报告「无电池，门④.5 N-A」并列出建电池的前置任务；NEVER 静默跳过 |
| 脚本自身异常 | 兜底放行至门⑤，但 MUST 在交付摘要标注「门④.5 降级放行（脚本异常）」 |

## 八、设计依据与边界（诚实声明）

**依据**：三轮 pilot 的实测对照（详见工作区 `tri-forge-handoff/compliance-items.md` 与 `pilot2b/REPORT.md`）。

**边界（MUST 随本门一起被引用，防止过度外推）**：

1. **本门验证的是"行为有没有变"，不是"变好还是变坏"。** 它不替代评分、不替代人工判断质量。
2. **依赖一份 case 电池。** 电池 MUST 有单一事实源并随 skill 演进；**电池的 search / eval 两集
   MUST 分离**，否则会重演"同一批 prompt 既当搜索集又当评估集"的过拟合坑。
3. **存在循环性风险**：若判类者同时是台账的撰写者，其结论与台账同源。缓解：每条翻转 MUST 锚在
   **结构性证据**上（如某概念在原版 grep 零命中），而非主观判断。
4. **未验证采集管道**：本门的实测只覆盖"台账形态下的诊断接口"，
   **不覆盖**真实评测系统如何把 case 执行记录写成台账 —— 后者需一次真实试点关闭。
5. **首选落地为"提示"而非"阻断"**：在电池的 search/eval 尚未分离前，B1/B2 的 FAIL 记账告警，
   **不阻断**落盘；待电池成熟后再升级为阻断门。
