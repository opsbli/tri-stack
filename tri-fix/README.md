# tri-fix

调试修复下游执行 skill。读取 tri-intent 快照 §三 结构化结论，处理 I12（调试修复）意图，自主管理「故障报告 → 根因诊断 → 修复任务 → 执行 → 修复报告」完整调试工作流。融合 6 阶段反馈循环与 4 阶段根因验证方法论，含双审批门 + 执行前确认 + 因果确认 + 回归测试门禁 + 最小化修复原则。当 tri-intent 快照下游路由建议指向本 skill 时激活。

## 特性

- **双审批门 + 执行前确认**：门①故障确认 → 门②诊断审计 → 门③执行前确认，三道关卡严格串行，禁止跳门直接改代码
- **6 阶段系统化调试方法论**：建立反馈循环 → 复现最小化 → 假设生成 → 插桩验证 → 修复回归 → 清理复盘，强制「先诊断后修复」
- **因果确认测试**：根因验证须通过三步因果确认（去掉根因→消失→加回→重现），不可跳过
- **回归测试门禁**：先写回归测试再修复，原始复现不再复现 + 回归测试通过 + 全量测试通过方可宣布完成
- **最小化修复原则**：变更仅落在根因处，重构与优化留给后续独立任务，需扩大范围须经用户确认
- **调试反模式对照表**：8 条反模式，每条含「特征（怎么发现自己正在犯）+ 替代做法」，命中即回退对应阶段
- **逃生舱机制**：无法建立反馈循环时停在阶段 1，向用户索取环境权限 / 抓取产物 / 生产插桩许可三者之一
- **三态依赖检测**：独立安装时支持快照模式 / 引导安装 / 降级模式三态逻辑

## 安装

将 `tri-fix/` 目录放入你的 skills 目录即可：

```bash
cp -r tri-fix/ /path/to/your/skills/
```

> 本 skill 依赖 tri-intent 进行意图识别与输入校验。若未安装 tri-intent，激活时会进入引导安装或降级模式（见 SKILL.md §上游依赖检测）。

## 使用

### 1. 调试工作流（核心流程）

收到 tri-intent 快照（L2 = I12）后，按以下链路串行推进：

```
快照 §三 → bug-report.md → 门①审计 → diagnosis.md → 门②审计 → fix-tasks.md → 门③执行前确认 → 执行 → fix-report.md
```

> **核心铁律**：没有能变红的反馈循环，就没有假设阶段——盯着代码看再久也无济于事。

| 阶段 | 产出物 | 审批门 | 关键动作 |
|---|---|---|---|
| 1 | `bug-report.md` | 门① | 建立反馈循环（10 种方式）+ 复现最小化 + 边界测绘 |
| 2 | `diagnosis.md` | 门② | 3-5 个可证伪假设 + 优先级排序 + 插桩验证 + 因果确认 |
| 3 | `fix-tasks.md` | 门③ | 修复方案 + 回归测试清单（先写测试再修）+ 依赖图 |
| 4 | 修复补丁 | — | 按 fix-tasks.md 逐项修复 + 回归测试，复选框状态切换 |
| 5 | `fix-report.md` | — | 清理确认 + 事后复盘 + 根因归档 + 遗留建议 |

### 2. 调试方法论与工作流映射

| 方法论阶段 | 工作流产出物 | 审批门 | 核心交付 |
|---|---|---|---|
| 阶段 1+2 建立反馈循环+复现最小化 | `bug-report.md` | 门① | 能变红的反馈循环 + 最小化复现 |
| 阶段 3+4 假设生成+插桩验证 | `diagnosis.md` | 门② | 3-5 个可证伪假设 + 因果确认证据 |
| 阶段 5 修复+回归 | `fix-tasks.md` + 执行 | 门③ | 修复补丁 + 回归测试通过 |
| 阶段 6 清理+复盘 | `fix-report.md` | 无 | 清理确认 + 事后复盘 + 根因归档 |

### 3. 交付产物

链路文档落盘于 `.tribro/fixes/<命名>/`，命名沿用 tri-intent 快照：

```
.tribro/fixes/I12_20250211_143022_6a5c037d/
├── bug-report.md
├── diagnosis.md
├── fix-tasks.md
└── fix-report.md
```

## 设计原则

- **先诊断后修复**：没有能变红的反馈循环就没有假设阶段，强制在动手修复前完成反馈循环建立和根因验证
- **因果确认不可跳过**：根因验证须通过去掉→消失→加回→重现的三步因果确认，杜绝猜测式修复
- **最小化修复**：只改根因处，不顺便重构、不顺便优化，保持改动最小化
- **职责边界**：本 skill「先诊断后修复」；tri-coding 负责新功能编码开发，绝不跳过诊断直接改代码
