# 代码版权与许可证合规（硬红线 · 完整参考）

> **原则**：tri-fix 产出的修复补丁必须**原创、可合规使用与发布**。版权与许可证问题零容忍——任何疑似侵权或许可证冲突的补丁，在解决前不得提交、发布或交付。
> 📌 本文件为 `SKILL.md` §代码版权与许可证合规（硬红线）的展开参考，两者冲突时以本文件为准。
> 📌 本文件按**调试场景**特化：重点覆盖「抄补丁 / 为修 bug 引入依赖 / 来源不明 fork 与 monkey patch / AI 披露」四类调试特有风险。

## 一、四类风险与预防（调试场景特化）

| 风险 | 调试场景中的典型形态 | 预防措施 |
|---|---|---|
| 补丁版权/署名 | 从 StackOverflow / GitHub issue / 博客整段复制补丁代码，剥离原始署名与 LICENSE | 依据根因原创实现；确需复用开源片段则完整保留其 LICENSE 与版权声明 |
| 许可证冲突 | 为修 bug 引入新依赖或上游 patch，与目标仓库许可证不兼容（如 GPL 传染） | 遵循目标仓库现有许可证；引入前先核对依赖许可证兼容性 |
| 依赖/供应链 | 为绕过 bug 换用来源不明的 fork、私有付费包，或对第三方库打未经审查的 monkey patch | 仅用可商用、来源可信的依赖，记录版本与来源；monkey patch 须在 `fix-report.md` 显式披露 |
| 标识/披露 | 组织要求披露 AI 生成代码，修复补丁未标注 | 提交前确认相关方政策，按需标注「AI 生成」 |

## 二、生成期：从源头杜绝

- 补丁主体依据 `diagnosis.md` 的根因结论原创实现，网络片段仅作参考不整段照搬。
- 只引入可商用的公共依赖并保留其许可证信息；不绕过付费/私有限制。
- 补丁落盘时，按目标仓库许可证写入声明或头部注释。

## 三、提交/发布前：合规自检（硬性，不过则不出）

1. 是否复制了他人代码而未保留其许可证/署名？→ 是则补回或改原创。
2. 是否引入了与目标仓库许可证不兼容的依赖或上游 patch？→ 是则替换。
3. 是否使用了未授权/来源不明的依赖、fork 或私有包？→ 是则替换。
4. 补丁是否与某闭源/商业代码高度雷同（疑似仿写）？→ 是则重写。
5. 是否按项目/平台/雇主要求标注了 AI 生成或 disclosures？→ 按需标注。
6. 对第三方库的 monkey patch / 猴子补丁是否已在 `fix-report.md` 显式披露？→ 未披露则补。

## 四、平台/仓库条款速查（提交与发布前必读，以各平台最新规则为准）

- **代码托管（GitHub/GitLab/工蜂等）**：AI 生成补丁通常可提交，但组织/雇主政策可能要求披露；商用以平台与雇主政策为准。
- **开源社区**：向上游回补（upstream patch）须遵循该项目的 CLA / DCO 签署要求。
- ⚠️ 各平台与组织条款会更新，提交、发布与商用前务必查阅最新官方规则；本表仅为方向提示，**不构成法律意见**。

## 五、商用授权与原创存证

- **可商用确认**：接商单或用于公司产品前，确认目标仓库许可证与生成工具授权范围允许相应使用。
- **原创存证（建议）**：保留 `diagnosis.md` 的根因推导链、提示词与生成时间作为原创证据。

## 六、侵权应急

- 若收到 DMCA / 下架 / 权属投诉：先撤回争议补丁，核对权属；确属误用则凭存证申诉，确属侵权则替换并致歉。
- 全程保留链路文档与依赖来源记录，作为争议时的证据链。

## 七、合规底线（五条全过才可交付）

> **原创不照搬、许可证兼容、依赖已授权、披露到位、LICENSE 已声明**——五条全过，才可提交、发布与交付。

| 底线条目 | 判定 | 未过时的处置 |
|---|---|---|
| 原创不照搬 | 补丁无整段照搬他人代码 | 依 `diagnosis.md` 根因改写为原创实现 |
| 许可证兼容 | 新引入依赖/上游 patch 与目标仓库不冲突 | 替换为兼容依赖 |
| 依赖已授权 | 依赖可商用、来源可信，无不明 fork | 替换为可信公共包 |
| 披露到位 | 按平台/雇主政策标注 AI 生成；monkey patch 已在 `fix-report.md` 披露 | 补充标注/披露 |
| LICENSE 已声明 | 落盘补丁带许可证声明或头部注释（frontmatter `license` 字段已声明） | 补写声明 |
