# 通用编程开发规范

> 本规范是 tri-coding 技术栈体系的**基底层**，始终加载。具体技术栈 skill 在此基础上叠加增强。

## 技术栈定义

通用软件工程规范，适用于跨语言、跨技术栈的项目，提供与具体语言无关的编码原则与最佳实践。

## 编码规范

### 命名与清晰性

- **命名即文档**：变量、函数、类、模块名必须有意义且一致，能自解释用途
- **注释解释"为什么"**：关键逻辑处注释说明设计原因，而非重复代码行为
- **卫语句优先**：避免过深嵌套，优先 Early Return 处理异常分支
- **消除魔法值**：硬编码数值/字符串提取为具名常量或枚举，集中管理
- **风格一致性**：遵循项目既有命名/目录/错误处理/测试方式，避免引入第二套体系

### 设计原则

- **SOLID 核心**：单一职责、依赖倒置、接口隔离，保持模块边界清晰
- **高内聚低耦合**：模块内聚焦一个领域，模块间通过稳定接口协作
- **组合优于继承**：优先组合、委托与策略，减少脆弱继承层次
- **DRY/KISS/YAGNI**：拒绝重复、保持简单、避免过度设计与预留式架构
- **复用胜过新造**：优先复用现有组件/函数/工具，扩展时保持风格统一

### 健壮性

- **积极防御**：公共接口必须校验入参、边界条件与状态前置条件，Fail Fast
- **精准错误处理**：只捕获能处理的异常，保留足够上下文，禁止吞错
- **副作用可控**：I/O、时间、随机性、全局状态必须封装并可替换
- **安全意识**：不记录密钥与敏感信息，不信任外部输入，权限分层

### 可测试性

- **纯函数优先**：核心业务规则写成纯函数，依赖注入，避免隐藏依赖
- **回归留痕**：修复问题必须留下可复现用例，避免"修了又回归"
- **按需覆盖**：核心业务规则、复杂算法、关键边界必须覆盖正常与异常路径

### 文档化

- **公共 API 文档**：包含使用示例和注意事项
- **决策记录**：重要设计决策记录在规范文档的决策章节
- **避免过度注释**：不重复代码可表达的内容，保持文档与实现同步

## 决策优先级框架

当存在多种有效方案时，按以下顺序评估：

1. **与规范一致性**：是否完全满足需求规范要求
2. **与项目氛围契合度**：是否符合项目架构风格和编码惯例
3. **可测试性**：是否易于编写测试用例
4. **思维清晰度**：其他开发者能否理解代码背后的思考过程
5. **简洁性**：是否是能解决问题的最简单方案
6. **可逆转性**：后续修改的调整成本

## 质量检查清单

### 编码前

- [ ] 是否阅读了相关上下文文档（ARCHITECTURE.md / CONVENTIONS.md 等）
- [ ] 是否理解了项目设计氛围（3-5 个核心要点）
- [ ] 命名是否符合项目现有命名模式
- [ ] 是否识别了可复用的既有组件/函数

### 编码后

- [ ] 代码编译通过，无语法错误
- [ ] 代码风格符合项目约定
- [ ] 关键逻辑有注释说明"为什么"
- [ ] 错误处理完善（不吞错、有上下文）
- [ ] 公共接口入参已校验
- [ ] 无硬编码魔法值
- [ ] 无过深嵌套（优先卫语句）

### 提交前

- [ ] 所有测试用例通过
- [ ] 测试覆盖主要场景和边界条件
- [ ] 实现决策已记录
- [ ] 文档已同步更新

## 氛围感知检查点

编写代码时持续自问：

- 这段代码看起来像这个项目原有的代码吗？
- 使用的设计模式是否与项目主流模式一致？
- 错误处理方式是否符合项目惯例？
- 日志格式和级别是否符合项目约定？
