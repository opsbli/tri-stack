## 一、目标

给 tri 家族补上**唯一缺失的一环**：一个真的把应用跑起来、驱动用户路径、拿到同源证据、
并在失败时驱动「归因 → 修复 → 复验」有界循环的**验证执行能力**。

它不是「接入 TestSprite」。TestSprite 只是这个能力席位的**可选引擎之一**。

**不改变**任何现有 skill 的意图认领与路由归属 —— tri-verify 是横向型，不注册 `tri-intent` 下游。

## 三、MECE 判定（先排除重叠，这是提案成立的前提）

| skill | 层次 | 作用域 | 核心动作 |
|---|---|---|---|
| `tri-review` | 静态 | 任意下游 | 读码审查，不执行 |
| `tri-test` | 计划层 | **SDLC P6 阶段绑定** | 编计划 / 映射验收标准 / 缺陷台账 / 出 P6 门禁结论 |
| **`tri-verify`（本提案）** | **执行引擎层** | **横向，跨下游复用** | **驱动运行中的应用，取同源证据，驱动有界修复循环** |

**分工不是竞争，是依赖**：`tri-test` 编制出三层测试计划后，其 AT/集成层的**实际执行**可委派 `tri-verify`；
`tri-verify` 只回答「这条路真的走得通吗」，不负责计划覆盖率与缺陷台账。

> 依据 `family-spec.md` §1.2 三条 MECE 判据：以「核心动作」为唯一主键 —— 三者核心动作分别为
> 「读」「编」「跑」，互不重叠。§1.1 角色 = **横向型**（与 `tri-true` / `tri-evolve` 同类）。

## 四、设计

### 4.1 角色与激活方式

| 项 | 值 |
|---|---|
| slug | `tri-verify`（备选名 `tri-prove`，见 §八 决策点 D1） |
| 角色 | **横向型**（`family-spec.md` §1.1）—— 不注册 `tri-intent` 路由表 |
| 激活 | **委派制**：由 `tri-coding`（交付前） / `tri-fix`（修复后） / `tri-sdlc`（P6-P7）显式唤醒；用户亦可直接调用 |
| 形态对标 | 与 `tri-coding` 既有 **§交付前风险预筛自动门 → 自动委派 tri-true** 完全同构（L218–258） |
| 落盘区 | `.tribro/verify/<命名>/` —— 目录名可由 slug 机械推导，符合 §1.4 判据 ✅ |

### 4.2 在 tri-coding 链路中的插入位置

```
执行（按 tasks.md 逐项编码+测试）
        │
        ▼
   implements.md
        │
        ▼
【新增】功能验证自动门（tri-verify）  ←── 失败 → 三类归因 → 有界循环（≤2 轮）
        │ 通过 / 盖章未执行                        ↓
        │                                    委派 tri-fix / 回炉 tasks.md
        ▼
   §交付前风险预筛自动门（tri-true）  ← 此时 tri-verify 的证据包可作 T1 信源
        │
        ▼
      交付
```

**顺序理由**：verify **先于** true —— 前者产出的同源证据包（DOM 快照 / 录像 / 步骤统计）是 T1 级事实源，
可直接支撑后者的句级引用归因；反序则 tri-true 只能核查「未经验证的自述」。

### 4.3 触发规则（确定性判定 · 无需人工判断「何时触发」）

| # | 触发条件 | 判定来源 | 默认动作 |
|---|---|---|---|
| V1 | 交付物含可运行入口（dev server / build 产物 / HTTP endpoint / CLI 入口） | `implements.md` 交付物清单 | 执行 |
| V2 | `tasks.md` §3.3 AT 层存在 ≥1 条端到端用户路径用例 | `tasks.md` | 执行 |
| V3 | 交付物为纯库 / 纯类型定义 / 纯静态资源，无运行时入口 | `implements.md` | **跳过** + 盖章「不适用」 |
| V4 | 用户显式要求端到端验证 | 快照 §三 / 用户原话 | 强制执行 |
| V5 | 快照 D1 ∈ {medical, financial, legal}，或属 R2 类操作（删除/发布/支付/迁移/权限） | 快照 D1 + `tasks.md` | 强制执行，且失败 **MUST** 人审 |

全部未命中 → 盖章 `功能验证: 未触发（可交付）`，零打扰继续。

### 4.4 三类归因（核心机制 · 改动任何代码之前 MUST 先归因）

> 原文明确警告：*「一次断言失败至少存在三种解释……如果工具默认把所有失败都归因于产品代码，
> 自动修复反而可能主动制造缺陷。」* 本节是这句话的可执行化。

| 归因 | 判据（来自证据包） | 处置 | 计入「修复轮次」 |
|---|---|---|---|
| **A · 产品缺陷** | 录像动作数 = 计划数；DOM 快照确认目标从未出现 / 被遮挡 / 内容错 | 回炉 `tasks.md` → 委派 `tri-fix` | ✅ 是 |
| **B · 契约缺陷** | 录像动作数 < 计划数；断言退化为「元素可见」；断言与 `requirements.md` 不符 | 更新契约，**单独标记为契约变更** | ❌ 否 |
| **C · 环境抖动** | 目标不可达 / 超时 / 非确定性失败 | 重试 1 次；仍失败则标记 `flaky` 并停止，**不修代码** | ❌ 否 |

**硬规则**：
- 连续 **2 轮**同类失败 → **停止**，升级人审，禁止继续调整。
- **NEVER** 为让测试变绿而弱化断言、跳过步骤或删改用例 —— 这是比明确失败更危险的
  「confident but wrong pass」。
- 归因判定 MUST 引用证据包中的**具体观察**（DOM 查询命中数 / 元素清单 / 截图），不得凭推测。

### 4.5 引擎抽象（平台无关契约 · 单一事实源）

```
engine contract:
  reachability(target: url | port) -> bool        # 派发前预检，避免注定失败的消耗
  create(contract) -> testId
  run(testId) -> { status, exitCode, runId, stepSummary }
  fetch_failure(runId) -> bundle {
      result.json / code / DOM snapshots / video / root-cause hypothesis
  }
  一致性约束: bundle 内 snapshotId / testId / runId MUST 同源，
              异源直接拒收（NEVER 拼装看似完整的混合证据包）
```

| 引擎 | 实现 | 定位 | 前置条件 |
|---|---|---|---|
| **A · 本地（默认）** | Playwright（前端）+ pytest/`requests`（后端） | 零外部依赖、离线可跑、零成本 | 本地有 Playwright/pytest |
| **B · TestSprite（可选增强）** | CLI `@testsprite/testsprite-cli` 或 MCP `@testsprite/testsprite-mcp` | 语义定位 + 云端真浏览器 + 失败证据包 | `TESTSPRITE_API_KEY` + 网络可达 + credits |

**前后端不对称是刻意的**（沿用原文结论）：前端模糊性有收益（抗 UI 漂移），后端契约必须精确（模糊性只增加假阳性）。

引擎选择 MUST 逐条记录在 `run-log.jsonl` —— **NEVER 混同两引擎的结果**。

### 4.6 降级矩阵（硬要求 · 保证不阻断交付）

| 情形 | 处置 |
|---|---|
| 两引擎均不可用 | 盖章 `功能验证: 未执行（无可用引擎）`，继续交付，**NEVER 阻断** |
| 目标不可达（预检拦截） | 盖章 `功能验证: 未执行（目标不可达）`，继续交付 |
| TestSprite 无 key / 欠费 / 超时（退出码 7） | **自动降级到引擎 A**，记录降级原因 |
| 引擎 A 缺 Playwright | 降级为「仅后端契约验证」，前端标 N/A |
| 官方排除路径（OAuth/SSO/2FA、原生文件对话框、iframe、多标签页） | 契约层标注不适用，MUST NOT 声称为已验证 |

> 对标 `tri-coding` 既有写法：「tri-true 未安装 → 标注降级后继续，NEVER 阻断交付」（L258）。

### 4.7 分层策略（成本硬约束）

| 层 | 内容 | 时机 | 引擎 |
|---|---|---|---|
| **冒烟层** | ≤5 条高价值用户路径（登录 / 核心表单 / 支付前置） | tri-coding 交付前、PR | 可上引擎 B |
| **回归层** | 全量行为契约（通过的用例留存累积） | 夜间 / 发布前 | 优先引擎 A |
| **单元层** | UT / 类型检查 / API 契约 | 每次改动 | 始终本地 |

**NEVER 把全量回归无差别放到昂贵路径上**（前端 ≈2 min/次 + 扣 credits，后端 ≈3 s）。

### 4.8 落盘产物

```
.tribro/verify/<命名>/
├── contract.md           验证契约（行为陈述 + 步骤 + 断言 + 层级 + 适用引擎）
├── run-log.jsonl         每轮 {round, engine, testId, runId, status, exitCode, attribution}
├── failure-<runId>/      失败证据包（同源校验通过才落盘）
├── escalation.md         触发人审时的升级说明（仅当升级）
└── verdict.md            最终判据 + 盖章（四态之一，见下）
```

**`verdict.md` 四态封闭判据**：

| 盖章 | 含义 |
|---|---|
| `功能验证: 通过（engine=<A\|B>，用例 n/n）` | 可交付 |
| `功能验证: 修复后通过（轮次 n，归因 A/B/C）` | 可交付 |
| `功能验证: 已升级人审（连续 2 轮同类失败，归因 <X>）` | **停止自动交付** |
| `功能验证: 未执行（<原因>）` | 可交付，但明确标注未验证 |

## 九、验收标准

1. 无 key / 无网络下，`tri-coding` 交付**不被阻断**，且 `verdict.md` 盖章 `未执行（原因）`
2. 有引擎时，失败用例产出**同源**证据包；人工构造的异源包被**拒收**（不得落盘）
3. 三类归因可复现：① 故意写错契约 → 判 B；② 故意断开 dev server → 判 C；③ 故意改坏产品代码 → 判 A
4. 重试上限生效：连续 2 轮同类失败后**停止并升级**，不出现第 3 轮
5. 契约变更被**单独标记**，不混入「产品修复」计数
6. `tri-fix` 修复后复验调用链成立（修复 → 自动复验 → 通过或升级）
7. 四处计数一致 + `version-lint.py` 退出码 0 + `apply.py` 连跑两次第二次「写入 0」
