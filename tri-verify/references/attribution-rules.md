# 三类归因判据表

> 本文件是 `tri-verify` **归因环节的单一事实源**。SKILL.md §三类归因 只给出表与硬规则；
> 判据细化、正反例、不确定态处置全部登记在此。
>
> **可扩展性**：新增归因维度只需在本表追加行，并给出**可机械判定的判据**
> （必须能由退出码 / 证据字段 / 轨迹比对之一判定）。只写主观描述的规则不予采纳。

---

## 一、为什么归因必须前置于改动

一次断言失败**至少存在三种解释**：

1. 产品真的坏了
2. 测试契约写错了
3. 运行环境不稳定

若工具默认把所有失败都归因于产品代码，**自动修复反而会主动制造缺陷** ——
对一个本来正确的实现，因为契约写错而"修"出 bug。

因此本 skill 的硬红线是：**改动任何代码之前 MUST 先归因**，且归因结论 MUST 附具体观察。
"我觉得是产品的问题"不构成归因。

## 二、三分类判据

| 归因 | 判据（逐条核对，命中任一即归类） | 处置 | 计入修复轮次 |
|---|---|---|---|
| **A · 产品缺陷** | ① 执行轨迹的**动作数 = 契约计划数**（没有步骤被跳过）；② 证据包确认目标元素**从未出现 / 被遮挡 / 内容错误**；③ 断言目标与 `requirements.md` 验收标准**一致**（即契约写对了） | 回炉调用方修复 | ✅ 是 |
| **B · 契约缺陷** | ① 执行轨迹动作数 **< 计划数**（有步骤被跳过或断言退化）；② 断言退化为「元素存在 / 元素可见」；③ 断言与验收标准**不一致**（契约写错了） | 修改契约，**单独标记为契约变更**，重跑 | ❌ 否 |
| **C · 环境抖动** | **由引擎退出码机械判定**（见 §三），**无需语义判断** | 重试 1 次；仍失败则标 `flaky` 并停止，**不修代码** | ❌ 否 |

### 判据 ① 的读法（最容易出错的一条）

「动作数是否一致」区分的是**A 与 B 的前置条件**：

- 动作数**一致** ⇒ 执行 Agent 确实按计划走了每一步，失败发生在**结果校验**上 ⇒ 更可能是 A（产品真坏了）
  或 B③（断言目标写错）
- 动作数**少于**计划数 ⇒ 执行 Agent 中途没走下去（找不到元素而跳过、或弱化了断言）⇒ **优先判 B**

> 归因顺序建议：**先用退出码排除 C → 再看动作数分 A/B 前置 → 最后用需求对齐定 A/B**。

### 判据 ③ 的读法（A 与 B 的最终裁决）

判据 ①② 只能把范围收窄，**决定性的裁决来自需求对齐**：

> 断言的目标在 `requirements.md` 里**确实被要求** ⇒ 契约写对了，产品没实现 ⇒ **A**
> 断言的目标在 `requirements.md` 里**没有被要求** ⇒ 契约写错了 ⇒ **B**

**正例（来自真机探测文章的实测场景）**：某登录页断言"按钮下方应存在 Register 链接"，
证据包显示页面搜索 Register 得到 0 个匹配、可交互元素只有用户名框/密码框/登录按钮。
此时**不能直接判 A** —— 必须回查需求：

| 需求实际内容 | 归因 | 处置 |
|---|---|---|
| 需求要求该页面有注册入口 | **A** | 修页面 |
| 需求未要求注册入口（断言是自加的） | **B** | 更新契约 |
| 需求为空 / 不可判定 | **uncertain** | 升级人审，**NEVER 猜成 A 去改代码** |

## 三、C 类的机械判据（退出码映射）

| 退出码 | 含义 | 归档 |
|---|---|---|
| 0 | passed | 通过 |
| **1** | failed / blocked / cancelled | **读证据包做 A/B 归因** |
| 3 | auth error | **C** |
| 4 | 用例 / 运行未找到 | B（配置缺陷） |
| 5 | validation error（含证据包 `meta.runId` 不一致） | B（契约缺陷） |
| 6 | conflict（已有运行中实例 / snapshot 生成中） | **C** |
| 7 | timeout | **C** |
| 10 | transport / network failure | **C** |
| 11 | rate limited | **C** |
| 未知码 | 引擎契约偏离 | **C** + 记录偏离 |

> **为什么值得把它做成机械判据**：环境类失败（网络抖动、鉴权过期、限流、超时）
> 在语义上与产品缺陷完全不像，但**在时间压力下极易被"顺手修一修"**。
> 用退出码一刀切，等于从机制上取消了这类误判的可能性。

### 3.1 归因与轮次计数的关系（可执行真源：`scripts/verify_gate.py`）

| 归因 | 计入产品轮次 | 是否打断「连续同类」链 | 自身上限 |
|---|---|---|---|
| A · 产品缺陷 | ✅ 是 | 否 | 连续 2 轮同类 → 升级 |
| B · 契约缺陷 | ❌ 否 | **是（打断）** | 同用例 ≥2 次 → 升级 |
| C · 环境抖动 | ❌ 否 | **是（打断）** | 重试 >1 次 → 升级 |
| `uncertain` | ❌ 否 | 否 | 异常计数 ≥2 → 升级 |

**「B/C 打断连续链」是一条必须写明的规则**：A→B→A 序列中，两次 A 失败**并不连续**
（中间夹了一次契约修正），若把 B/C 从序列里剔除而不打断，A…A 会被误算成「连续 2 轮 A」
从而把一次正常的回炉误判为失控 —— 这是实现期实测抓到的缺陷。

**总迭代硬上限 6**：规则「连续同类」单独使用时，无法阻止「A/B 跨用例交替」构造出的无限循环
（每轮换一个用例，连续计数始终为 1）。故补一条与归因无关的总量上限作为结构性兜底。

## 四、生产 / 消费依赖的失败传播规则

当一批用例存在数据依赖（先产出凭证 → 再消费凭证 → 最后清理）时：

> **不要把消费者的失败归因于消费者自身，直到它依赖的全部生产者在本轮中通过。**

| 现象 | 正确归因 |
|---|---|
| 生产者失败 + 下游批量失败 | 归因**最早失败的生产者**；下游是传播，不是缺陷 |
| 生产者通过 + 消费者失败 | 才可归因消费者 |
| 清理失败 | 单独判定：可能是测试数据污染，属 B（契约）或 C（环境） |

若不遵守此规则，一次生产者失败会产生 N 条虚假的「产品缺陷」，把轮次上限瞬间耗尽。

## 五、不确定态（`uncertain`）的处置

以下情形 MUST 标注 `uncertain` 并**升级人审**，NEVER 猜成 A 类：

| 情形 | 原因 |
|---|---|
| 证据包未通过同源校验 | 材料可能不是同一次运行，任何归因都不可信 |
| 执行轨迹信息缺失（无步骤统计） | 无法核对动作数，A/B 前置条件不可判 |
| 需求文档缺失或断言目标无对应验收标准 | 判据 ③ 无法裁决 |
| 引擎返回未知退出码且无失败摘要 | 连失败类型都不确定 |
| 同一用例在同一轮中出现**互相矛盾**的证据 | 例如录像显示点击成功但 DOM 快照无变化 |

> `uncertain` **不计入 A 类轮次**，但 MUST 计入「异常计数」；异常计数 ≥2 时同样升级人审。

## 六、反模式清单（MUST NOT）

| 反模式 | 为什么危险 |
|---|---|
| 为让测试变绿而**弱化断言**（如把「显示错误提示」改成「页面可见」） | 产出「自信但错误的通过」，比明确失败更危险 |
| 跳过或删掉「麻烦的」步骤 | 同上；且掩盖了真实的产品路径 |
| 把断言从「功能可用」降级为「元素存在」 | 元素存在 ≠ 功能可用（`src` 返回 404 的图片，`img` 元素依然存在） |
| 反复调整契约直到变绿 | 契约成了"迎合实现"的产物，失去独立判据能力 |
| **环境类失败顺手改代码** | 本表 §三 已用退出码堵死这条路 |
| 无人审直接放行 `已升级人审` 态 | 门禁规则本身仍需人负责 |
| 把 `未执行` / `未触发` 当作 `通过` 消费 | 调用方 MUST 按四态区分，NEVER 只判断「有没有红」 |
