# 验证执行（横向验证型 · 不注册下游路由）

> 本 skill 是 tri-xxx 家族的**横向验证型**能力，为任一下游 skill 补齐「交付物真的跑起来了吗」这一环。
> 用户心智：**写完了 ≠ 能用**。单测与类型检查证明局部逻辑，静态审查证明代码质量，事实核查证明结论没编造——
> 但只有真的把应用打开、按用户路径点一遍，才能回答「这次修改真的没有破坏原来的功能吗」。

## 强制执行契约（Execution Contract · 最高优先级）

0. **版本检查前置硬门（第零步）**：MUST 先通过 §版本检查与更新机制（运行 `scripts/check_update.py` 做本地版本一致性校验，本仓库为自维护 fork、不做远端比对；按脚本输出与退出码处置）——此为执行流程第零步，优先于后续所有步骤。版本检查完成前 NEVER 进入后续步骤。本条目优先级高于所有其他强制前置条目。

1. **强制前置 · 委派来源判定**：激活后 MUST 先判定本次委派来源，据来源决定验证范围与交付判据，NEVER 跳过判定直接跑测试：
   - **来源 A · tri-coding 交付前门**（`implements.md` 已产出）：对本次交付物做**冒烟层**验证（≤5 条高价值用户路径），产出 `verdict.md` 供门禁消费。
   - **来源 B · tri-fix 修复后复验**：只复验**被修复的那条路径** + 其邻接路径，MUST 取修复前 `runId` 与修复后 `runId` 做对比，判定有无回归。
   - **来源 C · 用户显式调用 / tri-sdlc P6-P7**：按用户或父阶段给的范围执行；范围未给时按 V1–V5 触发规则自行判定。
   - 来源不明时 MUST 向用户澄清，NEVER 猜。

2. **触发规则确定性判定（V1–V5）**：收到来源 A/C 且未指定范围时，MUST 按 §触发规则表 逐条判定；判定结果只有「执行 / 跳过 / 强制」三种，**NEVER 由 Agent 自由裁量**。全部未命中 → 盖章 `功能验证: 未触发（可交付）`，零打扰结束。

3. **三类归因前置（核心机制 · 硬红线）**：任一失败在**改动任何代码之前** MUST 先归因（产品缺陷 / 契约缺陷 / 环境抖动），并引用证据包中的**具体观察**作为判据。NEVER 跳过归因直接改代码——工具默认把失败归因于产品代码时，自动修复反而会主动制造缺陷。

4. **有界循环 + 反规避（硬红线）**：修复-复验循环 MUST 有上限——**连续 2 轮同类失败**即停止并升级人审。
   - **NEVER** 为让验证变绿而**弱化断言、跳过步骤、删改用例、降低优先级**——这是比明确失败更危险的「自信但错误的通过」。
   - **NEVER** 以「重跑了就通过了」「手动验证过了」「下轮再修」替代真实通过。
   - 契约缺陷（B 类）的修正 MUST **单独标记为契约变更**，NEVER 混入「产品修复」计数——否则轮次上限会被契约调整稀释成无限。
   - 归因 C 类（环境抖动）MUST **不修代码**。

5. **单一门禁权威纪律（硬红线）**：本 skill 是家族内**唯一**的「运行中应用验证」门禁权威。安装云端引擎时 MUST 使用其**只配凭证、不装 agent skill** 的安装方式（见 §权威纪律）；NEVER 让外部工具往用户项目写入第二套验证循环语义（会与 `tri-init` 的 `AGENTS.md` 生成职责争抢同一文件）。若检出外部工具已写入竞争性 skill，MUST 报告并请用户裁定，NEVER 静默共存。

6. **降级不阻断（硬红线）**：引擎不可用、目标不可达、凭证缺失、额度不足时，MUST 按 §降级矩阵 逐条处置并**显式盖章**（`功能验证: 未执行（<原因>）`），继续交付，**NEVER 阻断**。但 NEVER 把「未执行」描述为「通过」。

7. **职责边界**：本 skill 只回答「这条路真的走得通吗」。测试计划编制、覆盖率映射、验收标准对齐、缺陷台账不属本 skill（由 `tri-test` 或调用方负责）；代码修复不属本 skill（由 `tri-fix` / 调用方负责）；事实性断言核查不属本 skill（由 `tri-true` 负责，本 skill 的证据包可作其 T1 信源）。

8. **自检**：作答前用一句话声明「本次模式=<来源A/B/C>，已读取范围，当前阶段=<阶段>」，若与上述规则冲突则停止并纠正。

> 本 skill 可独立安装。激活时 MUST 检测上游 tri-intent skill 是否可用，据检测结果选择执行模式：

| 模式 | 触发条件 | 行为 |
|---|---|---|
| **A · 快照模式** | 按 tri-intent §快照定位契约 定位到**可用快照**（`.tribro/LATEST.md` 指针 → 会话内最新 → 全局最新且 ≤30 分钟） | 读取快照 §三 的 `D1_任务领域` 与任务要点，用于 V5 强制触发判定与验证范围补全 |
| **B · 引导安装** | 未检测到 tri-intent | MUST 向用户提示依赖并引导安装（提示语见下） |
| **C · 降级模式** | 用户明确拒绝安装 | 从委派来源或用户请求自构造等价输入，声明「降级模式：未加载快照上下文，V5 强制触发判定退化为保守默认（按需人工确认）」 |

**模式 B 提示语**：
> 本 skill 依赖 tri-intent 进行意图识别与快照上下文；当前未检测到 tri-intent。
> 请安装：`python ops/install-skills.py --target <目标目录>`
> 注意：本 skill 也可在无 tri-intent 的情况下由 `tri-coding` / `tri-fix` 委派工作（此时走模式 C 降级）。

> **委派来源与上游态是两个正交维度**：即使 tri-intent 缺失（模式 C），只要委派方给出了范围，验证仍可完整执行；
> 上游缺失只影响 V5 强制触发判定的精度，NEVER 因此跳过验证或伪装已验证。

## 职责边界

- **本 skill 负责**：判定是否该验证（V1–V5）→ 编写并本地校验行为契约 → 派发引擎执行 → 取回同源证据 → 三类归因 → 驱动有界修复-复验循环 → 产出 `verdict.md` 判据印章。
- **本 skill 不负责**：测试计划与覆盖率（`tri-test`）、代码修复（`tri-fix`）、静态审查（`tri-review`）、事实核查（`tri-true`）、意图识别（`tri-intent`）、验收标准与需求的编写（`tri-coding`）。
- **与相邻 skill 的边界判据**：

| 相邻 skill | 判据（谁做什么） |
|---|---|
| `tri-test` | **计划层 ↔ 执行引擎层**：`tri-test` 编制计划、映射验收标准、管理缺陷台账；其 AT/集成层的**实际执行**可委派本 skill。核心动作「编」vs「跑」，不重叠 |
| `tri-review` | **静态 ↔ 动态**：`tri-review` 只读代码不执行；本 skill 只跑应用不评审代码质量。缺陷记录不混用 |
| `tri-true` | **功能可用性 ↔ 断言真实性**：本 skill 产出的同源证据包是 `tri-true` 的 **T1 级信源**；本 skill 不提供置信度与信源分级 |
| `tri-coding` | **交付方 ↔ 验证方**：`tri-coding` 产出交付物并接受门禁结论；本 skill 出结论但**不改交付物**——需修复时回炉到 `tri-coding` / `tri-fix` |
| `tri-fix` | **修复方 ↔ 复验方**：`tri-fix` 修复后 MUST 回调本 skill 复验；本 skill NEVER 自行改代码 |

## 核心能力方法论（可插拔引擎 + 三类归因 · 可扩展）

### 一、触发规则表（确定性判定 · 无需人工判断「何时触发」）

| # | 触发条件 | 判定来源 | 默认动作 |
|---|---|---|---|
| V1 | 交付物含可运行入口（dev server / build 产物 / HTTP endpoint / CLI 入口） | `implements.md` 交付物清单 | 执行 |
| V2 | 验收测试（AT）清单存在 ≥1 条端到端用户路径 | `tasks.md` §3.3 | 执行 |
| V3 | 交付物为纯库 / 纯类型定义 / 纯静态资源，无运行时入口 | `implements.md` | **跳过** + 盖章「不适用」 |
| V4 | 用户显式要求端到端验证 | 委派来源 / 用户原话 | 强制执行 |
| V5 | 快照 `D1` ∈ {medical, financial, legal}，或属高风险操作（删除/发布/支付/迁移/权限变更） | 快照 §三 + 交付物清单 | 强制执行，且**未执行即人审、失败必人审** |

> V3 与 V1/V2 同时命中时：**V3 优先**（无运行时入口则无从驱动），但 MUST 在 `verdict.md` 写明「判 V3 的依据」。

### 二、三类归因（本 skill 的核心机制）

> **一次失败至少存在三种解释**：产品真的坏了 / 测试契约写错了 / 运行环境不稳定。
> 若默认把所有失败都归因于产品代码，自动修复反而会**主动制造缺陷**。故归因 MUST 前置于任何改动。

| 归因 | 判据 | 处置 | 计入修复轮次 |
|---|---|---|---|
| **A · 产品缺陷** | ① 执行轨迹的动作数与契约计划数**一致**；② 目标元素从未出现 / 被遮挡 / 内容错；③ 断言目标与 `requirements.md` 验收标准一致 | 回炉调用方（`tri-coding` 或 `tri-fix`）修复 | ✅ 是 |
| **B · 契约缺陷** | ① 执行轨迹动作数 **< 计划数**（有步骤被跳过）；② 断言退化为「元素存在/可见」；③ 断言与验收标准不符 | 修改契约并**单独标记为契约变更**，重跑 | ❌ 否 |
| **C · 环境抖动** | **由引擎退出码机械判定**，见下表 | 重试 1 次；仍失败则标 `flaky` 并停止，**不修代码** | ❌ 否 |

**C 类的机械判据（退出码 → 归因映射，无需语义判断）**：

| 退出码 | 含义 | 归档 |
|---|---|---|
| 0 | 通过 | —— |
| **1** | failed / blocked / cancelled | **读证据包做 A/B 归因** |
| 3 | 认证错误 | C |
| 4 | 用例未找到 | B（配置缺陷） |
| 5 | 校验错误 | B（契约缺陷） |
| 6 | 冲突（已有运行中的实例） | C |
| 7 | 超时 | C |
| 10 | 传输/网络失败 | C |
| 11 | 限流 | C |

> **把最易误判的一类变成确定性判据**：`{3, 6, 7, 10, 11}` 一律归 C 且**不修代码**，只有 `1` 需要读证据包。
> 这从机制上排除了「环境不稳定被误判成产品缺陷 → 自动修复制造缺陷」这一最危险的失败模式。

**归因纪律**：
- 归因结论 MUST 附**具体观察**（执行轨迹步数 / 元素命中数 / 截图对比），NEVER 凭推测。
- 无法归因（证据不足）时 MUST 标注 `uncertain` 并升级人审，NEVER 猜成 A 类去改代码。

### 三、有界循环（「直到功能真正实现」的可控形态）

```
        ┌──────────────────────────────────────────┐
        │  轮次上限：连续 2 轮同类失败 → 停止升级人审  │
        └──────────────────────────────────────────┘
                        │
   验证失败 → 归因 ──A 产品缺陷──→ 回炉修复 → 复验 ──┐
                   ├─B 契约缺陷──→ 改契约（标记）→ 重跑 ┤
                   └─C 环境抖动──→ 重试 1 次 → 仍失败则停 ┘
```

**硬规则**（可执行真源：`scripts/verify_gate.py`）：

| # | 规则 | 判据 |
|---|---|---|
| ① | **连续 2 轮同类失败 → 停止升级人审** | 连续计数 ≥ `ROUND_LIMIT=2` |
| ② | **B / C 类打断「连续同类」链** | A→B→A **不是**连续 2 轮 A，不升级（否则会把正常回炉误判为失控） |
| ③ | 同一用例契约变更 ≥2 次 → 视为**契约设计缺陷**并升级 | `CONTRACT_REPEAT_LIMIT=2` |
| ④ | 环境抖动重试 >1 次 → 升级 | 重试上限 `1` |
| ⑤ | **总迭代 >6 次 → 升级**（防 A/B 跨用例交替绕过规则①而无界循环） | `TOTAL_ITER_LIMIT=6` |

- 触发①③④⑤任一 → MUST 停止，写 `escalation.md`，盖 `已升级人审`，**停止自动交付**。
- 规则⑤是规则①的**结构性补丁**：规则①只挡「连续同类」，单独使用时无法阻止 A/B 跨用例交替的无限循环。
- 每次复验 MUST 保存修复前后的 `runId`，用引擎的**运行对比**能力机械判定有无回归（判定一致 = 无回归 / 判定不一致 = **有回归**，含代码版本漂移检测）。
- **中断即停**：引擎的等待模式被 Ctrl-C **只 detach、任务仍在云端跑并计费**。超时/中断分支 MUST 显式发送停止指令（见 `references/engine-contract.md` 的 `cancel`），否则「有界循环」在成本上是假的。

### 四、引擎抽象（平台无关契约 · 单一事实源）

引擎 MUST 实现下列契约；实现细节见 `references/engine-contract.md`：

```
reachability(target: url | port) -> bool        # 派发前预检，避免注定失败的消耗
create(contract) -> testId
run(testId, {target}) -> { status, exitCode, runId, stepSummary }
summary(testId) -> { failureKind, hypothesis, fixTarget }   # 一屏快速分流
fetch_failure(runId) -> bundle                  # 同源证据包
diff(runA, runB) -> { verdictMatch, regressions, codeVersionDrift }
cancel(runId) -> void                           # 成本兜底：真正停止计费
```

**同源校验由引擎执行**（NOT 由本 skill 实现）：证据包内 `snapshotId` / `testId` / `runId` 不一致时引擎 MUST 拒绝交付（TestSprite 对应 `exit 5` on `meta.runId` mismatch）。本 skill 收到不一致信号时 MUST 拒收并按 C 类处置，NEVER 拼装「看似完整」的混合证据包。

### 五、降级矩阵（保证 NEVER 阻断交付）

| 情形 | 处置 | 判定信号 |
|---|---|---|
| 云端引擎无凭证 | 降级到本地引擎，记录降级原因 | `TESTSPRITE_API_KEY` 缺失 |
| 云端引擎凭证无效 | 降级到本地引擎；若属 scope 缺失（如隧道权限），MUST 明示所需 scope 请用户重签 | 退出码 3 |
| 云端额度不足 | 降级到本地引擎（本地引擎不耗额度） | `summary` / 额度查询为 0 |
| 本地引擎缺依赖（如无 Playwright） | 降级为「仅后端契约验证」，前端层标 `N/A`（MUST 标注，NEVER 声称已验证） | 依赖探测失败 |
| **两引擎均不可用** | 盖章 `功能验证: 未执行（无可用引擎）`，继续交付 | 能力探测 |
| **目标不可达** | 预检拦截 → 盖章 `功能验证: 未执行（目标不可达）`，继续交付 | `reachability` 返回 false |
| 引擎官方排除路径（OAuth/SSO/2FA、原生文件对话框、iframe、多标签页） | 契约层标注「不适用」，MUST NOT 声称为已验证 | 契约层静态判定 |
| **V1 命中但无法真机驱动**（引擎可用，但运行环境不可驱动：起服探测失败 / 引擎 `drive()` 返回 non-zero） | 降级产物 MUST 是可执行冒烟脚本（如 `npm run e2e` 级别）或结构化手测清单（步骤 + 期望 + 判据逐条可勾选），NEVER 以口头指导替代降级产物 | 起服探测失败 或 `drive()` 退出码 ≠0（与上行「本地引擎缺依赖」互补：上行 = 引擎不可用，本行 = 引擎可用而目标不可驱动） |

> **例外**：触发规则命中 **V5** 时，降级不再等于放行——`未执行` 与 `已升级人审` 两种盖章均 MUST 转人审。

## 处理流程

```
委派来源判定（来源 A / B / C）
        │
        ▼
 版本检查（第零步）→ 上游依赖检测（三态）
        │
        ▼
 触发规则判定 V1–V5 ──全部未命中──→ 盖章「未触发」→ 结束
        │命中
        ▼
 引擎探测（云端可用？本地可用？）→ 降级矩阵
        │
        ▼
 编写行为契约 → 【本地契约校验（零成本，不过则回炉契约）】   ← 成本前移闸门
        │通过
        ▼
 【可达性预检】──不可达──→ 盖章「未执行（目标不可达）」→ 结束
        │可达
        ▼
 派发执行（冒烟层）
        │
        ├──通过──────────→ 盖章「通过」→ 结束
        │
        └──失败 → 三类归因
                     ├─ C 环境抖动 → 重试 1 次 ──仍失败──→ 标 flaky → 停止
                     ├─ B 契约缺陷 → 改契约（标记）→ 重跑（不耗轮次）
                     └─ A 产品缺陷 → 回炉修复 → 复验（含前后 runId 对比）
                                              │
                                    连续 2 轮同类失败
                                              │
                                              ▼
                                    写 escalation.md → 盖章「已升级人审」→ 停止
```

### 兜底处理（NEVER 静默失败）

| 情形 | 处置 |
|---|---|
| 委派来源不明 / 范围缺失 | MUST 向用户澄清，**NEVER** 猜范围后开跑 |
| 触发规则判定结果自相矛盾（如 V1 与 V3 同时成立） | 按 V3 优先，但 MUST 在 `verdict.md` 写明依据 |
| 契约无法编写（需求过于模糊，无任何可判定断言） | 归为 B 类契约缺陷，回炉调用方补需求，**NEVER** 编造断言凑数 |
| 引擎行为与契约不符（返回未知退出码 / 字段缺失） | 按 C 类处置 + 记录「引擎契约偏离」，**NEVER** 静默当作通过 |
| 证据包同源校验失败 | 拒收，按 C 类处置，**NEVER** 拼装混合证据包 |
| 轮次达上限 | 停止 + `escalation.md` + 盖章 `已升级人审`，**NEVER** 第 3 轮 |
| 任一环节异常 | MUST 转成可见结论（哪一步失败 / 原始信号 / 可能原因），**NEVER** 静默失败或整轮崩溃 |

## 🔴 检查点与红灯清单（STOP · NEVER）

### 🔴 用户确认检查点（STOP）
- 🔴 **STOP**：委派来源不明或范围缺失——MUST 向用户澄清，未获澄清 NEVER 猜范围开跑（§强制执行契约 条 1、§兜底处理）。
- 🔴 **STOP**：有界循环达上限（连续 2 轮同类失败 / 契约变更 ≥2 次 / 总迭代 >6）——写 `escalation.md` 盖「已升级人审」停止自动交付，未获人审处置 NEVER 第 3 轮（§核心能力方法论·有界循环）。
- 🔴 **STOP**：归因不确定（证据不足标 `uncertain`）——MUST 升级人审，未获人审确认 NEVER 猜成 A 类去改代码（§核心能力方法论·三类归因）。
- 🔴 **STOP**：V5 命中且验证「未执行」或失败——`未执行` 与 `已升级人审` 两种盖章均 MUST 转人审，未获人审确认 NEVER 视为可交付（§核心能力方法论·降级矩阵）。

### 🚫 红灯清单（NEVER）
- NEVER 为让验证变绿而弱化断言、跳过步骤、删改用例、降低优先级（§强制执行契约（Execution Contract · 最高优先级））
- NEVER 以「重跑了就通过了」「手动验证过了」「下轮再修」替代真实通过（§强制执行契约（Execution Contract · 最高优先级））
- NEVER 跳过三类归因直接改代码（§强制执行契约（Execution Contract · 最高优先级））
- NEVER 把「未执行/未触发」描述为「通过」（§强制执行契约 条 6）
- NEVER 拼装同源校验失败的混合证据包（§核心能力方法论·引擎抽象）
- NEVER 让外部工具往用户项目写入第二套验证循环语义，检出竞争性 skill MUST 报告请用户裁定，NEVER 静默共存（§核心能力方法论·权威纪律）

## 交付产物

### 一、产物清单

| 产物 | 文件名 | 内容 |
|---|---|---|
| 验证契约 | `contract.md` | 行为陈述 + 步骤 + 断言 + 层级 + 适用引擎（模板：`templates/contract.md`） |
| 运行台账 | `run-log.jsonl` | 每轮 `{round, engine, testId, runId, status, exitCode, attribution, note}` |
| 失败证据包 | `failure-<runId>/` | 引擎返回的原始 bundle（**原样归档**，只校验同源，不改写结构） |
| 升级说明 | `escalation.md` | 仅在触发人审时产出：轮次记录 + 归因链 + 候选方案 |
| **判据印章** | `verdict.md` | 最终结论 + 四态盖章（模板：`templates/verdict.md`） |

### 二、`verdict.md` 四态封闭判据

| 盖章 | 含义 | 是否阻断交付 |
|---|---|---|
| `功能验证: 通过（engine=<id>，用例 n/n）` | 冒烟层全过 | 否 |
| `功能验证: 修复后通过（轮次 n，归因 A/B/C）` | 循环内收敛 | 否 |
| `功能验证: 已升级人审（连续 2 轮同类失败，归因 <X>）` | 未收敛 | **是**（停止自动交付） |
| `功能验证: 未执行（<原因>）` | 降级矩阵命中 | 否；但 **V5 命中时转人审** |
| `功能验证: 未触发（可交付）` | V1–V5 全未命中 | 否 |

> **反规避**：`未执行` 与 `未触发` MUST NOT 被调用方当作 `通过` 消费。调用方消费 `verdict.md` 时
> MUST 按上表区分，NEVER 只判断「有没有红」。
>
> **证据锚定（真机实证）**：`通过（engine=<id>…）` 与 `修复后通过` 两态 MUST 引用同源证据（runId / 用例输出粘贴 / 用户提供的截图路径）。真机/手测场景中，用户的实测结论 ONLY 在附具体证据时才可采信为「通过」——NEVER 凭「成功了」一句话盖章。

### 三、落盘规则

```
.tribro/verify/<命名>/          # 命名沿用快照命名契约：<问题类型>_<日期>_<时间>_<会话ID>
├── contract.md
├── run-log.jsonl
├── failure-<runId>/            # 仅在出现失败运行且证据包同源校验通过时创建
├── escalation.md               # 仅在升级人审时创建
└── verdict.md                  # 每轮执行 MUST 产出（判据载体）
```

- 目录名 `verify/` 由本 skill slug 机械推导，符合家族产物区命名基准。
- 每轮执行 MUST 产出 `verdict.md`；`未触发` 与 `未执行` 也 MUST 落章（否则调用方无法区分「跳过了」和「忘了」）。
- 失败证据包 MUST **原样归档**，NEVER 改写其内部结构（其同源性由引擎保证）。
