01心智模型：三句话

① 意图只识别一次

所有提问先过 tri-intent，产出快照交给下游。下游 skill 绝不重新识别意图，只读快照 §三。

② 一切落盘

链路文档进 .tribro/；真实成果物（源码、CHANGELOG）进你的工作区。项目元数据在 .tribro/project-profile.json。

③ 闸门优先于速度

「要动手」的 skill 都有审批门。门没过，代码一行不写。想快，就在门上及时回「通过」。

用不好这套 skill 的症状只有三种：提问太泛（动作无法映射 → 被降级到咨询）、门上一言不发（skill 卡在等你确认）、跳轨（小需求用了重装轨）。后面每条都有对治。

03核心契约：快照 + LATEST 指针

tri-intent 的唯一交付产物是一份快照，快照 §三 是下游 skill 的唯一输入源。

# .tribro/snapshots/I11_20260923_181207_6a5c037d.md

一、用户原始提问（原文，不加工）
二、意图分析过程（L1/L2/D1–D5 逐步判定推导）   ← 溯源用
三、结构化结论（下游 skill 直接读取执行区）   ← 机器消费用

§三 是 YAML 块，核心字段：一句话复述 / intent{L1,L2,L3_子意图,置信度,置信度档位} / dimensions{D1–D5} / 任务要点 / 澄清门状态 / 交付预期 / 下游路由建议 / 下游 slug。

下游按四级优先级定位快照

优先级定位方式说明
①.tribro/LATEST.md 的 snapshot_path推荐路径，最稳
②会话 ID 匹配的最新快照同会话多次提问时用
③全局最新且修改时间 ≤ 30 分钟超时即过期，不得使用
④校验 intent.L2 属于本 skill 认领范围越界即停止并回退重路由
三个直接后果
  • 快照有时效：超过 30 分钟未使用，下游会要求重新识别。别隔夜再喊「继续」。
  • 下游会拒绝越界：快照 L2 与 skill 认领范围不符时它会停下来回退重路由，不会将就。
  • 低置信度不放行：置信度档位=低（<0.60）时下游直接拒绝执行，强制回 clarify-gate。把需求说清楚是省时间的唯一办法。

05三条落地轨道 + 决策表

轨道 A · 轻轨 —— 单功能 / 小需求
tri-intent (I11)→ requirements.md→门①需求审批→ design.md→门②设计审批→ tasks.md→门③执行前确认→ 执行 + 测试→implements.md

承接：tri-coding v1.7.0｜门数：3 道，全部落盘、逐级串行

门②消费链：读 .tribro/project-profile.json（技术栈/编码规范/DB 规范）→ 按 standards_doc 指针完整阅读项目规范文档（如 ops-pilot 的 docs/agents/project-standards.md）→ 逐条对照。测试先行（红绿循环）。

轨道 B · 规划轨 —— 先要方案
tri-intent (I13)→ plan-brief.md→门①方向确认→ plan.md→门②规划审计→ task-checklist.md→门③交付前确认

承接：tri-plan v1.3.0｜只出方案，不写代码、不执行。task-checklist 每项带「建议执行 skill」字段，可直接作为 tri-coding / tri-action 的输入。

轨道 C · 重装轨 —— 整项目端到端
tri-intent (I11/I13/I14 + L3=sdlc)→ P0P1P2P3 P4P5P6P7P8

承接：tri-sdlc v1.1.3｜每阶段「派发 → 审计 → 确认」三拍。闸门① 逐条对照 68 条必检项 + 21 条建议项；FAIL 携修订意见回炉，连 3 轮 FAIL 停机。剖面裁剪：full P0–P8｜standard 跳 P3/P8｜lite 只跑 P1 P2 P4 P6——skill 建议 + 你确认，不会静默裁剪。

轨道选择决策表

你的需求长相走哪条判据
「写个 XX 功能 / 改一下这个模块」轻轨 tri-coding目标代码不存在，单功能/模块
「PM 给了原型链接，帮我解析后开始编码」tri-prototype → tri-coding有原型链接或 PRD，需先解析成 requirements.md 再进 tri-coding 门②
「先出个方案 / 排个期 / 拆下任务」规划轨 tri-plan只要文档，不要动手
「按完整流程做个项目 / 从零到上线」重装轨 tri-sdlc交付对象是一个真实项目
「设计 CI 流水线 / 审批流 / DAG」tri-workflow交付物是流程定义，交付即结束
「建知识库 loop / 定期跑的循环」tri-loop交付物是长期循环体，无明确终点
「这个报错查一下」tri-fix有可复现故障
「帮我 review / 审一下这次改动」tri-review只看不改
「生成审计清单 / commit 前清单」tri-checklist要可勾选 checklist
「分析项目架构 / 画架构图」tri-html架构可视化
「把某人的方法论做成 skill」tri-god产物是一个可独立调用的 skill
「把需求拆给 N 个人并行做，总 todo 自动回写」tri-orchestrate协作编排：拆 spec + 分派 + 回执收集 + 汇总看板
「需求有歧义，逐条质询到对齐再动手」tri-grill六维质询（歧义/边界/反例/术语/依赖/优先级），消除「PM 说 X、Dev 理解成 Y」
「统一术语 / 记设计决策 / 补边界场景」tri-domain产出 CONTEXT.md 术语表 + docs/adr/ + 边界场景清单
「首次把项目接入 tri-stack / 初始化」tri-init（直调，不经路由）扫描技术栈 → 生成 AGENTS.md + project-profile + .tribro/；用户直接说「初始化这个项目」
「长期学某门课 / 长期求职辅导」tri-learn / tri-jobhunt领域单入口，不按单次意图
优先级冲突 sdlc 子类最高

子类可能同时命中时的优先序：sdlc > workflow > loop；pm-prototype 子类（原型链接/PRD 转需求）命中时直接覆写为 tri-prototype。最终以「交付对象是一个真实项目 / 一份流程定义 / 一个长期循环体 / 一份编码需求文档」四者择一。sdlc 子类靠任务要点语义触发，不是表层动词。

06SOP：7 步完成一次需求落地

Step 0 · 环境准备

# 自维护模式（远端比对已停用）：skill 经 junction 安装在本地，无需从平台下载
# 检查安装状态：
python ops/install-skills.py --target ~/.workbuddy/skills
# → 缺失的 skill 自动补装 junction；已存在的跳过

# 版本门为本地自校验（SELF_MAINTAINED），不发起任何远端请求：
python <skill>/scripts/check_update.py --slug <slug> --json
# 退出码 <20 放行，>=20 阻断（A 一致 / D 漂移均放行，D 附加告警）

# 新项目首次接入（tri-init 直调，不经 tri-intent 路由）：
# 对 AI 说「初始化 D:\path\to\project」→ 生成 AGENTS.md + .tribro/project-profile.json
# 已有 AGENTS.md 会先备份再询问；已有项目规范文档（docs/agents/project-standards.md 等）
# 会写入 profile 的 standards_doc 指针（唯一事实源，冲突以原文为准）

Step 1 · 把需求说出来（决定命中率）

意图识别的主键是核心动词。动词能映射到具体 I 编码就能精准分派；太泛（「搞定」「搞一下」）会降级为 I03 建议咨询并强制先澄清。

别这样问这样问为什么
帮我搞定那个表格的事用 React + TypeScript 写一个支持关键字搜索和分页的表格组件泛化动作无法映射 → 降级 I03
优化一下优化一下这段 SQL 的查询性能（附代码）动作明确但对象缺失 → 不降级，但会先澄清对象
（只丢一个原型 URL，无文字）PM 给的原型链接：https://…，解析出编码需求文档「解析出」定动作 +「原型链接」定对象 +「编码需求文档」定产物 → 三信号锁定 pm-prototype

补充维度能显著提升质量：说明任务领域、是否有素材、要多细、期望什么形态。这些写进快照 D1–D5，下游按它调整策略。

Step 2 · 被澄清时

反问模式: G1 苏格拉底式(引导) 或 G2 批判式(挑刺)
初步理解: 你想做数据看板，但没说给谁看、看哪些指标
需澄清项:（≤3 条，每条带「建议默认」）
回复方式: 逐条补充 | 回「按默认」全采纳 | 「继续」表示无需澄清

Step 3 · 识别与落盘

每个 skill 作答前会打一行自检句，这是判断「它有没有跑对」的窗口：

tri-intent：
本次意图=I11，置信度=0.92/高，版本检查=已通过，已产出快照+LATEST 指针，
路由建议=tri-prototype，下游检测=已安装，分发=直接交接

tri-prototype： 本次意图=I11，已读取快照，原型链接=Axure，PRD=有，保真度=高，衔接目标=tri-coding 门②
tri-coding： 本次意图=I11，已读取快照，当前阶段=门②设计审计
tri-sdlc：   本次意图=I11·sdlc，已读取快照，剖面=lite，当前阶段=P2，状态=待审计，门禁=未审计

Step 4 · 选轨道并确认

按 §05 决策表。若 tri-intent 建议的轨道与你想的不一样，直接说——它会更新快照，不设多轮审批。重装轨会问你剖面，这一步省时效果最大。

协作层时机：需求有歧义、多方理解可能不一致 → 先 tri-grill 质询对齐再进开发；需要多人并行分工 → tri-orchestrate 拆 spec 分派；术语/决策需要沉淀 → tri-domain 记 CONTEXT.md / ADR。先对齐、再拆解、后编码，比回炉便宜得多。

Step 5 · 过门（主循环）

门的三种结果
  • 通过 → 阶段置「已通过」，进入下一阶段
  • 打回 + 说清哪里不对 → 携修订意见回炉该阶段，轮次+1
  • 回退 说「回退到 Pn」→ 级联重置：Pn 之后全部置「未开始」，已产出物标 stale

反规避规则（对你有保护）：门禁不因「用户着急」下调标准；也不由编排器代笔补全交付物——补全必须回炉给对应子 SKILL。所以门上说「快点过」无效，真正快的方式是把需求一次说清，减少回炉轮次。

Step 6 · 执行后加装验证

想加什么在哪加怎么加
代码审查门③「执行前确认」被问到①是否调其它 skill 协同 → 答「调 tri-review」
审计清单任何改动前后说「生成这次改动的审计 checklist」→ tri-checklist 四维覆盖
幻觉消除由下游委派或直说说「验证这个结论」→ tri-true 四道防线
成本审计对话过长 / 关心开销时tri-cost 统计全过程 token 开销，可设预算闸门
skill 安全审计安装任何 skill 前tri-guard 委派 skillspector 确定性扫描
去 AI 化改写成稿后tri-humanize：5 条速查 + 35 种模式 tri-article 已内置委派

tri-fix 值得单独记住：第一性规则是「没有能变红的反馈循环，就没有假设阶段」。在一条你真实跑过、且在这个 bug 上失败的命令出现之前，它只允许做一件事：构造这条命令，不会凭代码阅读跳到根因。

tri-review v1.6.0：Phase 0/1/2 + Fowler 12 坏味 + 覆盖度账本（双源分离 + gaps）+ 反证据关闭门 + 严重度校准 rubric + 审查执行纪律八则。

Step 7 · 沉淀（可选，复利最高）

  • tri-cache v2.1.1 提供四层缓存（滑动窗口 / 结构化存储 / 轻量摘要 / 向量检索）+ 上下文压缩。I11/I12/I17–I20/M01–M04 不缓存（代码和故障会变）。
  • tri-evolve 从外部信号归因学习。改 skill 核心契约属高风险须人工审批；经验沉淀过 A/B 验证门（lift ≥5%，p<0.05）。
  • tri-god：说「把这套流程做成 skill」→ 识别蒸馏对象类型 → 加载方法论 → 双门 → 产出 skill。按家族规范锻造走 tri-forge（mode C，五门流程）。

10避坑清单（实战教训）

级别症状根因对治
P0skill 停下来一直问它在等你过门 / 等你澄清回 通过 或 按默认。这是设计不是故障
P0想接着昨天的活干，它要求重新识别快照过期（>30 分钟）同会话内连续推进；跨会话就重说一遍的需求
P0profile 里的规范与项目实际规范冲突（实例：del_flag 被写成「0=存在/2=删除」，项目硬规则是 0=正常/1=删除）生成 profile 时未发现项目已有规范文档，凭通用口径填写消费 profile 的 standards_doc 指针读原文，冲突一律以项目规范文档为准；发现冲突立即修 profile 并回报
P1包管理器被识别错（实例：项目实际用 pnpm，扫描器因遗留 package-lock.json 报 npm）lock 文件可能是历史遗留产物检测结果交用户确认后才写入 profile；冲突以用户确认为准并记 package_manager_note
P1小需求被拉成九阶段工程任务要点带了「完整流程/端到端/上线」→ 命中 sdlc 子类要么去掉那些词，要么接受并选 lite 剖面
P1说「搞定一下」结果只给了建议不动手动作泛化无法映射 → 降级 I03 + 强制澄清把动词说具体（写/改/修/翻译/审查/设计）+ 给对象
P1只丢一个原型 URL 没有文字说明缺意图描述，L3 子意图判定置信度下降链接附一句话：「PM 给的原型链接，解析出编码需求文档」——三信号锁定 pm-prototype
P1门禁连续 FAIL 一直在回炉需求/设计有结构性缺陷连 3 轮 FAIL 会停机；此时该回退到 P1/P2 改需求，而非继续打回
P2交付物上看不到源码源码应在你的工作区，不在 .tribro去 implements.md / release-report.md 看记录的路径
P2想知道某 skill 版本是否漂移自维护模式不与任何远端比对ops/version-lint.py 五点一致性校验（当前 46/46 全绿）；skill 内 check_update.py 返回 A/D 态
最短路径

新项目先 tri-init 直调初始化 → 说清需求（动词 + 对象 + 形态）→ 过澄清 → 认轨道 → 门上及时回「通过」→ 执行后按需加 tri-review / tri-checklist / tri-guard / tri-true。要快，唯一有效的杠杆是减少回炉轮次，不是催它放行——门禁不吃催。
