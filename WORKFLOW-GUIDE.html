tri-skills · v1.0.0 · 24 skills

使用手册：从一句需求到落地交付

这套 skill 不是工具箱，是一条流水线。它的设计内核只有三件事：意图只识别一次（快照交接）、每步落盘可溯源（.tribro 链路文档）、关键节点不放行不推进（审批门）。理解这三件事，24 个 skill 就是一条路，不是 24 个工具。

01先记住心智模型：三句话

① 意图只识别一次

所有提问先过 tri-intent，产出快照交给下游。下游 skill 绝不重新识别意图——它们只读快照 §三。

② 一切落盘

链路文档进 .tribro/（快照/规划/编码/SDLC 全留痕）；真实成果物（源码、CHANGELOG）进你的工作区。

③ 闸门优先于速度

凡是「要动手」的 skill 都有审批门。门没过，代码一行都不会写。想过得快，就在门上报「通过」。

反过来说，用不好这套 skill 的典型症状也只有三种：提问太泛（动作无法映射，被降级到咨询）、门上一言不发（skill 卡在等你确认）、跳轨（小需求用了重装轨，或大项目用了轻轨导致返工）。后面每一条都有对治。

02全景：24 个 skill 的五层结构

按「在流水线上的位置」分五层。你日常只需要认识入口层和编排层；执行层是被路由自动拉起来的，横向层是被委派或 hook 拉起来的。

L0 入口层 · 唯一入口v1.10.0
tri-intenttri-intent/clarify-gate

任何新提问的第一步：三分法判定（Asking / Doing / Expressing / Meta）→ 下钻二级意图 → 标注 D1–D5 正交维度 → 打置信度 → 落快照 → 交接下游。需求模糊则先过 clarify-gate。

L1 执行层 · 按意图分派12 个
tri-asktri-contenttri-articletri-coding tri-fixtri-reviewtri-plantri-action tri-bstri-mmtri-musictri-expresstri-god

拿快照、干专业活、产出成果物。每个都有自己的一套阶段与闸门（见 §04）。

L2 编排层 · 长链路 / 流程定义3 个
tri-workflowtri-sdlctri-loop

tri-workflow=设计一个流程（产出 CI 配置/DAG/审批模板就结束）；tri-sdlc=驱动一个真实项目走完 P0–P8；tri-loop=建一个长期运行的知识库循环体。三者极易混，判据见 §04 决策表。

L3 横向能力层 · 被委派或 hook 唤起4 个
tri-truetri-cachetri-evolvetri-translate

不占意图落点、不被路由。tri-true 消除幻觉（四道防线）、tri-cache 指纹去重复用、tri-evolve 从反馈中沉淀经验与画像、tri-translate 翻译方法论（信达雅）。你不用主动叫它们，下游 skill 会在需要时委派。

L4 元层 · 对话控制与清单2 个
tri-metatri-checklist

tri-meta 处理 M01–M04（澄清追问/纠错反馈/追加细化/能力询问）；tri-checklist 是 I10 的审计清单子类，产出可勾选的四维 checklist（改动点/审查点/测试点/测试步骤）。

一个容易踩的边界：tri-mece-audit 不是 skill

仓库根目录下的 tri-mece-audit/ 里只有一个 HTML，不参与路由、不出现在路由表里。别把它当成第 25 个 skill 去调用。

03核心契约：快照 + LATEST 指针

这是整套系统里最需要理解的一个机制。tri-intent 的唯一交付产物是一份快照，快照里的 §三 是下游 skill 的唯一输入源。

快照长什么样

# .tribro/snapshots/I11_20260923_181207_6a5c037d.md

一、用户原始提问（原文，不加工）
二、意图分析过程（L1/L2/D1–D5 逐步判定推导）   ← 溯源用
三、结构化结论（下游 skill 直接读取执行区）   ← 机器消费用

§三 是一个 YAML 块，核心字段如下（下游就靠这几个字段干活）：

一句话复述: 你要我用 React 写一个可搜索的表格组件

intent:
  L1_交互类型: B.Doing
  L2_核心意图: I11 编码开发
  L3_子意图: 无            # 仅子类路由时填 sdlc|workflow|loop|music|article
  置信度: 0.92
  置信度档位: 高            # 高≥0.85 / 中0.60–0.85 / 低<0.60

dimensions:
  D1_任务领域: 编程
  D2_输入形态: 无
  D3_交互轮次: 单轮
  D4_输出期望: 可执行代码
  D5_确定性: 明确

任务要点: [...]
澄清门状态: 已跳过(需求清晰)
交付预期: 可编译、含单测的表格组件

下游路由建议: I11 → 编码开发 skill（tri-coding）
下游 slug: tri-coding        # 依赖检测直接消费这个字段

下游怎么找到这份快照

快照文件名含会话 ID，下游无法凭空推算。所以 tri-intent 落盘快照的同时会覆盖写一个指针文件 .tribro/LATEST.md。下游按四级优先级定位：

优先级定位方式说明
①.tribro/LATEST.md 的 snapshot_path推荐路径，最稳
②会话 ID 匹配的最新快照同会话多次提问时用
③全局最新且修改时间 ≤ 30 分钟超时即过期，不得使用
④校验 intent.L2 属于本 skill 认领范围越界即停止并回退重路由
给运维的三个后果
  • 快照有时效：超过 30 分钟未使用，下游会要求重新识别。别隔夜再喊「继续」。
  • 下游会拒绝越界：如果快照 L2=I13 而你想让 tri-coding 干活，它会停下来回退重路由，不会将就。
  • 低置信度不放行：置信度档位=低（<0.60）时下游直接拒绝执行，强制先回 clarify-gate。所以把需求说清楚，是省时间的唯一办法。

双向依赖检测（上下游互查）

上游查下游、下游查上游，任一端缺失都会提示安装，不会静默失败：

# tri-intent 侧：产出快照后检测下游是否安装
python tri-intent/scripts/check_downstream.py --slug tri-coding --json
# 退出码 0=全部已安装 / 1=存在缺失；检测四处安装位置 + 注册表

未安装时会走两道确认门：门①问「是否现在安装」→ 同意则发送安装 prompt → 复检脚本自证安装成功 → 门②问「是否立即执行」。拒绝任一门的后果是停在快照态，快照仍在，随时可续。

04三条落地轨道怎么选

需求落地的全部路径就是三条轨道 + 若干旁支。选错轨道是最大时间浪费来源。

轨道 A · 轻轨 —— 单功能 / 小需求
tri-intent (I11)→ requirements.md→门①需求审计→ design.md→门②设计审计→ tasks.md→门③执行前确认→ 执行 + 测试→implements.md

承接：tri-coding（v1.5.2）｜适用：写一个功能/模块/脚本，目标代码尚不存在｜门数：3 道，全部落盘、逐级串行

特色：门②的「氛围校准」会扫你的项目特征文件（tsconfig.json/go.mod/pubspec.yaml…），从 tech-skills/ 注册表匹配出技术栈规范（general 基底 + 24 个技术栈）注入 design.md，执行阶段有约束力。新增技术栈零改动 SKILL.md。

轨道 B · 规划轨 —— 先要方案，再决定做不做
tri-intent (I13)→ plan-brief.md→门①方向确认→ plan.md→门②规划审计→ task-checklist.md→门③交付前确认

承接：tri-plan（v1.2.1）｜适用：要 WBS 分解 / 排期 / 里程碑 / 任务清单｜关键：只出方案，不写代码、不执行

衔接下一跳：task-checklist.md 每项都带「建议执行 skill」字段。tri-coding 与 tri-action 可直接拿它当输入。门③会主动问你两件事：① 是否需要调其它 skill 协同 ② 是否有补充约束。这是挂接下游的官方接口，别说「没有了」就完事。

轨道 C · 重装轨 —— 整项目端到端交付
tri-intent (I11/I13/I14 + L3=sdlc)→ P0 立项→P1 需求→ P2 设计→P3 开发准备→ P4 编码→P5 评审→ P6 测试→P7 发布→ P8 运维

承接：tri-sdlc（v1.1.1）｜适用：「按完整研发流程做个项目」「从零到上线」

每一阶段是「派发 → 审计 → 确认」三拍：把阶段交给 children/tri-<name>/ 子 SKILL 产出交付物 → 闸门① 逐条对照 gates/acceptance-criteria.md 的 68 条必检项 + 21 条建议项判定，产出 gate-report.md（FAIL 则携修订意见回炉，轮次+1，连 3 轮 FAIL 停机请人工介入）→ 闸门② 呈交给你确认。

剖面裁剪（省时的关键）：full P0–P8 全量（正式立项）｜standard 跳过 P3/P8（已有工程环境，常规迭代）｜lite 只跑 P1 P2 P4 P6（单功能快速闭环）。剖面由 skill 建议 + 你确认，不会静默裁剪。

状态机：.tribro/sdlc/<命名>/manifest.md 维护十态；支持 12 类自然语言指令：START / STATUS / APPROVE / REJECT / ROLLBACK / SKIP / PROFILE / REGATE / FASTMODE / PAUSE / RESUME / ABORT。回退是级联的：说「回退到 P2」会把 P2 之后所有阶段重置为未开始，已产出物标记 stale。

轨道选择决策表

你的需求长相走哪条判据
「写个 XX 功能 / 改一下这个模块」轻轨 tri-coding目标代码不存在，单功能/模块
「先出个方案 / 排个期 / 拆下任务」规划轨 tri-plan只要文档，不要动手
「按完整流程做个项目 / 从零到上线」重装轨 tri-sdlc交付对象是一个真实项目
「设计一个 CI 流水线 / 审批流 / DAG」tri-workflow交付对象是流程定义产物，交付即结束
「建一个知识库 loop / domain / 定期跑的循环」tri-loop交付对象是长期循环体，无明确终点
「这个报错查一下 / 跑不通了」tri-fix有可复现故障
「帮我 review 一下 / 审一下这次改动」tri-review只看不改
「生成审计清单 / commit 前检查清单」tri-checklist要可勾选的 checklist，不是结论报告
「把某人的方法论做成 skill」tri-god产物是一个可独立调用的 skill
优先级冲突 sdlc 子类最高

三个子类（sdlc / workflow / loop）可能同时被命中。规则是：sdlc 优先于 workflow、workflow 优先于 loop，最终以「交付对象是一个真实项目 / 一份流程定义 / 一个长期循环体」三者择一。而且 sdlc 子类的判据是任务要点里的语义，不是表层动词——你用「规划」还是「做个项目」开头，都可能落到 tri-sdlc。

05SOP：7 步完成一次需求落地

Step 0 · 环境准备（一次性）

# 方式一：克隆
git clone https://github.com/TrisighT9527/tri-skills.git

# 方式二：SkillHub prompt（任一支持 SkillHub 协议的环境）
请根据 https://skillhub.cn/install/skillhub.md，安装 tri-intent。

# 入口必须先装，其他按需；缺失会被自动检测出来并引导安装

版本门提醒（每个 skill 的第零步）：所有 skill 启动后的第一件事是跑版本检查脚本，连 skillhub 校验，24 小时节流一次。四态降级（A 通过 / B 离线 / C 通道不可用 / D 升级失败）一律放行，只有 BLOCK 才阻断。所以断网不会卡死流程，但你会在交付物上看到「版本校验未完成（离线）」的标注——这是标注，不是错误。

Step 1 · 把需求说出来（决定命中率的一步）

意图识别的主键是核心动词。动词能映射到具体的 I06–I16 / I21，就能精准分派；动词太泛（「搞定」「搞一下」「处理一下」）会被降级为 I03 建议咨询并强制先澄清。

别这样问这样问为什么
帮我搞定那个表格的事用 React + TypeScript 写一个支持关键字搜索和分页的表格组件泛化动作无法映射 → 降级 I03
优化一下优化一下这段 SQL 的查询性能（附代码）动作明确但对象缺失 → 不降级，但会先澄清对象
按完整流程做个项目按完整研发流程做一个图书借阅管理系统，要能上线加上「完整流程 + 交付物 + 目标」→ 稳定命中 sdlc 子类
设计个工作流设计一个 GitHub PR 提交后自动跑 lint + 单测 + 部署到预发环境的流水线补上触发方式 + 核心节点 → 模板匹配度 ≥70%

补充维度能显著提升质量：说明任务领域、是否有素材、要多细、期望什么形态（简答/长文/可执行代码/文件产物/分步指引）。这些会被写进快照的 D1–D5，下游 skill 直接按它调整策略。

Step 2 · 被澄清时（clarify-gate）

需求模糊/矛盾/缺关键信息时，会先出澄清对齐卡——一次只问 ≤3 个真正阻塞执行的问题，每项都带建议默认值：

反问模式: G1 苏格拉底式(引导) 或 G2 批判式(挑刺)
初步理解: 你想做数据看板，但没说给谁看、看哪些指标
需澄清项:
  - 问题: 目标用户是谁？
    为何要问: 缺它会导致指标口径偏差
    建议默认: 运营团队内部使用
回复方式: 逐条补充 | 回「按默认」全采纳 | 「继续」表示无需澄清

三种应答：逐条答 / 「按默认」全校准 / 「继续」跳过。默认值都给了，回答成本很低——别在这里沉默，这是唯一会卡住你的地方。

Step 3 · 识别与落盘（你什么都不用做，但要会看自检句）

每个 skill 作答前都会打一行自检句。这行字是你判断「它有没有跑对」的窗口：

tri-intent：
本次意图=I11，置信度=0.92/高，版本检查=已通过，已产出快照+LATEST 指针，
路由建议=tri-coding，下游检测=已安装，分发=直接交接

tri-coding： 本次意图=I11，已读取快照，当前阶段=门②设计审计
tri-sdlc：   本次意图=I11·sdlc，已读取快照，剖面=lite，当前阶段=P2 方案设计，状态=待审计，门禁=未审计

Step 4 · 选轨道并确认

按 §04 的决策表。如果 tri-intent 建议的轨道和你想的不一样，直接说——它会更新快照，不设多轮审批（这是唯一的「轻量复述」环节，需求已澄清时连这步都跳过）。

重装轨会在这里问你剖面（full / standard / lite），务必选对，这一步的省时效果最大。

Step 5 · 过门（逐级审批，这是主循环）

三条轨道的门都是同一套逻辑：产出文档 → 呈交你审计 → 通过才进下一步。你的应答方式见 §06 口令卡。

门的三种结果与对应动作
  • 通过 携反馈零意见 → 阶段置「已通过」，进入下一阶段
  • 打回 说清楚哪里不对 → 携修订意见回炉该阶段，轮次 +1；轻轨/规划轨是原地重做该文档，SDLC 是重新派发子 SKILL
  • 回退 说「回退到 Pn」→ 级联重置：Pn 之后全部置「未开始」，已产出物标 stale

反规避规则（对你有保护的）：门禁不会因为「用户着急」「内容大致齐了」下调标准；也不会由编排器自己代笔补全交付物——补全必须回炉给对应子 SKILL。所以你在门上说「快点过」是没用的，只会让门更啰嗦。真正快的方式是把需求一次说清，减少回炉轮次。

Step 6 · 执行后加装验证

想加什么在哪加怎么加
代码审查门③「执行前确认」被问到①是否调其它 skill 协同 → 答「调 tri-review」
审计清单任何改动前后说「生成这次改动的审计 checklist」→ tri-checklist 四维覆盖
幻觉消除由下游委派或你直说说「验证这个结论 / 消除幻觉」→ tri-true 四道防线
修 bug（不新写）—new：说「查一下这个报错」→ tri-fix（红循环铁律 + 6 阶段 + 3 门）

tri-fix 值得单独记住：它的第一性规则是「没有能变红的反馈循环，就没有假设阶段」。在一条你真实跑过、且在这个 bug 上失败的命令出现之前，它只允许做一件事：构造这条命令，不会凭代码阅读跳到根因。这是它比通用 debug 靠谱的原因，但也会让你觉得「它在绕」——让它绕完。如果实在构造不出循环，它会停下来向你要三样东西之一：环境访问权 / 抓取产物（HAR、日志转储、core dump、带时间戳录屏）/ 临时生产插桩许可。

Step 7 · 沉淀（可选，但复利最高）

  • tri-cache 自动缓存作答产物（SHA-256 前 16 位指纹去重、差异化 TTL）。注意 I11/I12/I17–I20/M01–M04 不缓存——代码和故障会变，缓存它们有害。
  • tri-evolve 从外部信号（你的显式反馈 / 隐式行为 / 缓存命中 / 纠偏记录）中归因学习。改 skill 核心契约属高风险，必须人工审批；经验沉淀要过 A/B 验证门（lift ≥5%，p<0.05）。
  • tri-god：如果你发现某套流程反复用，说「把这套流程做成 skill」，它走「识别蒸馏对象类型 → 加载方法论 → 双门 → 产出 skill」。

06三道门怎么答（口令卡）

把下面这些原样复制使用，识别率最高。

场景你说效果
门上的文档没问题通过阶段置「已通过」，推进下一阶段
方向对但细节要改打回，XX 章节的第 3 条改成 YY携修订意见回炉，轮次 +1（历史轮次保留不删）

07场景速查：这样问就对了

场景照抄这句链路你会拿到
新写一个功能 用 React + TypeScript 写一个支持关键字搜索和分页的表格组件，要可编译、带单测 tri-intent(I11) → tri-coding 3 门 .tribro/coding/<n>/ 下 requirements / design / tasks / implements + 组件代码落工作区
修复一个报错 查一下这个报错：TypeError: Cannot read properties of undefined（附堆栈） tri-intent(I12) → tri-fix 6 阶段 3 门 bug-report（含能变红的循环）/ diagnosis（3–5 个可证伪假设）/ fix-tasks / fix-report
审查一次改动 审查一下当前分支相对 main 的改动，走规格合规 + 代码质量两阶段 tri-intent(CR) → tri-review（Phase1 未过不进 Phase2） review-report.md：6 维度 + 12 种 Fowler 坏味，只记录不修改
架构师视角审计增量 增量审计这个项目，以架构师视角看改动给修复建议和优先级 tri-review 增量审计模式（不依赖快照） Phase 0 三维审计：代码设计改动 / 架构设计实现 / 功能设计实现 + 修复建议 + 优先级
只要方案不要代码 给「订单履约时效优化」出个方案，要 WBS 分解、里程碑、风险登记和任务清单 tri-intent(I13) → tri-plan 3 门 plan-brief / plan / task-checklist（每项带「建议执行 skill」）

设计一条流水线 设计一个 GitHub PR 提交后自动 lint + 单测 + 部署预发的流水线 tri-intent(I13/I14 + workflow 子类) → tri-workflow 7 阶段 .github/workflows/<n>.yml + 设计文档 + 统一 DSL + 依赖校验与可执行性报告

建长期循环体 建一个「竞品动态周报」的知识库 loop，每周一跑 tri-intent(I14 + loop 子类) → tri-loop domains/<name>/README.md（charter + Timeline）+ LOG.md 条目 + 一次真实测试运行
tri-loop 的「真实测试运行」不是走过场

它的核心断言是「证明这个 loop 确实能跑，而不只是文件夹存在」。所以会真的小规模跑一次（拉一条真实 SERP / 分诊几张真实工单 / 跑一个分析查询），并强制产出两个记录：README 的 ## Timeline 追加一行 + LOG.md 追加一条。artifact 可选，但这两条记录必须有。凭证缺失时它会做「能达到的最远 dry run」并标注差距。

08.tribro 目录地图

一个约定：链路文档进 .tribro/，真实成果物进工作区。判据是「这份东西是不是给人用的最终产品」——是，就落工作区；是过程留痕，就落 .tribro。

09避坑清单

级别症状根因对治
P0 skill 停下来一直问，你以为它卡死了 它在等你过门 / 等你澄清 看它最后一行的问题，回 通过 或 按默认。这是设计，不是故障
P0 想让它接着昨天的活干，它要求重新识别 快照过期（>30 分钟） 同会话内连续推进；跨会话就重新说一遍需求（成本很低）
P0 小需求被拉成了九阶段大工程 任务要点里带了「完整流程/端到端/上线」类语义 → 命中 sdlc 子类 要么去掉那些词，要么接受并选 lite 剖面（只跑 P1 P2 P4 P6）
P1 说「搞定一下」结果被当成咨询，只给了建议不动手 动作泛化无法映射 → 降级 I03 + 强制澄清 把动词说具体（写/改/修/翻译/审查/设计），并给对象
P1 下游 skill 拒绝执行，说要回退重路由 快照 L2 与 skill 认领范围不符（越界了） 让 tri-intent 重新识别，别硬塞
P1 门禁连续 FAIL，一直在回炉 需求/设计本身有结构性缺陷，不是措辞问题 连 3 轮 FAIL 会自动停机并请人工介入；此时该回退到 P1/P2 改需求，而不是继续打回
P2 交付物上看不到源码 源码应该在你的工作区，不在 .tribro 去 implements.md / release-report.md 里看记录的路径
P2 交付物标了「版本校验未完成（离线）」 网络不可达，走了 B 态降级放行 这是标注不是错误。想消除就先跑一次 check_update.py
P2 想跳过验证直接出代码 门禁不支持「着急就放行」 用 快速模式 自动过闸门②，但闸门① 的 FAIL 永远硬阻断——真有问题就一定拦
最短路径总结

说清需求（动词 + 对象 + 形态）→ 过澄清 → 认轨道 → 门上及时回「通过」 → 执行后按需加 tri-review / tri-checklist。要快，唯一有效的杠杆是减少回炉轮次，而不是催它放行——门禁不吃催。
