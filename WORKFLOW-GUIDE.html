01心智模型：三句话

① 意图只识别一次

所有提问先过 tri-intent，产出快照交给下游。下游 skill 绝不重新识别意图，只读快照 §三。

② 一切落盘

链路文档进 .tribro/；真实成果物（源码、CHANGELOG）进你的工作区。项目元数据在 .tribro/project-profile.json。

③ 闸门优先于速度

「要动手」的 skill 都有审批门。门没过，代码一行不写。想快，就在门上及时回「通过」。

用不好这套 skill 的症状只有三种：提问太泛（动作无法映射 → 被降级到咨询）、门上一言不发（skill 卡在等你确认）、跳轨（小需求用了重装轨）。后面每条都有对治。

02全景：编程工作流专线的 24 skill 分层

分支说明：本分支是编程工作流专线

本分支携带编程线 22 个 + 横向方法论 2 个（tri-evolve / tri-true），共 24 个。全量 46 个（另含内容生成、格式转换族、多模态、表达陪伴、领域单入口，以及另外 5 个横向方法论）保存在归档分支 archive-full-skills-20260924。分层轴只有一条：离编程主干的远近——G0 控制面，G1 是主干，G2 / G3 是它的手和眼，G4–G6 是邻近支撑。

为什么撤掉原来的 L0–L6

旧分层把三根轴压在了一起——交付对象（L1/L2）、调用方式（L4/L5/L6）、skill 性质（L3）。后果是「编程主线」被摊成三处（L1 主列表 / L1 子类族 / L2 编排层），一眼看不出主线有多重；同时 5 个「用户直调、不进路由」的内部工具被切成 L4「协作执行层」与 L6「内部工具层」两个名字。新分层只留一根轴，编程资产全部归到 G1–G5。

G0 控制面 · 分流与自我修正2

G5 内务 / 造物 · 直调3
tri-init 1.0.1 项目接入 tri-forge 1.0.4 skill 锻造 tri-god 1.2.2 I21 蒸馏造物

G6 相邻支撑 · 通用能力4
tri-plan 1.3.2 I13 tri-action 1.2.4 I14 tri-workflow 1.2.5 I13/I14 + workflow tri-loop 1.2.4 I14 + loop

不专属于编程，但编程任务天天用。tri-plan=只出方案不动手（plan-brief / plan / task-checklist，每项带「建议执行 skill」字段）；tri-action=真去干（下单 / 设提醒 / 发消息 / 调 API）；tri-workflow=交付一份流程定义（CI 配置 / DAG / 审批模板），交付即结束；tri-loop=建长期运行的知识库循环体，无明确终点。三者判据：交付对象是「真实项目 / 一份流程定义 / 一个长期循环体」，与 G4 的 sdlc 子类冲突时 sdlc 优先。

G7 横向方法论 · 被所有组调用2
tri-evolve 1.1.6 tri-true 1.1.4

不认领 L2 编码、不进路由表，由下游委派或用户显式调用激活。tri-evolve=多渠道信号驱动的持续改进（OODA 闭环 + 经验条目库 + 用户画像 + A/B 验证门 + 回滚；§调度安全门规定默认为手动批处理，定时为 opt-in 且依赖外部调度器）；tri-true=四道防线消除幻觉（置信度 → 事实源 T1–T4 → 多模型交叉 → 自反思修正，兜底为拒答/人审）。全量版另有 tri-cache / tri-translate / tri-cost / tri-guard / tri-humanize 五个横向型，未包含在本分支。

  • 通过（可按 skill 名推导）：coding/ fixes/ reviews/ plans/ actions/ workflows/ loops/ sdlc/ code-analyzer/ html/ checklist/ 等（本分支实际会产生的全部落盘目录）
  • 同上，但对应 skill 本分支未包含（仅归档分支适用）：content/ cost/ pdf2md/ article/ geo/ jobhunt/ 等
  • 已改名（2026-09-24）：arch-viz/→html/、audit-checklist/→checklist/（本分支）；tri-article/→article/、tri-geo/→geo/、tri-jobhunt/→jobhunt/（对应 skill 本分支未包含，仅归档分支适用）
  • 豁免（跨 skill 共享，登记于 tri-forge/references/family-spec.md §1.4）：snapshots/（tri-intent）、skills/（tri-forge 生成物位）。multimedia/（原 tri-mm，slug 为缩写）本分支未包含。另 specs/ 嵌在 coding/ 下，不占顶层

规则已固化可判定：合规清单第 10 条现在要求——新建 skill 的落盘目录名不可推导、又未登记豁免，即门④ FAIL；skill 目录内出现 .tribro/ 同样 FAIL（会经 junction 安装暴露、被打包收录）。

第三类产物区（跨项目台账）：除上表两类，家族还承认落在项目根、不属 .tribro/ 的跨项目台账。典型例子 .geo-snapshots/<品牌>/ 来自原 tri-geo（本分支未包含，仅归档分支适用），本分支目前无第三类产物区实例。它同样受可推导性判据约束，且 MUST 登记于 family-spec.md §1.4 第三类清单；NEVER 迁入 .tribro/——判据是数据的生命周期跟随「业务实体」还是「项目」，跟随业务实体者迁入会被项目目录切碎。

另有两处未解决（独立问题，不属命名范畴）：tri-frontend-design 与 tri-grill 的交付物没有固定 .tribro/ 落点，只随对话交付；两者若接入门禁审计，会因「定位不到固定产物」而无法取证。

仓库根该目录只有一份 HTML 审计报告，不是 skill、不参与路由。它是 tri-forge 重建前的取证资料存档。

03核心契约：快照 + LATEST 指针

tri-intent 的唯一交付产物是一份快照，快照 §三 是下游 skill 的唯一输入源。

# .tribro/snapshots/I11_20260923_181207_6a5c037d.md

一、用户原始提问（原文，不加工）
二、意图分析过程（L1/L2/D1–D5 逐步判定推导）   ← 溯源用
三、结构化结论（下游 skill 直接读取执行区）   ← 机器消费用

§三 是 YAML 块，核心字段：一句话复述 / intent{L1,L2,L3_子意图,置信度,置信度档位} / dimensions{D1–D5} / 任务要点 / 澄清门状态 / 交付预期 / 下游路由建议 / 下游 slug。

下游按四级优先级定位快照

优先级定位方式说明
①.tribro/LATEST.md 的 snapshot_path推荐路径，最稳
②会话 ID 匹配的最新快照同会话多次提问时用
③全局最新且修改时间 ≤ 30 分钟超时即过期，不得使用
④校验 intent.L2 属于本 skill 认领范围越界即停止并回退重路由
三个直接后果
  • 快照有时效：超过 30 分钟未使用，下游会要求重新识别。别隔夜再喊「继续」。
  • 下游会拒绝越界：快照 L2 与 skill 认领范围不符时它会停下来回退重路由，不会将就。
  • 低置信度不放行：置信度档位=低（<0.60）时下游直接拒绝执行，强制回 clarify-gate。把需求说清楚是省时间的唯一办法。

04版本门：自维护模式

每个 skill 启动后的第零步都会跑 scripts/check_update.py。全部 24 个 skill 内置 SELF_MAINTAINED = True：完全跳过远端请求，改为校验本 skill 自身 5 处版本声明的一致性。

轨道 D · 协作链 —— 需求成形 → 对齐 → 沉淀 → 规划 → 分派 → 编码
tri-init 可选前置→ tri-prototype 需求成形→ tri-grill 对齐→ tri-domain 沉淀→ tri-plan 规划→ tri-orchestrate 分派→ tri-coding × N 并行→ tri-review 收口

与 A–C 的本质区别：那三条按 L2 意图切（一个意图一条轨道）；这条按 阶段串，横跨 I11 与 I13 两个 L2——前半段（需求成形 / 对齐 / 沉淀 / 规划）是 I13 语义，后半段（编码）是 I11 语义，所以「按意图分派」的模型装不下它。中间三个节点 tri-grill / tri-domain / tri-orchestrate 是不注册路由表的内部专用工具，由用户直接调用，本就没有 L2 意图。

何时走：需求有歧义、多方理解可能不一致 → 先 tri-grill 质询对齐；术语 / 决策需沉淀 → tri-domain 记 CONTEXT.md + docs/adr/；需多人并行分工 → tri-orchestrate 拆 spec 分派。先对齐、再拆解、后编码，比回炉便宜得多。

终止条件（重要）：tri-orchestrate 拆出的 N 份 spec 由多个人 / 多 agent 并行执行，执行完不回收到单机链路——本轨道在「分派」处即发散，收口靠 tri-review 逐份审。这是它天然不适配「单轨道闭环」模型的原因，也是当初只进决策表的理由。

与其他轨道的衔接：链走到 tri-plan 时即接入轨道 B 的三门；走到 tri-coding 时接入轨道 A 的三门。若需求本就带「端到端 / 完整流程」语义，优先走 轨道 C（tri-sdlc，子类优先级最高）。

轨道选择决策表

你的需求长相走哪条判据
「写个 XX 功能 / 改一下这个模块」轻轨 tri-coding目标代码不存在，单功能/模块
「PM 给了原型链接，帮我解析后开始编码」tri-prototype → tri-coding有原型链接或 PRD，需先解析成 requirements.md 再进 tri-coding 门②
「先出个方案 / 排个期 / 拆下任务」规划轨 tri-plan只要文档，不要动手
「按完整流程做个项目 / 从零到上线」重装轨 tri-sdlc交付对象是一个真实项目
「设计 CI 流水线 / 审批流 / DAG」tri-workflow交付物是流程定义，交付即结束
「建知识库 loop / 定期跑的循环」tri-loop交付物是长期循环体，无明确终点
「这个报错查一下」tri-fix有可复现故障
「帮我 review / 审一下这次改动」tri-review只看不改
「生成审计清单 / commit 前清单」tri-checklist要可勾选 checklist

「把需求拆给 N 个人并行做，总 todo 自动回写」tri-orchestrate协作编排：拆 spec + 分派 + 回执收集 + 汇总看板

优先级冲突 sdlc 子类最高

子类可能同时命中时的优先序：sdlc > workflow > loop；pm-prototype 子类（原型链接/PRD 转需求）命中时直接覆写为 tri-prototype。最终以「交付对象是一个真实项目 / 一份流程定义 / 一个长期循环体 / 一份编码需求文档」四者择一。sdlc 子类靠任务要点语义触发，不是表层动词。

Step 4 · 选轨道并确认

按 §05 决策表。若 tri-intent 建议的轨道与你想的不一样，直接说——它会更新快照，不设多轮审批。重装轨会问你剖面，这一步省时效果最大。

协作层时机：需求有歧义、多方理解可能不一致 → 先 tri-grill 质询对齐再进开发；需要多人并行分工 → tri-orchestrate 拆 spec 分派；术语/决策需要沉淀 → tri-domain 记 CONTEXT.md / ADR。先对齐、再拆解、后编码，比回炉便宜得多。

Step 5 · 过门（主循环）

门的三种结果
  • 通过 → 阶段置「已通过」，进入下一阶段
  • 打回 + 说清哪里不对 → 携修订意见回炉该阶段，轮次+1
  • 回退 说「回退到 Pn」→ 级联重置：Pn 之后全部置「未开始」，已产出物标 stale

反规避规则（对你有保护）：门禁不因「用户着急」下调标准；也不由编排器代笔补全交付物——补全必须回炉给对应子 SKILL。所以门上说「快点过」无效，真正快的方式是把需求一次说清，减少回炉轮次。

Step 6 · 执行后加装验证

想加什么在哪加怎么加
代码审查门③「执行前确认」被问到①是否调其它 skill 协同 → 答「调 tri-review」
审计清单任何改动前后说「生成这次改动的审计 checklist」→ tri-checklist 四维覆盖

tri-fix 值得单独记住：第一性规则是「没有能变红的反馈循环，就没有假设阶段」。在一条你真实跑过、且在这个 bug 上失败的命令出现之前，它只允许做一件事：构造这条命令，不会凭代码阅读跳到根因。

tri-review v1.6.2：Phase 0/1/2 + Fowler 12 坏味 + 覆盖度账本（双源分离 + gaps）+ 反证据关闭门 + 严重度校准 rubric + 审查执行纪律八则。

Step 7 · 沉淀（可选，复利最高）

  • tri-cache v2.1.1 提供四层缓存（滑动窗口 / 结构化存储 / 轻量摘要 / 向量检索）+ 上下文压缩。I11/I12/I17–I20/M01–M04 不缓存（代码和故障会变）。 本分支未包含（原 tri-cache，见归档分支）
  • tri-evolve 从外部信号归因学习。改 skill 核心契约属高风险须人工审批；经验沉淀过 A/B 验证门（lift ≥5%，p<0.05）。 本分支未包含（原 tri-evolve，见归档分支）
  • tri-god：说「把这套流程做成 skill」→ 识别蒸馏对象类型 → 加载方法论 → 双门 → 产出 skill。按家族规范锻造走 tri-forge（mode C，五门流程）。

10避坑清单（实战教训）

级别症状根因对治
P0skill 停下来一直问它在等你过门 / 等你澄清回 通过 或 按默认。这是设计不是故障
P0想接着昨天的活干，它要求重新识别快照过期（>30 分钟）同会话内连续推进；跨会话就重说一遍的需求
P0profile 里的规范与项目实际规范冲突（实例：del_flag 被写成「0=存在/2=删除」，项目硬规则是 0=正常/1=删除）生成 profile 时未发现项目已有规范文档，凭通用口径填写消费 profile 的 standards_doc 指针读原文，冲突一律以项目规范文档为准；发现冲突立即修 profile 并回报
P1包管理器被识别错（实例：项目实际用 pnpm，扫描器因遗留 package-lock.json 报 npm）lock 文件可能是历史遗留产物检测结果交用户确认后才写入 profile；冲突以用户确认为准并记 package_manager_note
P1小需求被拉成九阶段工程任务要点带了「完整流程/端到端/上线」→ 命中 sdlc 子类要么去掉那些词，要么接受并选 lite 剖面
P1说「搞定一下」结果只给了建议不动手动作泛化无法映射 → 降级 I03 + 强制澄清把动词说具体（写/改/修/翻译/审查/设计）+ 给对象
P1只丢一个原型 URL 没有文字说明缺意图描述，L3 子意图判定置信度下降链接附一句话：「PM 给的原型链接，解析出编码需求文档」——三信号锁定 pm-prototype
P1门禁连续 FAIL 一直在回炉需求/设计有结构性缺陷连 3 轮 FAIL 会停机；此时该回退到 P1/P2 改需求，而非继续打回
P2交付物上看不到源码源码应在你的工作区，不在 .tribro去 implements.md / release-report.md 看记录的路径
P2想知道某 skill 版本是否漂移自维护模式不与任何远端比对ops/version-lint.py 一致性校验（当前 24/24 全绿）；skill 内 check_update.py 返回 A/D 态
最短路径

新项目先 tri-init 直调初始化 → 说清需求（动词 + 对象 + 形态）→ 过澄清 → 认轨道 → 门上及时回「通过」→ 执行后按需加 tri-review / tri-checklist / tri-code-analyzer（安全审计 tri-guard 与 tri-true 本分支未包含）。要快，唯一有效的杠杆是减少回炉轮次，不是催它放行——门禁不吃催。
